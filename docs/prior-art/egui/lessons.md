# Lessons for Buiy

This is the consult-this-when-designing decision file. The other files in this corpus are evidence; this file is the synthesis. Three sections — **Validates** (Buiy choices that egui's experience confirms), **Avoid** (pitfalls to mitigate), **Borrow** (primitives worth studying).

This file pairs with [`../bevy-egui/lessons.md`](../bevy-egui/lessons.md) — the bevy_egui lessons cover the *bridge* (the wrapper crate's choices: per-camera contexts, picking-order resource, MIT-only license, two-layer pin); this file covers *upstream egui itself* (the paradigm, the rendering pipeline, the plugin API, the text-stack swap, the always-on AccessKit shift). Where the two overlap, this file defers; readers consulting both should treat bevy_egui's lessons as the more concrete operational notes and these as the more architectural ones.

Before everything else: the load-bearing finding for the whole corpus.

## Top-of-file finding: egui and Buiy occupy non-overlapping niches

egui's success at dev-tooling scale **validates immediate-mode for that niche** — 16.96M lifetime downloads, dominance of Rust dev-tool UI, validated production deployment at Rerun where the workload (streaming data, mostly-3D viewports with egui chrome) amortizes the immediate-mode rebuild cost against work the app would be doing anyway. egui is the *right tool* for: dev tools, inspectors, debug overlays, settings panels, configuration UIs, level editors, modding UI, asset browsers, prototypes, and Rerun-shaped streaming-data viewers. See [`immediate-mode-deep-dive.md`](immediate-mode-deep-dive.md) § "When immediate-mode is the RIGHT choice."

egui's absence from production game UI **validates retained-mode for that niche** — *by absence*, not contradiction. Through 16.96M downloads and seven years of Emil's stewardship, **no AAA or notable indie game ships its in-game UI on egui.** Tiny Glade wrote a custom UI renderer. Foresight Spar wrote a custom UI renderer. Polished consumer apps where distinctiveness matters are not on egui. Accessibility-critical apps where APG widget contracts are non-negotiable are not on egui. Complex-script i18n-critical apps are not on egui. 10k+-widget data-grid apps are not on egui. The cluster of weaknesses — homogeneous "looks like egui" aesthetic, per-frame rebuild cost, structurally bolted-on AccessKit, animation primitives that stop at `animate_value`, layout simpler than Flexbox/Grid, ad-hoc `Id` hashing — is the production-UI-grade-polish gap retained-mode is built to close. See [`critiques.md`](critiques.md) § "The 'Production Game UI' gap" and [`open-problems.md`](open-problems.md) § "The 'Production Game UI' gap."

**Buiy's retained-mode bet does not compete with egui; the two coexist.** Most real Bevy projects will use both — egui (via `bevy_egui`) for dev overlays / inspectors / editor panels, Buiy (or `bevy_ui` today) for shipped player-facing UI. The dev/ship pattern is documented in [`immediate-mode-deep-dive.md`](immediate-mode-deep-dive.md) § "The dev/ship pattern" and reinforced in [`/home/user/buiy/docs/specs/2026-05-07-buiy-foundation/cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.18.

The follow-on for every Buiy spec: **stop asking "should Buiy do X better than egui?" and start asking "does X belong on the production-UI axis Buiy targets, or on the dev-tool axis egui already owns?"** Most dev tooling answers "ship it on bevy_egui." Production UI answers "ship it on Buiy." The two are different problems, not different sizes of the same problem.

## Validates

These Buiy design choices are confirmed by egui's experience:

- **Retained-mode for production UI (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.3).** egui's absence from production game UI after seven years and 16.96M downloads is the single largest validation in this corpus. The cluster of weaknesses listed in [`critiques.md`](critiques.md) (homogeneity, animation gaps, layout simplicity, a11y structural ceiling, `Id` collisions, custom-widget complexity) is the production-UI gap retained-mode + entity-backed components closes. See [`open-problems.md`](open-problems.md) § "The 'Production Game UI' gap."

- **AccessKit as the a11y substrate (foundation [`accessibility.md`](../../specs/2026-05-07-buiy-foundation/accessibility.md)).** egui adopted AccessKit opt-in in 0.20.0 (2022-12-08) and made it **always-on in 0.34.0** (2026-03-26). Iced converged on AccessKit. bevy_ui converged on AccessKit. egui is now the third major Rust GUI library to ship default-on AccessKit. Buiy's AccessKit-first, default-on stance matches and slightly leads the consensus — egui's always-on shift validates the direction.

- **Owning the render pipeline end-to-end is a viable choice.** egui's `epaint` is a small custom tessellator targeting textured triangles with scissor clipping — no Skia, no Vello (yet), no external 2D graphics dep. The deliberate absence of a Skia backend (egui explicitly avoids the heavyweight C++ dep) shows that a Rust-native render pipeline with own-tessellator + own-atlas + own-clipping is shippable at 16.96M-download scale. Buiy's parallel render pipeline (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.3) follows the same shape — own-render-passes, own-atlasing, own-compositing — but uses Bevy's wgpu render graph as the substrate. See [`architecture.md`](architecture.md) § "Backend abstraction" and [`open-problems.md`](open-problems.md) § "egui's relationship to the Linebender stack."

- **Honest "Goals / Non-goals" framing in the project README.** Emil's egui README ships an explicit non-goals list ("Become the most powerful GUI library," "Native looking interface") and an unsolicited "Not recommended for" section ("non-Rust projects, applications requiring native OS appearance, or users needing API stability between versions"). This honest scoping has helped egui avoid feature-creep accusations and steer users to the right tool. Buiy's foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 1 non-goals list carries the same shape. See [`immediate-mode-deep-dive.md`](immediate-mode-deep-dive.md) § "Emil Ernerfeldt's design philosophy."

- **The tessellator + textured-triangle + scissor-clipping render path as a simple-but-sufficient baseline.** egui demonstrates that a minimal rendering model (mesh + texture + rect clip) covers the entire dev-tool workload without needing path rendering, non-rect clip, or filter effects. Buiy targets a richer surface (web-platform parity: `backdrop-filter`, `mix-blend-mode`, isolation, true top layer, non-rect clip via `clip-path`) and validates that egui's simpler baseline is correctly insufficient for that scope — confirming the parallel-stack decision in foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) goal 4.

- **The property-shape widget contract (`Response`, `Sense`).** Every egui widget returns an `egui::Response` carrying `clicked()`, `double_clicked()`, `secondary_clicked()`, `hovered()`, `dragged()`, `drag_delta()`, `has_focus()`, `interact_rect`, and pointer-coordinate accessors; widget interactivity is declared via `Sense::hover() | Sense::click() | Sense::drag()`. The shape generalizes cleanly across widgets and is well-loved in the community. Buiy's retained-mode widgets need a parallel contract (a `BuiyInteraction` component or `WidgetResponse`-shaped query) — the shape is borrowable even though the binding mechanism (ECS query vs procedural return value) differs. See [`api-surface.md`](api-surface.md) § "Widget vocabulary."

- **The compile-and-cache pattern for shaped glyphs.** egui's `epaint::text::Galley` is the unit of cached text — once a `(text, font, size, wrap)` tuple is shaped, the glyph positions + atlas references are cached and reused. The 0.34.0 release made `Galley::pos_from_layout_cursor` `pub` so high-perf consumers can avoid redundant re-shaping. Buiy uses cosmic-text, which has its own caching, but the *pattern* (shape once, cache the resulting layout, re-render from the cache for static text) is the right baseline. See [`text-rendering.md`](text-rendering.md) § "The text stack as of 0.34.x."

- **Variable-font support is non-optional going forward.** The 0.34.0 swap from `ab_glyph` to `skrifa` + `vello_cpu` was driven primarily by variable-font support (the original ab_glyph stack had no shaping, no hinting, no variable axes). egui shipping variable fonts in March 2026 sets the floor; any Rust UI library shipping today without variable-font support will look dated within a year. Buiy's cosmic-text dep covers this via `rustybuzz` → harfbuzz-equivalent shaping plus skrifa for parsing; the validation is "yes, this is the right scope to ship."

- **Single-author-with-commercial-steward governance works at egui's scale.** Emil + Rerun has held for seven years and produced a 16.96M-download project. The model — benevolent dictator, no foundation, no RFC process, an employer that uses the project as its core product surface — is structurally efficient. Buiy is currently single-author (intendednull) without a Rerun analog; the model is *aspirationally* borrowable but not directly replicable until Buiy has a commercial steward. The documentation-first discipline (`docs/specs/` + `docs/plans/` + `docs/prior-art/`) is the substitute for the single-architect's in-head knowledge. See [`governance.md`](governance.md).

- **"Use the right tool" mentality (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) goal 6 + non-goals).** Buiy explicitly is *not* positioning as an egui replacement, and the foundation spec is honest about what's in scope (production game + app UI) and what isn't (dev-tool UI is not Buiy-exclusive). This honest scoping mirrors Emil's "Not recommended for" stance. See [`immediate-mode-deep-dive.md`](immediate-mode-deep-dive.md) § "Emil Ernerfeldt's design philosophy."

## Borrow

Concrete primitives worth studying and adapting:

1. **The honest "Goals / Non-goals" README pattern.** Emil's upstream egui README ships an explicit non-goals list ("Become the most powerful GUI library," "Native looking interface") and a "Not recommended for" section. This honest scoping is the single most effective tool for steering users to the right library and avoiding feature-creep accusations. Buiy's foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 1 carries the same shape; the pattern is borrowable for every sub-spec too — every Buiy sub-spec should list non-goals up front. See [`immediate-mode-deep-dive.md`](immediate-mode-deep-dive.md) § "Emil Ernerfeldt's design philosophy."

2. **The `Response` / `Sense` widget contract shape.** Every egui widget returns an `egui::Response` carrying interaction state (clicked, double-clicked, secondary-clicked, hovered, dragged, focused, drag-delta, interact-rect, pointer coords); widget interactivity is declared via `Sense::hover() | Sense::click() | Sense::drag() | Sense::focusable_noninteractive()`. The shape generalizes cleanly. Buiy's retained widgets need a parallel contract — likely a `WidgetResponse` component or query result — and the property-shape (one struct with many predicate accessors) is borrowable. See [`api-surface.md`](api-surface.md) § "Widget vocabulary" and [`architecture.md`](architecture.md) § "Output: `egui::FullOutput`."

3. **The opt-in feature-flag pattern for AccessKit.** egui's `accesskit` Cargo feature was opt-in from 0.20.0 through 0.33.3 — the wrong default, but the *shape* of the gate is borrowable for the opposite direction: Buiy is AccessKit-default-on, but exposes a `no_a11y` feature for embedded / WASM size-sensitive consumers who want to drop the AccessKit adapter and platform crates. Hard constraint: the gate must never silently disable a11y under `default-features`. See [`open-problems.md`](open-problems.md) § "WASM bundle size."

4. **The Plugin trait API (0.33.0).** egui 0.33.0 introduced a trait-based `egui::Plugin` API with `on_begin_pass`, `input_hook`, `output_hook`, `on_end_pass`, and `on_widget_under_pointer` (added 0.33.2). Plugins are owned by the `Context` and run at fixed lifecycle points; state lives on the plugin struct directly. Composable extensions (inspectors, instrumentation, picker overlays) become first-class without polluting `Memory`. Buiy's plugin shape — likely a Bevy `Plugin` impl per extension, with explicit lifecycle hooks via Bevy `Schedule` ordering — borrows the principle (lifecycle-hook composability) even though the implementation differs (Bevy schedules vs context-owned trait objects). See [`architecture.md`](architecture.md) § "The plugin trait."

5. **The unified `Panel` API (0.34.0).** egui 0.34.0 consolidated `SidePanel::left` / `SidePanel::right` / `TopBottomPanel::top` / `TopBottomPanel::bottom` / `CentralPanel::default` into a single `Panel` type with directional config; legacy types still work as aliases. The shape — one primitive parameterized by edge + side, replacing four near-duplicate APIs — is a cleanup pattern Buiy can follow for resizable panels, sidebars, and dock primitives. See [`api-surface.md`](api-surface.md) § "Container widgets."

6. **The `skrifa` + `vello_cpu` text-rendering stack — worth studying as an alternative.** egui's 0.34.0 swap from `ab_glyph` to `skrifa` (Linebender's Rust port of FreeType's font-parsing primitives) plus `vello_cpu` (Linebender's CPU-only Vello variant) is the Linebender stack creeping into upstream egui. Buiy currently uses cosmic-text (rustybuzz + skrifa + swash). If parley becomes the dominant Rust text-shaping crate (because egui + Xilem + others adopt it), Buiy's `buiy-text-rendering-design` sub-spec should revisit the choice. Not urgent; worth watching. See [`text-rendering.md`](text-rendering.md) and [`open-problems.md`](open-problems.md) § "egui's relationship to the Linebender stack."

7. **The tessellator + scissor-clipping render path as a baseline.** Simpler than full `clip-path` (non-rect clip), simpler than path rendering, no filter effects. For the bulk of UI surfaces (rectangular widgets in rectangular containers), this is the right baseline path. Buiy's render pipeline should fast-path this case — most widgets don't need `clip-path` or `backdrop-filter`, so the rect-clip-textured-triangle path should be the default. See [`architecture.md`](architecture.md) § "Backend abstraction."

8. **The `egui_extras` + `egui_plot` second-party crate pattern.** Officially adjacent but not in core: `egui_extras` (image loaders, `Table` widget, `DatePickerButton`) and `egui_plot` (in a separate repo entirely). The pattern keeps core lean while still shipping advanced widgets under coordinated stewardship. Buiy can adopt the same shape — `buiy_core` is the minimal substrate; `buiy_plot`, `buiy_table_advanced`, `buiy_richtext_editor` ship as second-party crates that follow Buiy's release cadence but live separately. See [`distribution.md`](distribution.md).

9. **The embed-the-tutorial-in-the-demo authoring pattern (`egui_demo_lib`).** egui's demo lib is shipped as a library so other tools can embed the demo, and the demo source code is the tutorial. New users learn the API by reading the demo. Buiy's `buiy_demo` (foundation [`cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.16 — devtools) should follow the same pattern: ship the demo as a library so the inspector / contrast-checker / focus-visualizer can embed pieces of it. See [`distribution.md`](distribution.md) workspace listing.

10. **The Rerun streaming-data-amortizes-cost pattern (for if Buiy ever wants real-time data viz).** Rerun is the cleanest "immediate-mode at scale, in production" case study because Rerun's data is always changing (streaming sensor input) — there's no "unchanged frame" to optimize for, so the immediate-mode per-frame rebuild cost is amortized against work the app would be doing anyway. If Buiy ever targets a real-time data-visualization workload (engine telemetry overlays, profiler dashboards, live AI inspector), the lesson is "rebuild-every-frame is acceptable when the data forces a redraw anyway." For static-mostly UI (HUDs, menus, settings) it's not. See [`immediate-mode-deep-dive.md`](immediate-mode-deep-dive.md) § "Rerun's data visualization viewer" and [`ecosystem.md`](ecosystem.md) § "Rerun (the canonical at-scale user)."

## How to use this file

When designing a Buiy feature:

1. **Re-read the Top-of-file finding.** The instinct "make Buiy compete with egui on X" is usually wrong — egui owns the dev-tool axis Buiy doesn't target, and the cluster of weaknesses egui has on the production-UI axis is precisely the slot Buiy is built for. The two coexist; pick the right tool per UI surface.
2. **Find the row in `Avoid`** that names a pitfall close to your design. Read the linked file for the original incident; bring the mitigation back into the Buiy spec.
3. **Find the entry in `Borrow`** that names a primitive close to what you're designing. Read the linked file to understand the egui shape, then adapt for Buiy's retained-mode component model.
4. **Cross-check against `../bevy-egui/lessons.md`.** Where the two files overlap (multi-pass, picking, AccessKit, license, governance), the bevy_egui file has the more concrete operational notes; this file has the more architectural ones. Both are decision input.
5. **Promote any decision into a Buiy spec** under `docs/specs/` — this file is for capturing what we learn from egui, not for encoding Buiy's own decisions.
