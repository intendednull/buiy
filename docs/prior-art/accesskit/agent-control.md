# AccessKit as an agent-control surface

The rest of this folder reads AccessKit through the screen-reader lens: Buiy is the producer, the platform AT is the end consumer, the tree is the *output* that NVDA / VoiceOver / Orca narrate. This file reads the *same* tree through the **agent / automation** lens. The claim is structural: the AccessKit tree Buiy already authors is, with no change to the schema, the surface an LLM agent (or a test driver) would drive a Buiy UI through — and the inbound half of that contract is mostly already wired one layer down in `bevy_winit`. See [`tree-model.md`](tree-model.md) for the `Action` enum + `ActionRequest`/`ActionHandler` mechanics this file builds on; this file is the automation reading of them.

## 1. The bidirectional contract

AccessKit is not output-only by design. The schema has a request channel: an AT (or any client of the platform AX API) issues `ActionRequest { action: Action, target: NodeId, data: Option<ActionData> }`, the adapter routes it to the producer's `ActionHandler::do_action`, and the producer mutates its own state. A node advertises which verbs it accepts via `Node::add_action(Action::…)` — so the per-node action set *is an affordance menu*: "this node can be Clicked, this one Increment/Decrement'd, this one SetValue'd." An agent reading the tree reads not just "what is this" but "what can I do to it, by reference."

Buiy today exploits exactly none of this on the inbound side. The only action ever attached to any node is `add_action(accesskit::Action::Focus)` on focusable nodes (`a11y/translate.rs:38-39`), and even that declared `Focus` is never honored back into `FocusedEntity`. Buiy consumes **zero** inbound `ActionRequest`s — a grep across `crates/` for `do_action` / `ActionRequest` / `ActionHandler` / `MessageReader<ActionRequestWrapper>` finds no consumer. The tree is verified output-only. The affordance menu is empty and nobody reads the orders.

## 2. Platform AX as an automation substrate, not just a screen-reader feed

The same control-pattern interfaces AccessKit's adapters expose to screen readers are the ones GUI-automation stacks already drive: Windows UIA control patterns (`IInvokeProvider`/Invoke, `IToggleProvider`/Toggle, `IExpandCollapseProvider`, `IRangeValueProvider`) used by **WinAppDriver** and **Appium**; Linux AT-SPI `do_action` / `Action` interface used by **dogtail** and **Orca**; macOS `AXUIElementPerformAction` driven by `AXUIElement` automation. **Playwright** drives by accessible role+name. These tools never owned a screenshot pipeline; they act *by semantic reference* — find the node by role/name, request the action. That is the "set-of-marks" / semantic-locator pattern: each interactive node carries a stable handle, the driver names the handle, the toolkit performs the verb. AccessKit's adapters already publish Buiy's tree into exactly these interfaces (see [`platform-adapters.md`](platform-adapters.md): UIA control patterns on Windows, `accessibilityPerformAction:` on macOS, AT-SPI on Linux), so a UIA/AT-SPI automation client can *already* enumerate a Buiy window — it just can't make any verb stick, because nothing answers `do_action`.

## 3. The agent-surface framing

LLM-agent GUI control is converging on the *same* substrate. Playwright-MCP and similar servers (e.g. xa11y) drive a UI from the **accessibility snapshot** — a compact role/name/ref tree — rather than from screenshots, because the snapshot is roughly 10–100× cheaper in tokens than a screenshot-plus-OCR loop and is directly addressable (act on `ref=e7`, not on pixel (412, 380)). The loop is: snapshot → pick a ref → emit an action against that ref → re-snapshot. One tree thus serves three consumers at once — screen readers, test automation, and LLM agents — which is the central thesis the sibling [`../retained-mode-semantics-automation/`](../retained-mode-semantics-automation/) folder calls "one tree, N consumers," and which [`../llm-agent-interface/playwright-mcp.md`](../llm-agent-interface/playwright-mcp.md) makes concrete as the per-tool template (`snapshot` / `click{ref}` / `type{ref,text}`) for a future `buiy_*` agent surface. See also [`../browser-automation/`](../browser-automation/) (Playwright/CDP/WebDriver-BiDi actionability + locators) and [`../wai-aria-apg/`](../wai-aria-apg/) (the role/name vocabulary the snapshot is keyed on).

## 4. The Buiy seam — how Buiy goes bidirectional

The inbound plumbing **already exists one layer down**, inside `bevy_winit`. Its accessibility module forwards inbound OS/AT/agent `ActionRequest`s onto a Bevy message channel: `WinitActionRequestHandler` buffers them, `poll_receivers` drains them into a `MessageWriter<ActionRequestWrapper>` (`bevy_winit-0.18.1/src/accessibility.rs:173-181`), registered via `add_message::<ActionRequestWrapper>()` (`:312`). Buiy reads this channel **nowhere**. Verified present in 0.18.1 and **identical** in `bevy_winit-0.19.0-rc.3` (`accessibility.rs:174` / `:314`) — so the seam survives the in-flight 0.18→0.19 BSN bump.

So Buiy does **not** need a new `ActionHandler` (and must not register one — `bevy_winit` owns the single-occupant per-window adapter; a competing handler would fight it). The recommended seam is **one Buiy system** added in/after `BuiySet::A11yUpdate` that:

1. drains `MessageReader<ActionRequestWrapper>`;
2. inverts `node_id_for` — `node_id_for(e) = NodeId(e.to_bits().saturating_add(1))` (`a11y/translate.rs:17-21`), so `Entity::from_bits(n - 1)` recovers the target entity (`ROOT_NODE_ID = NodeId(0)` is the synthetic root, skip it);
3. dispatches the `accesskit::Action` into the **real** pipelines, reusing the existing seams rather than re-implementing them:
   - `Focus` → write `FocusedEntity` (`focus.rs:38`) — closes the gap that the *declared* `Focus` action (emitted for every `Focusable` node, `translate.rs:38-39`) is currently ignored;
   - `Click` → emit the activation a pointer would, i.e. the `OnPress` message the button path already fires (`buiy_widgets/button.rs:27` `OnPress(Entity)`, written at `:92`);
   - `SetValue` / `SetTextSelection` / `ReplaceSelectedText` → the public `TextEditState::apply` seam (`text/edit/input.rs:67`) driving the existing `EditCommand` vocabulary (`text/edit/command.rs:21`, 13 variants: Motion, Insert, Backspace, Delete, Enter, Cut, Copy, Paste, Undo, Redo, SelectAll, Escape, Submit).

No new dependency: `accesskit` + `accesskit_winit` are already direct deps (`crates/buiy_core/Cargo.toml:12-13`).

**The action vocabulary to advertise.** Inbound dispatch is only reachable for verbs Buiy both *declares* (`add_action`) and *handles*. Today it declares one (`Focus`) and handles none. The per-widget vocabulary worth wiring, drawn from the 22-variant `Action` set ([`tree-model.md`](tree-model.md)): buttons → `Click`; focusables → `Focus`/`Blur`; text inputs → `SetValue`/`SetTextSelection`/`ReplaceSelectedText`; sliders/spinners → `Increment`/`Decrement`/`SetValue`; disclosure/tree widgets → `Expand`/`Collapse`; scroll containers → `ScrollIntoView`/`ScrollToPoint`/`SetScrollOffset`; context-menu hosts → `ShowContextMenu`. Each widget in the catalog should pin both the role *and* its ingestible action set, the same way [`capabilities.md`](capabilities.md) pins its role.

## 5. The inverted-lossiness insight

The standard critique of AX-tree automation — "the AX tree is a lossy, reverse-engineered projection of opaque pixels, so driving by it is brittle" — is **inverted for Buiy**. A browser or native app derives its AX tree *after the fact* from a DOM / view hierarchy it didn't author for accessibility; the tree is a best-effort shadow. Buiy's tree is the **authored source of truth**: `build_tree` walks the decomposed `A11yRole`/`A11yLabel`/`A11yDescription` content components plus the `Focusable` marker (`a11y/mod.rs:90-98` — `Focusable` is the 4th query driver and the one that produces the lone declared `Focus` action) every frame and emits nodes directly. There is no pixel-to-semantics inference gap to be brittle about. That makes Buiy *materially better positioned* to be agent-drivable than the systems the automation tools in §2 were built to wrestle with — the snapshot is not a guess, it is the model.

## 6. Honest limits

- **Closed verb set.** `Action` is a closed 22-variant enum; `CustomAction` is the only escape hatch and it carries only an index (`ActionData::CustomAction(i32)`), not a name+args calling convention. App-level transitions ("open settings," "run the deploy") don't decompose into Click/SetValue and won't be expressible as AX actions — those need a separate command surface (the [`../engine-devtools-protocols/`](../engine-devtools-protocols/) and [`../bevy-remote-protocol/`](../bevy-remote-protocol/) folders cover that complementary RPC lane).
- **Per-frame rebuild → target instability.** `build_tree` calls `nodes.clear()` each frame (`a11y/mod.rs:100`), so an inbound `ActionRequest` targets a `NodeId` captured in a *prior* frame. `do_action` must tolerate a target that moved or despawned across the read→act gap — the xa11y "element replaced between query and action" failure mode. `NodeId` *stability* holds (it is a pure function of `Entity::to_bits`), but *liveness* does not; dispatch must check the entity still exists and re-validate state, never assume.
- **GPU-drawn content is invisible.** Anything Buiy draws straight to the GPU without emitting nodes is invisible to **both** screen readers and agents — same gap, same fix (emit nodes). The inverted-lossiness advantage only holds for content that actually authored a node.
- **Multi-window NodeId scoping.** `ROOT_NODE_ID` is a single `NodeId(0)`; `adapter.rs` pushes one shared `TreeUpdate` to *every* window (`adapter.rs:66-71`), and `node_id_for` carries **no** window discriminator (`translate.rs:11` flags multi-window as a v0.x concern). Any ref/snapshot scheme an agent surface exposes must be window-aware or explicitly single-window-scoped, or refs will collide across windows.
- **accesskit version delta — re-validate.** In-tree accesskit is **0.21**; the BSN bump targets **0.24**. The `Action` variant list is **identical across 0.21 and 0.24** — exactly **22 variants**, verified against the published crate source in the cargo registry for both `accesskit-0.21.1/src/lib.rs:281` and `accesskit-0.24.1/src/lib.rs:289` (same names, same order) — so there is *no* Action delta to migrate here. That is a point-in-time check: re-verify against the pinned version when the bump lands, since pre-1.0 minors carry breaking changes elsewhere (see [`README.md`](README.md) cadence note).
