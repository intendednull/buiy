**Status:** active
**Subject:** Makepad — the consult-this-when-designing decision file: validates / avoid / borrow

# Lessons

This is the file Buiy spec authors should read first when a design question touches: a DSL above a Rust UI runtime, mobile-first targeting, GPU rendering, hot-reload of UI source, or the AI-replaces-accessibility framing that Makepad's maintainers have publicly advanced. Other files in this folder are evidence; this file is the synthesis.

## Validates

Choices Makepad's experience confirms Buiy should keep making — or that Buiy can credibly bet on because Makepad has proven the shape ships:

1. **DSL above runtime is viable for production Rust UI (Makepad + Slint = two independent data points).** Makepad's `.live` syntax above `makepad-platform`, paired with Slint's `.slint` syntax above its Rust runtime, are now **two 1.0+ production proofs** that a Rust UI toolkit can ship with a declarative DSL above the runtime. Buiy's BSN authoring layer ([architecture.md § 2.4](../../specs/2026-05-07-buiy-foundation/architecture.md)) inherits the validation. The pattern works; the bugs are scoped to LSP / refactoring / two-language-friction (see [`live-language.md`](live-language.md), [`critiques.md`](critiques.md) §4). See [`../slint/lessons.md`](../slint/lessons.md) Validates #3 for the parallel.

2. **Mobile-first Rust UI targeting is real, not aspirational.** Robrix runs daily in production on macOS / Linux / Windows / Android / iOS / iPadOS — the same Rust + Makepad codebase compiled to all six. This is the cleanest field data point that **Buiy's mobile-platform-staging plan ([accessibility.md § "Platform support — staged"](../../specs/2026-05-07-buiy-foundation/accessibility.md)) is credible**, not a stretch goal. Cargo-makepad's integrated cross-target toolchain is a polish target for Buiy's mobile tooling. See [`mobile-targets.md`](mobile-targets.md).

3. **GPU rendering for production app UI is workable.** Robrix and Makepad Studio ship at acceptable performance with custom GPU pipelines. Validates Buiy's own render pipeline commitment ([architecture.md § 2.3](../../specs/2026-05-07-buiy-foundation/architecture.md)) — *some* GPU-rendered UI library shape ships at 1.0, even if Buiy's specific choices (wgpu via Bevy, no in-house Metal / DX11 / OpenGL / WebGL backends) differ from Makepad's. See [`gpu-rendering.md`](gpu-rendering.md).

4. **Hot-reload of UI source is a 6+-year-proven product feature.** Rik Arends's live-coding-IDE thesis from Cloud9 (2010s) through Makepad's `hotload_ui` example demonstrates that hot-reload of UI source — including, in Makepad's case, **shader code** — is a real, shipped feature, not a research curiosity. Buiy's BSN asset hot-reload ([`buiy-bsn-integration-design`](../../specs/2026-05-07-buiy-foundation/README.md)) inherits the validation. See [`live-language.md`](live-language.md), [`history.md`](history.md).

5. **MIT/Apache dual-permissive licensing aligns the Rust UI ecosystem.** Makepad ships under `MIT OR Apache-2.0` (matching Bevy, AccessKit, most of the Rust ecosystem). Slint's GPL+commercial gate is the contrast; Makepad's permissive choice is the broader pattern. Buiy's identical licensing ([foundation README](../../specs/2026-05-07-buiy-foundation/README.md)) is the well-trodden choice, validated by Makepad's adoption (small as the absolute numbers are, the lack of license friction is one less procurement question). See [`distribution-and-governance.md`](distribution-and-governance.md).

6. **A canonical-app-built-in-the-framework is load-bearing for credibility.** Makepad Studio (the IDE) is itself a Makepad app — the framework's existence is justified by the IDE that uses it. Buiy similarly benefits from a canonical Buiy-built application that proves the framework's claims. The Buiy-foundation spec doesn't yet identify this; it should be a planning item.

7. **Mobile-touch event primitives at per-finger granularity are the right model.** Makepad's `FingerDown` / `FingerMove` / `FingerUp` / per-finger-id events are a clean baseline for touch-driven UIs — leaving gesture recognition as application-level concern. Buiy's `buiy-input-events-design` ([foundation README sub-spec roadmap](../../specs/2026-05-07-buiy-foundation/README.md)) should adopt the same shape. See [`mobile-targets.md`](mobile-targets.md).

8. **Animator-as-state-machine declarative animation pattern is good UX.** Makepad's `animator: { state = { from, apply } }` syntax (and Slint's `states + transitions`) demonstrate that named-state-with-property-targets is a clean authoring surface for animation. Buiy's `buiy-animation-design` ([foundation README](../../specs/2026-05-07-buiy-foundation/README.md)) should consider this alongside keyframe / spring primitives. See [`live-language.md`](live-language.md).

## Avoid

Makepad pitfalls Buiy has explicit mitigations for, or chooses to design around. **Avoid #1 is the load-bearing one** — the AI-replaces-a11y framing is the cleanest single-statement contrast Buiy can draw against the prior-art ecosystem.

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **AI-will-do-accessibility-later as a framework position.** Issue [#196](https://github.com/makepad/makepad/issues/196) records the community report of Rik Arends's presentation framing: "for Accessibility most likely AI would soon do the heavy lifting." The issue has been open since 2023-08-08 with zero team responses. No AccessKit, no AT-SPI / UIA / NSAccessibility / TalkBack producer-side wiring. | [`critiques.md`](critiques.md) §6, [`open-problems.md`](open-problems.md), issue #196 verbatim | **Buiy commits to AccessKit-first as foundational** ([architecture.md § 2.6](../../specs/2026-05-07-buiy-foundation/architecture.md)). Accessibility is producer-side infrastructure shipped at the framework level — not delegated to AI, not delegated to authors, not deferred. Buiy must say this publicly; it's the cleanest contrast against the prior-art ecosystem and the strongest single positioning Buiy can adopt. |
| **DSL as the *primary* authoring layer.** Makepad's `.live` blocks (whether embedded in `live_design!` or external) are the source-of-truth for layout, styling, animation, and shader code. Rust glue defines behaviour. Programmatic UI construction is *possible* but fights the grain (no `BSN.spawn`-equivalent supported path). | [`architecture.md`](architecture.md), [`live-language.md`](live-language.md), [`open-problems.md`](open-problems.md) | Buiy makes **ECS + BSN equally first-class** ([architecture.md § 2.4](../../specs/2026-05-07-buiy-foundation/architecture.md)). The ECS world is the source of truth; BSN is one authoring surface among others (direct Rust spawning, runtime-constructed entities, hot-reloaded `.bsn` files). No single authoring layer dominates. Game inventory grids, IDE tree views, dynamic forms — all of which fight Makepad's grain — are first-class in Buiy. |
| **Yet-another-DSL with custom syntax.** Live is its own syntax (not JSON, not Rust, not Lisp). Adds a learning curve on top of Rust. LSP support is concentrated in Makepad Studio; no editor-agnostic equivalent of `slint-lsp`. | [`live-language.md`](live-language.md), [`critiques.md`](critiques.md) §1, §5 | Buiy keeps **everything in Rust syntax** via BSN macro or `.bsn` Rust-compatible files. `rust-analyzer` covers the macro form. No new language to learn; no editor lock-in. Tradeoff acknowledged: no shader-as-first-class authoring layer the way Live offers. |
| **Skipping wgpu — four GPU backends to maintain.** Makepad ships direct Metal / DX11 / OpenGL / WebGL backends. Every GPU feature has to be implemented up to four times. WebGPU is not yet a backend. No automatic benefit from wgpu's upstream improvements. | [`gpu-rendering.md`](gpu-rendering.md), [`architecture.md`](architecture.md) | Buiy stays on **wgpu via Bevy's render graph** ([architecture.md § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md)). Inherits wgpu's WebGPU + Vulkan + DX12 + Metal-Argument-Buffers backends "for free." Trades the per-platform low-level control Makepad has for the cross-platform maintenance leverage Buiy needs. |
| **Skipping winit — forecloses AccessKit-via-accesskit_winit.** Makepad does its own per-platform event loops; this means the canonical `accesskit_winit` integration path is unreachable. Adding accessibility later would require either replatforming on winit (massive refactor) or hand-rolling per-platform AT bridges (large engineering cost). | [`architecture.md`](architecture.md), [`open-problems.md`](open-problems.md) | Buiy stays on **winit via Bevy** ([architecture.md § 2.6](../../specs/2026-05-07-buiy-foundation/architecture.md)). The `accesskit_winit` adapter integrates per-window per Buiy's spec; AT bridges work cross-platform without bespoke producer code. |
| **Custom text-shaping below cosmic-text's capabilities.** Makepad's text stack lacks BiDi, complex-script shaping (Arabic / Indic / Thai), comprehensive font fallback by Unicode block, and full IME composition for CJK / Korean. Robrix Matrix messages with mixed RTL/LTR surface these gaps. | [`gpu-rendering.md`](gpu-rendering.md), [`open-problems.md`](open-problems.md) | Buiy uses **cosmic-text directly** ([architecture.md § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md)) for both rendering and editing. BiDi, complex shaping, emoji, font fallback are all upstream-correct out of the box. |
| **No theming token system / OS-preference wiring.** Makepad's `THEME_*` constants are build-time selection. No `prefers-color-scheme` / `forced-colors` / `prefers-contrast` / `prefers-reduced-motion` automatic binding. | [`open-problems.md`](open-problems.md), [`live-language.md`](live-language.md) | Buiy commits to **semantic tokens with OS-preference binding** ([architecture.md § 2.5](../../specs/2026-05-07-buiy-foundation/architecture.md)). Runtime token mutation; OS preferences wired automatically. |
| **LSP locked to the project's own IDE.** Makepad Studio is the supported editor; VS Code / Helix / Neovim users lack first-class Live language support. | [`live-language.md`](live-language.md), [`critiques.md`](critiques.md) §1 | Buiy's BSN tooling uses **`rust-analyzer` for the macro form** (already editor-agnostic) and editor-agnostic LSP for `.bsn` asset files. Borrow Slint's `slint-lsp` shape, not Makepad's Studio-lock-in. |
| **Small-team founder-driven project at 1.0 — governance risk.** 3 core architects, no foundation, no charter, no formal RFC process. Bus factor is concentrated. | [`distribution-and-governance.md`](distribution-and-governance.md), [`history.md`](history.md), [`critiques.md`](critiques.md) §8 | Buiy plans **Bevy-Foundation-adjacent governance** ([foundation README](../../specs/2026-05-07-buiy-foundation/README.md), implicit). Multiple maintainer attention surface, no single corporate sponsor de-facto-runs-it. Tradeoff: no commercial-license revenue model funds full-time engineers. Structural risk taken deliberately. |
| **Documentation maturity as adoption gate.** 5.92% / 0% docs.rs coverage on flagship crates; no static project site (`makepad.dev` is JS SPA shell). Procurement teams ask "is there a reference manual?" and Makepad fails. | [`open-problems.md`](open-problems.md), [`critiques.md`](critiques.md) §9 | Buiy commits to **rustdoc-as-spec + per-subsystem design documents + verification harness enforces examples** ([verification.md](../../specs/2026-05-07-buiy-foundation/verification.md)). Documentation is a CI-gate-blocking deliverable, not an afterthought. |
| **Mobile-first feature scope deferring desktop concerns.** Makepad's drag-and-drop, system tray, real OS-modal dialogs, accelerator keys, spell-check integration are limited or absent. | [`critiques.md`](critiques.md) §3 | Buiy's **web-platform-parity target** ([foundation README goal 1](../../specs/2026-05-07-buiy-foundation/README.md)) keeps desktop concerns in F / C tier. The full feature inventory in [interaction.md](../../specs/2026-05-07-buiy-foundation/interaction.md) and [cross-cutting.md](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) must cover them. |
| **Single-corporate-sponsor downstream community.** Project Robius / Futurewei runs the most-visible Makepad app (Robrix). If Futurewei policy changes, the visible-adoption story degrades immediately. | [`distribution-and-governance.md`](distribution-and-governance.md), [`history.md`](history.md) | Buiy's community-cultivation strategy should plan for **multiple Buiy-app contributors from multiple companies**. Not a "one Futurewei-equivalent runs the demo apps" arrangement. |

## Borrow

Specific Makepad primitives, patterns, and tooling shapes Buiy should adopt or adapt — including some that are *more impressive* than Buiy's current substrate offers and worth deep study:

1. **Live-reload pattern for `.bsn` (including the shader-hot-reload extension).** Makepad's `.live` source change → re-parse → re-bind `#[live]` fields → `LiveHook::after_apply` → redraw pipeline is the gold standard for UI-source hot-reload in Rust. The capacity to hot-reload **shader code** (the inline `fn pixel(self) -> vec4 { ... }` in Live syntax) is genuinely novel and worth carrying into Buiy's BSN asset hot-reload + Buiy's render-pipeline shader hot-reload strategy. See [`live-language.md`](live-language.md), [`gpu-rendering.md`](gpu-rendering.md). Cross-link to [`../slint/lessons.md`](../slint/lessons.md) Borrow #4 (Slint Live Preview pattern) for the same shape on the DSL side.

2. **The integrated cross-target build tool (`cargo-makepad`).** A single cargo subcommand drives toolchain installation (NDK / iOS signing / tvOS / OpenHarmony), per-target builds, and on-device run. Buiy's mobile-platform-staging would benefit from a `cargo-buiy` wrapper around `cargo-mobile2` that does the same integrated install + build + run. See [`mobile-targets.md`](mobile-targets.md).

3. **Per-finger mobile-touch event primitives.** Makepad's `FingerDown` / `FingerMove` / `FingerUp` / `FingerHoverIn` / `FingerHoverOut` / `FingerScroll` / `FingerLongPress` event family is a clean baseline for `buiy-input-events-design` mobile coverage. Gesture-recognizer-as-application-layer (not framework-layer) is the right boundary. See [`mobile-targets.md`](mobile-targets.md).

4. **Animator-as-declarative-state-machine.** Makepad's `animator: { state = { from: {all: Forward {duration: 0.1}}, apply: { ... } } }` block (and Slint's `states + transitions`) — named states with property targets, declarative transitions — is one of the right authoring surfaces for animation. Buiy's `buiy-animation-design` should expose this alongside keyframe / spring primitives. See [`live-language.md`](live-language.md).

5. **Inline shader-authoring-as-first-class-UI.** Live's inline `pixel` / `vertex` functions inside Live blocks, with backend-specific shader codegen (MSL / HLSL / GLSL ES / GLSL), are uniquely powerful. Buiy's render pipeline sub-spec ([`buiy-render-pipeline-design`](../../specs/2026-05-07-buiy-foundation/README.md)) should consider whether BSN-authored UI can carry shader snippets the same way (likely as asset references rather than inline syntax, but the *principle* — UI authors can write shaders — is borrowable).

6. **Trait-object widgets via `#[derive(Live)]` + `#[derive(Widget)]` derive macros.** Makepad's derives reduce the boilerplate of "implement Live + Widget + LiveHook on a struct" to a few derives. Buiy's BSN-friendly component constraint ([architecture.md § 2.4](../../specs/2026-05-07-buiy-foundation/architecture.md)) inherits the same derive-driven approach (`Reflect + FromReflect + Default + Clone + Component`). The shape — concentrate boilerplate in derives, not in trait impls — is shared.

7. **Per-window event loop separation.** Makepad's per-window state isolation (each `<Window>` owns its surface, GPU swap chain, event queue) is a clean model. Buiy's `buiy-window-and-surface-design` ([foundation README sub-spec roadmap](../../specs/2026-05-07-buiy-foundation/README.md)) can borrow the per-window state shape — same as Slint's per-window AccessKit-adapter pattern (see [`../slint/lessons.md`](../slint/lessons.md) Borrow #9).

8. **`<StackNavigation>` as a mobile-pattern primitive.** Push/pop view stacks with platform-idiomatic transitions are how mobile users expect navigation to work. Makepad ships `<StackNavigation>` in the catalog. Buiy's [`media-and-widgets.md`](../../specs/2026-05-07-buiy-foundation/media-and-widgets.md) widget catalog should include this pattern (it does not currently appear in the catalog list — open question whether to add).

9. **Dependency-resolution syntax for assets (`dep("crate://self/icons/foo.svg")`).** Makepad's `dep()` syntax for resolving asset paths relative to the calling crate is a clean, language-agnostic asset-reference shape. Buiy's `buiy-asset-pipeline-design` sub-spec could borrow the syntax (BSN-friendly `dep()` calls, or `.bsn`-syntax-equivalent) for theme assets, font assets, icon atlases.

10. **The "canonical-app-built-in-the-framework" cultural commitment.** Makepad Studio dogfoods Makepad. This is more than a marketing point; it's a forcing function for the framework to be usable for non-trivial applications. Buiy should identify and commit to a canonical Buiy-built application early — possibly a Buiy devtools / inspector application that depends on Buiy itself, or a sample Bevy game that uses Buiy as its full UI stack. The foundation-spec does not currently identify this; flag as planning input.

## How to use this file

When designing a Buiy feature that touches:

- **DSL authoring** — read this file's Validates #1, Avoid #2, Avoid #3, plus [`../slint/lessons.md`](../slint/lessons.md). Both Makepad and Slint are inputs. Buiy is rejecting their DSL-first model in favor of BSN-as-Rust-syntax, but the *separation of authoring layer above runtime* is the right architectural pattern.
- **Mobile targeting** — read Validates #2, Borrow #2, Borrow #3, Borrow #8. Robrix is the existence proof. `cargo-buiy` should aspire to `cargo-makepad`'s tooling integration.
- **Hot-reload of UI source** — read Validates #4, Borrow #1. The shader-hot-reload extension is the stretch goal worth considering.
- **Accessibility** — read Avoid #1. This is the single load-bearing decision. The AI-replaces-a11y framing is the position Buiy must reject publicly.
- **GPU pipeline** — read Borrow #5 and Avoid #4/#5. Buiy keeps wgpu and winit; borrowing shader-as-authored-source is the polish target.
- **Animation** — read Borrow #4. State-machine declarative animation is a worthwhile authoring surface alongside keyframes/springs.

Promote any decision into a Buiy spec under `docs/specs/` — this file captures what we learn from Makepad, not Buiy's own commitments. When Makepad ships a 1.1 or beyond, this file's claims may drift; re-verify against the live `makepad-widgets` docs.rs + crates.io API before lifting any concrete claim.
