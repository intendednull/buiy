**Subject:** bevy_egui — Validates / Avoid / Borrow decisions for the Buiy foundation

# Lessons for Buiy

This is the consult-this-when-designing decision file. The other files in this corpus are evidence; this file is the synthesis. Three sections — **Validates** (Buiy choices that bevy_egui's experience confirms), **Avoid** (pitfalls to mitigate), **Borrow** (primitives worth studying).

Before everything else: the load-bearing finding for the whole corpus.

## Top-of-file finding: immediate-mode and retained-mode are different problems, not competitors

bevy_egui validates **immediate-mode as the right paradigm for dev tools** — debug overlays, inspectors, level editors, prototype settings panels. 2M+ lifetime downloads, dominant in `bevy-inspector-egui`, dominant in early Bevy editor experiments, dominant in game-jam UI. The fit is exact: data tree changes every frame, audience is the developer, accessibility is not required, widget count is moderate. This is not a slot Buiy is competing for. See [`use-cases.md`](use-cases.md) § "Where bevy_egui wins."

bevy_egui *also* validates **retained-mode as the right paradigm for production game UI** — by absence. **No flagship commercial Bevy game ships its production player-facing UI on bevy_egui.** Tiny Glade wrote its own UI renderer. Foresight Spar wrote its own. The Bevy editor experiments are shifting toward `bevy_feathers` (in-tree retained-mode) and away from bevy_egui. The cluster of weaknesses — flat `Visuals` (no token system), animation primitives that stop at `animate_bool`, layout simpler than Flexbox/Grid, opt-in AccessKit with structural per-frame-rebuild limits, hit-target sizes tuned for mouse precision, "looks like egui" homogeneity — is the production-UI-grade-polish gap. See [`critiques.md`](critiques.md), [`open-problems.md`](open-problems.md) § "The production game UI gap," [`ecosystem.md`](ecosystem.md) § "Commercial Bevy releases."

**Buiy's retained-mode bet does not compete with bevy_egui; the two coexist.** Most real Bevy projects will use both — bevy_egui for dev overlays / inspectors / editor panels, Buiy (or `bevy_ui` today) for shipped player-facing UI. See [`use-cases.md`](use-cases.md) § "The dev mode + ship mode pattern" and [`../../specs/2026-05-07-buiy-foundation/cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.18 (the Buiy / bevy_ui no-mixing-in-one-window rule explicitly does *not* apply to bevy_egui — bevy_egui's no-default-AccessKit + flat-tessellated-output composes cleanly with anything else on screen).

The follow-on for every Buiy spec: **stop asking "should Buiy do X better than bevy_egui?" and start asking "does X belong on the production-UI axis Buiy targets, or on the dev-tool axis bevy_egui already owns?"** Most dev tooling answers "ship it on bevy_egui" — even Buiy's own inspector / focus visualizer / theme editor / contrast checker are candidates for bevy_egui hosting (with dogfooding on Buiy as a separable choice). See [`use-cases.md`](use-cases.md) § "What this means for the prior-art corpus."

## Validates

These Buiy design choices are confirmed by bevy_egui's experience:

- **Retained-mode for production UI (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.3).** bevy_egui's adoption in production game UI is essentially zero — Tiny Glade, Foresight Spar, and other shipped Bevy titles wrote custom UI rather than reach for bevy_egui. The Bevy editor experiments are shifting away from it. The cluster of weaknesses listed in [`critiques.md`](critiques.md) (styling rigidity, animation gaps, layout simplicity, a11y structural limits) is the production-UI gap that retained-mode + entity-backed components is designed to close. See [`open-problems.md`](open-problems.md) § "The production game UI gap." This is the single largest validation of Buiy's retained-mode bet in the whole corpus.

- **AccessKit as the a11y substrate (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6).** bevy_egui adopted AccessKit (opt-in, 0.38 onward). Both retained-mode (`bevy_ui` since 0.10, March 2023) and immediate-mode (egui upstream, scaffolded 0.20, matured through 0.33) converged on AccessKit. This is the common a11y ground in the Rust UI ecosystem — AccessKit is the right cross-platform AT bridge regardless of paradigm. Buiy's commitment matches the entire field. See [`api-surface.md`](api-surface.md) § "Accessibility."

- **`bevy_picking` as the pointer-input substrate (foundation [`interaction.md`](../../specs/2026-05-07-buiy-foundation/interaction.md) § 3.7).** bevy_egui registers a `bevy_picking` backend (since 0.32, 2025-01-06) — same substrate Buiy registers against in parallel. The blocking/forwarding model (bevy_egui suppresses bevy_picking events when a pointer is over an egui widget; the `EguiPickingOrder` resource sets priority) is the production-proven pattern for multi-UI-stack coexistence. See [`architecture.md`](architecture.md) § "Picking integration" and [`integration.md`](integration.md) § "Coexistence with bevy_ui."

- **Multi-window from day one (foundation [`cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.19).** bevy_egui supported multi-window in 0.4 (2021-04-10) — early in Bevy's life, and refined repeatedly since (per-camera contexts in 0.35, two-windows example shipped continuously). Buiy's commitment to multi-window from foundation is validated as table-stakes for any serious Bevy UI stack.

- **Per-window AccessKit adapter ownership (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6).** Bevy's `bevy_a11y` integration (which bevy_egui's opt-in AccessKit support uses) keys the adapter to winit `WindowId`, not Bevy `Entity`. bevy_egui follows the same model. Buiy's commitment to per-window AccessKit adapters matches the entire ecosystem.

- **`PluginGroup`-style setup (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.8).** `EguiPlugin` is a single plugin with configuration fields (`enable_multipass_for_primary_context`, `ui_render_order`, `bindless_mode_array_size`) plus a render-graph node group. Buiy's `BuiyPlugin` follows the same composition shape. See [`architecture.md`](architecture.md) § "The plugin struct."

- **"Use the right tool" mentality (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) goal 6 + non-goals).** Buiy explicitly is *not* positioning as a bevy_egui replacement, and the foundation spec is honest about what's in scope (production game + app UI) and what isn't (dev-tool UI is not Buiy-exclusive). This honest scoping mirrors egui's own non-goals list ("not aimed at becoming the most powerful GUI library," "does not target native looking interface") — see [`immediate-mode-paradigm.md`](immediate-mode-paradigm.md) § "egui's stated philosophy."

- **Owning substrate deps directly, not through a wrapper crate.** bevy_egui's two-layer pin (Bevy + egui) produces a 2–8 week pin-lag every release cycle (see [`distribution.md`](distribution.md) § "egui version pins" — bevy_egui 0.39.1 is currently one minor behind egui upstream). Buiy depends on Taffy / cosmic-text / AccessKit / bevy_picking / wgpu directly, avoiding the wrapper-crate cadence chase. See [`open-problems.md`](open-problems.md) § "egui upstream cadence vs Bevy cadence."

## Avoid

Pitfalls drawn from bevy_egui's experience, with Buiy's mitigation.

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **Using bevy_egui (or any immediate-mode UI) for production game UI.** Animation, theming, layout flexibility, full APG conformance, and visual polish are paradigm-tied gaps in immediate-mode that years of egui upstream work haven't closed. No flagship commercial Bevy game ships on bevy_egui. Tiny Glade + Foresight Spar both built custom UI rather than use it. | [`use-cases.md`](use-cases.md) § "Where bevy_egui does not belong"; [`ecosystem.md`](ecosystem.md) § "Indie / hobbyist games"; [`open-problems.md`](open-problems.md) § "The production game UI gap." | Buiy is the production-UI choice on Bevy; bevy_egui stays in dev tooling. Foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) goal 6 ("Game and app, both") and foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.1 (parallel stack) are the design responses to this gap. |
| **Confusing immediate-mode and retained-mode as points on a continuum.** They are different architectures with different costs. "Make Buiy more immediate-mode-friendly" or "support immediate-mode authoring inside Buiy" loses the structural benefits retained-mode buys (stable a11y tree IDs, layout caching, animation on persistent nodes, change-detection performance, BSN reflection). | [`immediate-mode-paradigm.md`](immediate-mode-paradigm.md) § "What gets erased" + "When retained-mode wins." | Buiy is explicitly retained-mode. The foundation spec frames the bet clearly. Authoring is ECS + BSN over persistent entities. The immediate-mode option is bevy_egui itself — coexistence, not absorption. |
| **Pinning to a specific bevy_egui release because of the egui-version-lag chain.** bevy_egui 0.39.1 pins egui 0.33 while upstream egui is at 0.34.2 — one minor behind. The two-layer pin (Bevy + egui) makes every Bevy minor *and* every egui minor a breaking-change event, with no overlap window. | [`distribution.md`](distribution.md) § "egui version pins"; [`critiques.md`](critiques.md) § "Version pinning frustration"; [`open-problems.md`](open-problems.md) § "Misaligned upstream cadences." | Buiy owns its substrate deps directly (Taffy, cosmic-text, AccessKit, bevy_picking, wgpu through Bevy) — no wrapper-crate cadence chase. Each Bevy minor is a Buiy migration event but it's a *one*-cadence chase, not two. |
| **Counting on AccessKit being on by default.** bevy_egui's `accesskit` feature is **opt-in, not default** since the 0.38.0 re-enable. Apps using `bevy_egui` with `default-features` get *no* a11y unless they explicitly enable it. This is a deliberate stance (bevy_egui's a11y story is still incomplete relative to retained-mode UI) but means accessibility is silently off in most consumer apps. | [`critiques.md`](critiques.md) § "Accessibility"; [`api-surface.md`](api-surface.md) § "Accessibility"; [`distribution.md`](distribution.md) § "Cargo features." | Buiy's foundation [`accessibility.md`](../../specs/2026-05-07-buiy-foundation/accessibility.md) commits to AccessKit-first, default-on. There is no "opt into a11y" gate — the AccessKit adapter ships in the default plugin set. WCAG 2.2 AA is the floor (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) goal 2). |
| **Single-pass rendering.** bevy_egui deprecated single-pass mode in 0.35.0 (2025-06-30); multi-pass is now the default and on track to be the only mode. Auto-sizing tooltips, popovers that need to know their content size before placement, and many production-UI patterns need multi-pass. Designing a render pipeline that can only run once per frame is a re-architecture event the moment you need to retrofit it. | [`architecture.md`](architecture.md) § "Multi-pass vs single-pass"; [`open-problems.md`](open-problems.md) § "Multi-pass mode policy." | Buiy's render pipeline plans for multi-pass from day one. Top-layer compositing, `backdrop-filter`, popovers, anchor-positioned overlays, and the focus-restoration story all benefit from multi-pass — foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.3 + the `buiy-render-pipeline-design` sub-spec. |
| **Per-window egui contexts** (pre-0.35.0 model). bevy_egui's original model attached one context per *window*; it was reworked to per-*camera* in 0.35.0 to support split-screen, multiple cameras-into-one-window, and render-to-texture diegetic UI. The migration was a structural shift. | [`architecture.md`](architecture.md) § "Per-window / per-camera contexts"; [`history.md`](history.md) 0.35.0 entry. | Buiy uses **per-window AccessKit adapters** (because winit `WindowId` is the AT-system key) but **per-camera render targets** (because cameras own the view → render-target relationship). The two keys are kept separate, by design. See foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6 and the `buiy-window-and-surface-design` sub-spec. |
| **Treating Zed as an egui consumer.** Zed (zed.dev) is sometimes mis-cited as a flagship "egui at scale" production app. Zed is on **GPUI** (Nathan Sobo's bespoke retained-mode Rust framework), not egui. The legitimate egui-at-scale counterexample is **Rerun.io** — and Rerun's pattern doesn't generalize to game UI (see next row). | [`use-cases.md`](use-cases.md) § "Productivity apps with serious widget counts"; [`ecosystem.md`](ecosystem.md) § "egui's own ecosystem"; [`critiques.md`](critiques.md). | GPUI gets a separate prior-art folder (deferred). Don't conflate. The Buiy spec's productivity-app fixtures at 1000+ nodes (foundation [`verification.md`](../../specs/2026-05-07-buiy-foundation/verification.md)) are calibrated for retained-mode + change-detection — explicitly the pattern Zed/GPUI use, not egui's. |
| **Assuming "egui at scale" applies to game UI.** Rerun ships egui at production scale (multi-pane, performance-sensitive, streaming-data viewer). It works because Rerun's data is *always changing* (streaming sensor input) — there's no "unchanged frame" to optimize for, so the immediate-mode per-frame rebuild cost is amortized against work you'd be doing anyway. Game UIs don't have this property — most HUD frames change very little, and retained-mode's "draw zero pixels for an unchanged frame" is a structural win. | [`use-cases.md`](use-cases.md) § "Productivity apps"; [`critiques.md`](critiques.md) § "Immediate-mode performance cost"; [`open-problems.md`](open-problems.md) § "Performance at 1000+-widget scale." | Buiy commits to change-detection + dirty-propagation through the layout pipeline (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.3). The verification harness fixtures (foundation [`verification.md`](../../specs/2026-05-07-buiy-foundation/verification.md)) include both static-and-changing scenarios; unchanged-frame cost is a named CI gate. |
| **Solo maintainer in the wrapper layer.** bevy_egui has a bus factor of 1 — vladbat00 has been the sole maintainer for 5+ years. The upstream egui is robust (Rerun-funded, multi-engineer); the wrapper is a hobby project in Mariupol, Ukraine. If vladbat00 steps back, bevy_egui orphans. This is an asymmetric risk consumers don't always see. | [`governance.md`](governance.md) § "Bus factor analysis"; [`governance.md`](governance.md) § "The two-layer maintenance model." | Buiy's modular subsystem boundaries (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.8 — `buiy_core` / `buiy_widgets` / `buiy_a11y` / etc.) reduce single-author choke points. Buiy itself is currently single-author (intendednull) — the same risk applies and is named in foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 ("single-maintainer succession"). The mitigation is documentation-first discipline (`docs/specs/`, `docs/plans/`, `docs/prior-art/`) so the project state isn't in any one head. |
| **MIT-only when Bevy + upstream are dual.** bevy_egui is MIT only; upstream egui is MIT OR Apache-2.0; Bevy is MIT OR Apache-2.0. Apache-2.0-only downstream consumers can use egui directly but not bevy_egui. For corporate adoption pipelines that require the Apache-2.0 patent grant, this is a real blocker. | [`governance.md`](governance.md) § "License divergence"; [`distribution.md`](distribution.md). | Buiy will be **MIT OR Apache-2.0** to match Bevy + AccessKit + Taffy + cosmic-text. The foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 1 and `architecture.md` § 2.8 commit to the dual license. |
| **Flat styling without a token layer.** egui's `Visuals` is a flat struct of end-state colors / sizes; no token model, no semantic colors, no cascade, no state-driven styles in the data model. Theming requires precomputed complete `Visuals` instances. OS preferences (`prefers-color-scheme`, `prefers-contrast`, `prefers-reduced-motion`) are not wired. The "looks like egui" homogeneity follows directly — re-theming is substantial work. | [`critiques.md`](critiques.md) § "Styling limitations"; [`open-problems.md`](open-problems.md) § "Theme expressiveness." | Buiy commits to multi-variant tokens with OS-preference binding, subtree overrides, hot-reload, and a contrast linter — foundation [`visuals.md`](../../specs/2026-05-07-buiy-foundation/visuals.md) and the `buiy-theme-tokens-design` sub-spec. |
| **Animation primitives that stop at `animate_bool` / `animate_value`.** egui has linear interpolation over a fixed duration and nothing else — no keyframes, no springs, no easing library, no transition system, no layout transitions, no reduced-motion gate. Production HUDs (damage popups, score flourishes, screen transitions) require all of these. | [`critiques.md`](critiques.md) § "Animation / transition primitives are weak"; [`api-surface.md`](api-surface.md). | Buiy commits to transitions, keyframes, layout transitions, springs, and a reduced-motion gate — foundation [`interaction.md`](../../specs/2026-05-07-buiy-foundation/interaction.md) § 3.8 and the `buiy-animation-design` sub-spec. |

## Borrow

Concrete primitives worth studying and adapting:

1. **bevy-inspector-egui-style dev tooling on Buiy (eventually).** `bevy-inspector-egui` is the canonical Bevy dev tool: reflection-driven world inspector, every entity / component / resource / asset live in a panel, every field directly editable. The *use case* is the takeaway — Buiy's own inspector / focus visualizer / theme editor / contrast checker (foundation [`cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.16) should serve the same workflow. The *implementation choice* is open: ship on bevy_egui (the path of least resistance, validated by 1.2M downloads) or dogfood on Buiy (heavier per widget, but tightens the Buiy feedback loop). See [`ecosystem.md`](ecosystem.md) § "Canonical consumer: bevy-inspector-egui" and [`use-cases.md`](use-cases.md) § "What this means for the prior-art corpus."

2. **AccessKit feature-flag opt-in pattern.** bevy_egui's `accesskit` Cargo feature is opt-in for downstream consumers who don't need a11y (the headless test consumer, the build-size-conscious WASM consumer). Buiy is AccessKit-default-on but can expose a similar gate for niche consumers — e.g., a `no_a11y` feature for embedded / WASM size-sensitive builds that drops the AccessKit adapter and `accesskit_*` platform crates. See foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.8 — the crate-split open question lists this as a configuration knob. Caveat: never expose the gate in a way that lets `default-features` silently drop a11y — bevy_egui's choice is a known footgun.

3. **Multi-pass-by-default rendering.** bevy_egui deprecated single-pass in 0.35.0 because production patterns (auto-sizing tooltips, popovers that measure their content before placing themselves, anchor-positioned overlays) need re-layout within a frame. Buiy's render pipeline adopts multi-pass from foundation — the `buiy-render-pipeline-design` sub-spec specifies the per-pass ordering (layout → style → paint → composite → top-layer composite), with explicit multi-pass support for re-layout. See [`architecture.md`](architecture.md) § "Multi-pass vs single-pass."

4. **Per-camera context pattern.** Since 0.35.0 each camera carries its own `EguiContext`, supporting split-screen, multiple cameras-into-one-window, and `RenderTarget::Image` diegetic UI. Buiy's render-to-texture surface API (foundation [`cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.17 and the `buiy-window-and-surface-design` sub-spec) borrows the per-camera key for render targets, while keeping AccessKit adapters per-*window* (because winit `WindowId` is the AT system key — see foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6). The two-key separation is borrowable.

5. **Mesh-picking for diegetic UI.** bevy_egui 0.35.0 added the pattern: spawn a camera with `RenderTarget::Image(handle)`, attach the image to a `MeshMaterial3d<StandardMaterial>` on a 3D mesh, and with the `picking` feature on, bevy_picking forwards mesh-surface pointer hits to the egui camera's virtual pointer position. Buiy's `buiy_3d` subsystem (foundation [`cross-cutting.md`](../../specs/2026-05-07-buiy-foundation/cross-cutting.md) § 3.17) targets the same use case and borrows the mesh-based hit-test pattern. See [`integration.md`](integration.md) § "Render-to-texture surfaces."

6. **Dynamic priority resource (`EguiPickingOrder`) instead of a const.** 0.39.0 replaced the `PICKING_ORDER` const with the `EguiPickingOrder` resource for runtime configurability. Buiy's `bevy_picking` backend ordering uses a similar dynamic resource (`BuiyPickingOrder`) so applications can re-order backends at runtime without recompiling. See [`architecture.md`](architecture.md) § "Picking integration."

7. **`PluginGroup`-style setup with configuration fields.** `EguiPlugin` exposes three fields: `enable_multipass_for_primary_context`, `ui_render_order` (when `bevy_ui` feature on), `bindless_mode_array_size` (when `render` feature on). Buiy's `BuiyPlugin` follows the same composition: a single user-facing plugin with feature-gated configuration fields, internally composing sub-plugins (`BuiyCorePlugin`, `BuiyA11yPlugin`, `BuiyRenderPlugin`, etc.). See [`architecture.md`](architecture.md) § "The plugin struct" and foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.8.

8. **The blocked-vs-forwarded picking event model.** When a pointer is over an egui widget, bevy_egui's `capture_pointer_input_system` *suppresses* `bevy_picking` events for that frame. Other UI stacks see the pointer "consumed." Buiy adopts the same blocking model for coexistence with bevy_ui (per-window, different stacks): the foreground UI stack consumes the hit, the background stack sees a "no-op" event. See [`integration.md`](integration.md) § "Coexistence with bevy_ui" and foundation [`interaction.md`](../../specs/2026-05-07-buiy-foundation/interaction.md) § 3.7.

9. **Emil Ernerfeldt's explicit non-goals pattern.** The upstream egui README ships a list of *non*-goals: "Not aimed at becoming the most powerful GUI library," "Does not target native looking interface." This honest scoping has helped egui avoid feature-creep accusations — users who need power or native looks know upfront to choose differently. Buiy's foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 1 carries the same shape (the explicit non-goals list: no networking / persistence / routing, no game-side accessibility content, no v1 reactive component model with signals, etc.). The pattern is borrowable for sub-specs too: every Buiy sub-spec should list non-goals up front. See [`immediate-mode-paradigm.md`](immediate-mode-paradigm.md) § "egui's stated philosophy."

10. **The 4-days-after-Bevy-launch start (2020-08-14).** bevy_egui 0.1.0 published 4 days after Bevy 0.1's public announcement on 2020-08-10. The crate has tracked Bevy's ~3-month cadence for 5+ years across 70 versions. The lesson: a third-party crate *can* keep pace with Bevy's release treadmill if the maintainer commits to the discipline, even as a hobby project. Buiy's parallel-stack commitment (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) goal 5 "Tracks Bevy") includes the same migration discipline — every Bevy minor is a Buiy migration event, with the docs-first workflow (`docs/specs/` + `docs/plans/`) as the institutional memory. See [`history.md`](history.md) § "bevy_egui genesis."

## How to use this file

When designing a Buiy feature:

1. **Re-read the Top-of-file finding.** The instinct "make Buiy compete with bevy_egui on X" is usually wrong — bevy_egui owns the dev-tool axis Buiy doesn't target, and the cluster of weaknesses bevy_egui has on the production-UI axis is precisely the slot Buiy is built for. The two coexist; pick the right tool per UI surface.
2. **Find the row in `Avoid`** that names a pitfall close to your design. Read the linked file for the original incident; bring the mitigation back into the Buiy spec.
3. **Find the entry in `Borrow`** that names a primitive close to what you're designing. Read the linked file to understand the bevy_egui / egui shape, then adapt for Buiy's retained-mode component model.
4. **Promote any decision into a Buiy spec** under `docs/specs/` — this file is for capturing what we learn from bevy_egui, not for encoding Buiy's own decisions.
