# Composition, state & events — the core authoring DX

The opposite primitive from Buiy: Compose is a *reactive function-call* model
(UI recomputed from state); Buiy is *retained ECS* (a spawned entity tree
mutated in place). The value here is not the recomposition machinery — Buiy
rejects it — but the **API conventions** layered on it. See
[architecture.md](architecture.md) for the runtime split,
[styling-theming.md](styling-theming.md) for `Modifier`/tokens,
[lessons.md](lessons.md) for verdicts. The a11y/semantics projection lives in
the sibling
[`../retained-mode-semantics-automation/compose-semantics.md`](../retained-mode-semantics-automation/compose-semantics.md).

## 1. Composables emit; they don't return a tree

A `@Composable` that emits UI returns `Unit`; calling it *is* the emission.

```kotlin
@Composable
fun Greeting(name: String) {
    Text(text = "Hello, $name")   // emits a Text node into the enclosing composition
}
```

No `View` object is assembled and returned. (Guideline: a `Unit`-returning
`@Composable` is `PascalCase` and the name MUST be a noun; value-returning
composables are ordinary `camelCase`.)

### Children & slots: `content: @Composable () -> Unit`

A "slot" is a `@Composable` lambda parameter — child content is *passed in* as
a trailing lambda rather than configured through a pile of `text:`/`icon:`
parameters:

```kotlin
// single content slot, scoped so children get RowScope helpers
Button(onClick = { submit() }) {
    Icon(Icons.Filled.Send, contentDescription = null)
    Spacer(Modifier.width(8.dp))
    Text("Send")
}

// multiple NAMED slots — Scaffold lays out four independent content lambdas
Scaffold(
    topBar    = { TopAppBar(title = { Text("Inbox") }) },
    bottomBar = { NavigationBar { /* … */ } },
    floatingActionButton = { FloatingActionButton(onClick = ::compose) { Icon(Icons.Filled.Add, null) } },
) { innerPadding ->
    MessageList(Modifier.padding(innerPadding))
}
```

The guideline prefers slots over parameter proliferation. Buiy parallel: this
is the **F7** answer — pass children as a block, not as N flattened props.

### Dynamic / data-driven lists

Composition is *generated from data each recomposition*, so a list is a
`for`-like emission, not a pre-built marker tree:

```kotlin
LazyColumn {
    items(messages, key = { it.id }) { msg ->   // stable key per item
        MessageRow(msg)
    }
    item { Divider() }                           // one-off non-data item
}
```

**No direct retained-mode analog:** the content lambda is re-run and diffed
against the prior composition. Buiy has no re-run; data-driven content must be
reconciled by a *system*, not regenerated by a call (the **F7** "no dynamic
content in scenes" friction).

## 2. The state model

### Local state: `remember { mutableStateOf(…) }`

`mutableStateOf` creates an observable holder; reading it inside a composable
subscribes that composable to changes. `remember` survives recomposition;
`rememberSaveable` also survives config change / process death.

```kotlin
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("Count: $count") }
}
```

### State hoisting — the canonical pattern (F1/F2)

Official rule: "hoist UI state to the **lowest common ancestor** between all
the composables that read and write it … expose to consumers immutable state
and events to modify the state." This turns a *stateful* composable into a
*stateless* one whose state is owned by the caller. The pattern is a pair:

```kotlin
// stateless: value flows DOWN, change events flow UP. No internal state.
@Composable
fun NameField(value: String, onValueChange: (String) -> Unit, modifier: Modifier = Modifier) {
    OutlinedTextField(value = value, onValueChange = onValueChange, modifier = modifier)
}

// stateful: a thin overload that owns the state and feeds the stateless one
@Composable
fun NameField(modifier: Modifier = Modifier) {
    var name by rememberSaveable { mutableStateOf("") }
    NameField(value = name, onValueChange = { name = it }, modifier = modifier)
}
```

The `value: T` + `onValueChange: (T) -> Unit` shape **is** Compose's
"controlled component" convention (identical to React's controlled inputs).
It is the **canonical answer to F1/F2**: a widget exposes its value as plain
data and emits a *typed, per-widget* change callback, instead of Buiy's single
untyped `OnPress(Entity)`. The component guidelines actively *forbid* the
joint-ownership shortcut: "Parameters of type `MutableState<T>` are
discouraged since it promotes joint ownership over a state between a component
and its user" — don't hand the widget a writable handle; hand it a read value
+ a change event.

### App state is a SEPARATE layer from the Semantics (a11y) tree

For app-wide state the owner moves out of the composition entirely (a
`ViewModel`), and the composition observes it:

```kotlin
@Composable
fun InboxScreen(vm: InboxViewModel = viewModel()) {
    val state by vm.uiState.collectAsStateWithLifecycle()
    MessageList(state.messages, onArchive = vm::archive)
}
```

Critically, **app state and the Semantics tree are distinct planes**: state
lives in `mutableStateOf`/`ViewModel`; the semantic projection is attached
separately via `Modifier.semantics { … }` (see the sibling
[`compose-semantics.md`](../retained-mode-semantics-automation/compose-semantics.md)).
That separation is direct evidence for Buiy's **F1** open question (should app
STATE be distinct from the AccessKit tree?) — Compose keeps them distinct and
projects one from the other.

### State-typed components & `remember*State()` factories

When per-field hoisting is impractical, the convention is a domain state object
plus a `remember`-prefixed factory; the hoisted type is named `<Composable>State`
(`LazyColumn` ↔ `LazyListState` ↔ `rememberLazyListState()`).

## 3. How change/events propagate

Compose has **no signal/binding object** for widget events — events are plain
Kotlin lambdas passed *down* as parameters and invoked *up* by the widget
("value down, events up", unidirectional). The callback *is* the wiring:

```kotlin
Switch(checked = isOn, onCheckedChange = { isOn = it })
Slider(value = vol, onValueChange = { vol = it }, valueRange = 0f..1f)
Checkbox(checked = agreed, onCheckedChange = { agreed = it })
```

Every interactive Material component follows the same `<state>` +
`on<State>Change` pair: `value`/`onValueChange`, `checked`/`onCheckedChange`,
`selected`/`onClick`, `expanded`/`onExpandedChange`. The *uniformity of that
naming* is what the API guidelines enforce, and what gives Compose a
predictable event surface without a typed-event subsystem. For Buiy (**F2**)
the transferable idea is the **shape** (one typed change callback per widget,
named by convention), not the lambda mechanism.

> **A real "multiple spellings" case (F5).** Text input now ships **two** state
> models side-by-side: the original **value-based** overload
> (`BasicTextField(value, onValueChange, …)`) and a newer **state-based**
> overload (`BasicTextField(state: TextFieldState, …)` /
> `rememberTextFieldState()`), which "fully encapsulates the entire input
> flow." The state form is now *recommended*; the value form persists for
> compatibility. Even Compose, with a published style guide, grew two
> co-existing spellings of its most-used widget once the controlled-value
> convention hit the limits of complex editing state — a cautionary data point
> for Buiy's **F5**.

Verdicts (controlled-value as the F1/F2 answer, named-slots-yes /
dynamic-lambda-no, state-vs-semantics separation) are decided in
[lessons.md](lessons.md).
