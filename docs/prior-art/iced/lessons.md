**Subject:** Iced — Validates / Avoid / Borrow decision file for Buiy

This is the consult-this-when-designing decision file. The other files in this folder are evidence; this file is the synthesis. Three sections — **Validates** (Buiy choices Iced's experience confirms), **Avoid** (pitfalls to mitigate), **Borrow** (primitives worth studying).

## Top of file: the single most important finding

**Iced is the strongest empirical validation available that cosmic-text scales to production retained-mode UI outside Bevy.** System76's COSMIC desktop — every COSMIC application (`cosmic-files`, `cosmic-settings`, `cosmic-text-editor`, `cosmic-terminal`, `cosmic-launcher`, `cosmic-applets`) plus the `cosmic-comp` Wayland compositor — ships cosmic-text in production daily. With Bevy `main` (0.19-dev) migrating `bevy_text` from cosmic-text to Parley + swash (issue [#21765](https://github.com/bevyengine/bevy/issues/21765), 2025-11-06), Iced becomes the **largest non-Bevy production cosmic-text consumer**. Buiy's commitment to cosmic-text ([foundation architecture.md § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md)) has independent confirmation outside Bevy — the bet does not depend on Bevy's continued use of the substrate. See [`text-and-cosmic.md`](text-and-cosmic.md) for the version timeline and [`../cosmic-text/lessons.md`](../cosmic-text/lessons.md) § Validates → "System76 stewardship via COSMIC desktop dogfooding" for the cross-link.

A secondary corollary: the brief that produced this folder asserted Iced had migrated to Parley + harfrust. **That is false as of 0.14.0.** Iced 0.14 pins `cosmic-text = "0.15"` directly ([Cargo.toml](https://github.com/iced-rs/iced/blob/0.14/Cargo.toml)). Iced is on `harfrust` *transitively* via cosmic-text 0.15.0's PR [#417](https://github.com/pop-os/cosmic-text/pull/417), not directly. Treat the "convergence on Parley" framing as Bevy-side only — Iced + Buiy converge on cosmic-text, bevy_ui post-0.19 diverges. See [`text-and-cosmic.md`](text-and-cosmic.md) § "Brief correction."

## Validates

These Buiy design choices are confirmed by Iced's experience:

- **cosmic-text + harfrust (via `cryoglyph`) for production retained-mode UI.** Iced has shipped cosmic-text since 0.10.0 (2023-07-28, PR [#1697](https://github.com/iced-rs/iced/pull/1697)) and forked `glyphon` into `iced-rs/cryoglyph` in March 2025, committing *deeper* to cosmic-text rather than migrating away. The flagship is COSMIC desktop (~7 production apps); the long tail is Halloy, Cryptowatch desktop, Sniffnet, Veloren menus, ajour, ludusavi. Buiy's cosmic-text bet inherits all of that production validation. See [`text-and-cosmic.md`](text-and-cosmic.md), [`../cosmic-text/lessons.md`](../cosmic-text/lessons.md) § Validates.
- **Retained-mode UI with state-management discipline is viable at production scale.** COSMIC desktop apps ship at tens-of-thousands of lines on the Elm Architecture; Halloy IRC client and Cryptowatch desktop confirm the pattern works for non-trivial productivity surfaces. Buiy is not Elm-architecture (it is ECS), but the *retained* part — application state survives across frames, widgets get rebuilt on demand, layout caches against change — is the shape Buiy commits to. Iced is the existence proof that retained-mode Rust GUI works without a native widget kit. See [`elm-architecture.md`](elm-architecture.md), [`architecture.md`](architecture.md).
- **Owning a render pipeline is viable when paired with cosmic-text + own layout.** `iced_wgpu` (default) + `iced_tiny_skia` (CPU fallback) is a complete render stack that Iced has maintained since 0.1 (2020-04). The maintenance cost is real (`wgpu` major bumps land every cycle), but the architecture is sound. Buiy's commitment to plug into Bevy's render graph ([foundation architecture.md § 2.3](../../specs/2026-05-07-buiy-foundation/architecture.md)) shares Bevy's wgpu pipeline rather than running a parallel one — Iced is the existence proof that the parallel-pipeline approach also works.
- **MIT-style permissive licensing works in practice for Rust GUI.** Iced has shipped under single-MIT since `0.0.0` (2019) without legal incident. Buiy commits to `MIT OR Apache-2.0` (matches Bevy + AccessKit + Taffy + cosmic-text), but Iced demonstrates that the strict-MIT path is operationally fine — the cost is paperwork friction in dual-license-dependency-graphs, not legal exposure. See [`governance.md`](governance.md) § "License."
- **Bus-factor concentration with one architect is bearable if the project has a vendor-scale backer.** Héctor Ramón is the sole committer; Kraken/Cryptowatch sponsors Héctor financially; System76 employs engineers who contribute via COSMIC. Iced has survived six years with this structure. Buiy's modular subsystems (separable text, layout, render, a11y, focus, picking sub-spec areas — see [foundation README § 4](../../specs/2026-05-07-buiy-foundation/README.md)) reduce single-author dependency by distributing the surface area, but Iced is the existence proof that single-architect Rust GUI can ship at scale.
- **Multi-window landed in 0.12.0 (2024-02-15, PR [#1964](https://github.com/iced-rs/iced/pull/1964)).** Useful timing precedent — Iced launched in 2020 and added multi-window four years later when COSMIC required it. The architectural choice (single Model spans multiple winit windows; each window has its own `view` projection) matches bevy_ui's per-window pattern (Window entity per winit `WindowId`). Buiy can defer multi-window similarly without committing in v1; when commit happens, the per-`WindowId` AccessKit-adapter pattern is the right shape. See [`open-problems.md`](open-problems.md) § "Multi-window support depth."
- **Sponsor-funded open source is a viable funding model for Rust GUI.** Kraken/Cryptowatch has sponsored Héctor's development since ~the 0.6 era (2022-12). Combined with GitHub Sponsors (~14 current sponsors per [hecrj's page](https://github.com/sponsors/hecrj)), this gives Iced commercial-runway-without-commercial-license. Buiy's funding model is open (TBD per foundation governance discussions); Iced shows one path that works. See [`governance.md`](governance.md) § "Funding."
- **Custom text-engine integration via fork is a workable pattern.** `cryoglyph` is Iced's March 2025 fork of `grovesNL/glyphon` (the cosmic-text → wgpu adapter). The fork lets Iced keep its substrate current without waiting on upstream `glyphon`. Same shape as Bevy potentially needing to fork cosmic-text if upstream slows — pattern is established. Iced's experience: forking is operationally fine, but you own the maintenance forever. See [`text-and-cosmic.md`](text-and-cosmic.md) § "Text rendering pipeline."

## Avoid

Pitfalls drawn from Iced's experience, with Buiy's mitigation.

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **Shipping without AccessKit.** Iced issue [#552](https://github.com/iced-rs/iced/issues/552) has been open since 2020-10-05 — ~5.5 years. No PR with a credible landing path; COSMIC team built bespoke wiring outside the repo. Production-app screen-reader coverage is zero. | [`critiques.md`](critiques.md) § "No native AccessKit integration"; [`open-problems.md`](open-problems.md) § "AccessKit integration." | Buiy is AccessKit-first from day one ([foundation architecture.md § 2.6](../../specs/2026-05-07-buiy-foundation/architecture.md)). Per-window AccessKit adapter, decomposed `A11yRole` / `A11yLabel` / `A11yDescription` / `A11yStates` / `A11yRelations` components, WCAG 2.2 AA as the floor (foundation goal 2). The AccessKit gap is *the* structural reason Iced is unviable for productivity apps with a11y requirements — Buiy refuses to repeat. |
| **Rolling your own layout engine instead of Taffy.** Iced ships hand-rolled flex in `iced_core::layout::flex.rs` ("inspired by druid"). No CSS Grid algorithm, no subgrid, no anchor positioning, no `position: sticky`, no float, no baseline alignment, no writing-mode awareness, no fragmentation. The 0.14 `grid` widget is a fixed-shape table, not a CSS-Grid solver. | [`layout-engine.md`](layout-engine.md); [`critiques.md`](critiques.md) § "No Grid layout." | Buiy commits to Taffy ([foundation architecture.md § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md)) and inherits CSS Flexbox Level 1, Grid (Taffy 0.3+), block (0.4+), float (0.10+), named-line grid (0.9+). bevy_ui has 3.5+ years on Taffy as cross-validation. See [`../bevy-ui/lessons.md`](../bevy-ui/lessons.md) § Validates → Taffy. |
| **Single-architect bottleneck without a published RFC process.** No formal RFC; design discussion lives across GitHub Issues + Zulip + Discord + Whimsical roadmap + the in-progress iced book. The 14-month 0.13 → 0.14 gap is partly the cost. Issue #552 sat 5+ years; outsiders cannot predict what lands when. | [`governance.md`](governance.md) § "RFC / decision process"; [`critiques.md`](critiques.md) § "Release-cadence drift", § "Maintainer review style", § "Single-maintainer bus-factor risk." | Buiy keeps a canonical doc log in `docs/specs/` + `docs/plans/` + `docs/reports/` + `docs/prior-art/`. Modular subsystem layout reduces single-author dependency. Same mitigation as for bevy_ui's lightweight-RFC critique. |
| **The Elm architecture's `Message` enum + single-Model pattern at very large scale.** COSMIC + Cryptowatch + Halloy all report friction at ~200+ Message variants. Mitigations (substruct decomposition, `Element::map(SubMessage → Message)`) are verbose and refactor-hostile — adding a field to the global Model means touching every `update` arm that needs it. | [`elm-architecture.md`](elm-architecture.md) § "State management at scale"; [`critiques.md`](critiques.md) § "Elm-architecture verbosity at scale", § "Single state tree." | Buiy is ECS-native ([foundation architecture.md § 2.4](../../specs/2026-05-07-buiy-foundation/architecture.md)). State is per-entity-decomposed, not single-global. Per-component observers replace the central `Message` enum; observers fire per-component without requiring a central dispatch. Iced is the cautionary tale, not the model. |
| **Single-MIT licensing drift from the surrounding ecosystem.** Iced has shipped under MIT-only since 2019. Most of the Rust GUI ecosystem (Bevy, AccessKit, Taffy, cosmic-text, egui, Linebender stack) dual-licenses `MIT OR Apache-2.0`. Mixing into a multi-license bundle is operational paperwork, especially for patent-conscious commercial users. | [`governance.md`](governance.md) § "License." | Buiy commits to `MIT OR Apache-2.0` to match Bevy + AccessKit + Taffy + cosmic-text. Inherits Apache-2.0's explicit patent grant; no paperwork tax for downstream dual-licensed consumers. |
| **Mobile / touch support not first-class.** Iced README lists only Windows/macOS/Linux/Web. No iOS or Android targets in CI. No touch-first widgets, no soft-keyboard handling, no swipe / pinch / multi-touch, no drawer / bottom-tab / modal-sheet patterns. winit's mobile support is the lower bound; Iced has not built above it. | [`critiques.md`](critiques.md) § "Mobile support is limited"; [`open-problems.md`](open-problems.md) § "Mobile target maturity." | Bevy supports Android and iOS natively; Buiy inherits this. Foundation [README § 1.6](../../specs/2026-05-07-buiy-foundation/README.md) lists "Game and app, both" as a goal — mobile must work. AccessKit's pre-1.0 Android adapter + new iOS adapter give the a11y plumbing Iced lacks. Open question: whether v1 ships mobile or stages it (foundation README § 5). |
| **WASM target second-class.** Iced "Web" support is wgpu's WebGL2 backend; no clipboard parity, no native file dialog, no multi-window, no system-font enumeration, no AccessKit web-adapter integration. Bundle size is multi-megabyte (production web apps target sub-500 KB). | [`critiques.md`](critiques.md) § "WASM support is limited"; [`open-problems.md`](open-problems.md) § "WASM target completeness." | Buiy treats WASM as in-scope per [foundation README § 5](../../specs/2026-05-07-buiy-foundation/README.md) ("Bevy WASM target policy" open question). Buiy inherits Bevy's wgpu→WebGL/WebGPU pipeline (same substrate as Iced) but commits to the AccessKit web adapter once it matures — Iced has not. |
| **Custom renderer = doubled maintenance.** Iced ships `iced_wgpu` + `iced_tiny_skia` + `cryoglyph` (its own glyphon fork). Each `wgpu` major bump (22.0 → 27.0 in 0.14) is a porting event. The `cryoglyph` fork commits Iced to maintaining its own cosmic-text→wgpu adapter forever. Total surface area is large for a single-architect project. | [`architecture.md`](architecture.md); [`critiques.md`](critiques.md) § "Iced owns its own renderer." | Buiy uses `wgpu` directly via Bevy's render graph ([foundation architecture.md § 2.3](../../specs/2026-05-07-buiy-foundation/architecture.md)) — shares Bevy's `wgpu` upgrade work, shares Bevy's render-graph node infrastructure. No parallel render pipeline; no glyphon-fork analogue (Buiy embeds cosmic-text directly into its render passes). |
| **Function-based styling without a token system limits expressiveness at design-system scale.** Iced's `style: fn(&Theme, Status) -> Style` is type-safe and per-widget, but a 50-widget app accumulates style closures linearly. No semantic tokens, no CSS-style cascade, no per-subtree variable scoping. `libcosmic`'s `cosmic_theme::Theme` is the add-on layer System76 wrote because raw Iced wasn't enough. | [`widgets-and-styling.md`](widgets-and-styling.md) § "Themes", § "No design-token system"; [`critiques.md`](critiques.md) § "No CSS-style cascade." | Buiy commits to semantic-token theming at the design layer + per-subtree token overrides ([foundation architecture.md § 2.5](../../specs/2026-05-07-buiy-foundation/architecture.md)). Function-based styling remains available for one-offs; the token system is the design-system substrate. Open question: whether to support CSS-style declarative stylesheets above tokens (foundation README § 4 → `buiy-theme-tokens-design`). |
| **No CSS Grid widget; Row-of-Column for two-axis structure.** Iced 0.14's `grid` widget is bounded equally-sized cells, not the CSS Grid algorithm. Two-axis layouts require nesting `Row` of `Column` with manual gutter math, or the new bounded `grid`. | [`layout-engine.md`](layout-engine.md); [`widgets-and-styling.md`](widgets-and-styling.md) § "Built-in widget catalog." | Buiy's Taffy provides CSS Grid directly (named lines, templates, span, auto-flow, subgrid in flight). The widget catalog can ship a `Grid` component that maps 1:1 to Taffy's grid solver. |
| **Animation primitives below CSS-transitions bar.** Pre-0.14 was `Subscription::frame()` polling. 0.14 added the Animation API (PR [#2757](https://github.com/iced-rs/iced/pull/2757)) but no CSS-style style-property transitions, no layout transitions, no spring physics, no gesture-driven, no scroll-driven. | [`critiques.md`](critiques.md) § "No animation primitives"; [`open-problems.md`](open-problems.md) § "Animation / transition primitives." | Buiy plans dedicated animation primitives in `buiy-animation-design` ([foundation interaction.md § 3.7](../../specs/2026-05-07-buiy-foundation/interaction.md)) with web-platform parity (transitions on style properties, layout transitions, spring physics, reduced-motion gating). Iced's Animation API is a *reference for variant shapes*, not a *model to copy*. |
| **No drag-and-drop primitive or sortable-list contract.** Iced exposes winit-level pointer events; widget-to-widget DnD, reorder-by-drag lists, drop-zone widgets are app-author work. No a11y-compatible alternatives. | [`open-problems.md`](open-problems.md) § "Drag-and-drop ergonomics." | Buiy commits to first-class drag-and-drop in `buiy-input-events-design`, including a11y-compatible alternatives (drag-as-keyboard-operation, screen-reader announcements). |

## Borrow

Concrete primitives worth studying and possibly adapting:

1. **The `cryoglyph` fork pattern for keeping a substrate current.** Iced forked `grovesNL/glyphon` to `iced-rs/cryoglyph` in March 2025 when keeping iced's cosmic-text→wgpu adapter on Iced's own roadmap mattered more than waiting on upstream. The pattern: fork a single-purpose adapter crate, not the substrate itself; keep the fork small enough to merge upstream changes when desired. If cosmic-text upstream stalls (Bevy moving to Parley reduces upstream pressure — see [`text-and-cosmic.md`](text-and-cosmic.md)), Buiy may need to apply the same pattern. See [`distribution.md`](distribution.md) § "Workspace crates."
2. **COSMIC desktop's dogfooding model.** System76 employs engineers who contribute to Iced as part of their COSMIC work. The pattern (vendor-with-commercial-stake employs project contributors) is more reliable than pure-sponsorship for keeping a project alive long-term. Bevy has cart's Foundation; cosmic-text has System76 directly; Iced has System76 via COSMIC + Kraken via Cryptowatch. Useful reference for thinking about Buiy's long-term funding/governance story. See [`ecosystem.md`](ecosystem.md) § "The flagship at-scale user."
3. **GitHub Sponsors-funded development as a partial funding source.** Iced's [GitHub Sponsors page](https://github.com/sponsors/hecrj) shows 14 current sponsors / 40 past sponsors across four coffee-themed tiers ($5 / $10 / $20 / $50). Combined with Kraken's corporate sponsorship, this gives Héctor financial runway without a commercial license. Borrow the multi-source funding pattern; Iced has six years of evidence it works.
4. **The Elm architecture as a conceptual reference for state-management discipline.** Even though Buiy is ECS-native, the Elm-architecture *insight* — application state is a value, mutations are described not performed, side effects are values the framework executes — is a useful frame. ECS observers + commands have the same shape if you squint: the observer is the `update` reaction; the command is the `Task<Message>` descriptor. See [`elm-architecture.md`](elm-architecture.md) § "`Task<Message>` for side effects" — Buiy can study `Task` as a reference for what a clean async-effect descriptor looks like in Rust GUI, even though Buiy uses `AsyncComputeTaskPool` + observers directly.
5. **The `Subscription::frame` pattern for animation timing.** Pre-0.14, Iced apps animated via `Subscription::frame()` (a 60Hz tick that produces Messages). Buiy's animation system can study this for the "time-as-stream-of-Messages" framing — though Buiy's ECS naturally provides per-frame system execution, the conceptual shape (animation is a subscription to time) is useful design vocabulary. See [`architecture.md`](architecture.md) § "System layer."
6. **Property-based widget contracts via `view() -> Element`.** Iced widgets are *values* that compute a layout + draw + event-dispatch contract; the runtime never mutates them. Compare to ECS where widgets are entities that systems read/write. The property-only contract is what makes Iced's reconciliation possible; Buiy's ECS variant ("entity persists; components hold the state") trades different costs. Worth understanding what stateless-widget-with-parallel-state-tree buys, even when not adopting it. See [`elm-architecture.md`](elm-architecture.md) § "The stateless widgets trade-off."
7. **The "stateless widgets, state in Model" pattern as a counter-example.** Iced's parallel widget-state `Tree` keyed by tree-position + type-id is the mechanism that makes per-frame rebuild work. ECS bypasses this entirely (entity identity *is* the persistence). Useful negative reference: when designing Buiy's authoring layer, *not* needing a reconciliation tree is a real ergonomic advantage worth naming explicitly. See [`architecture.md`](architecture.md) § "The Element tree."
8. **Iced's `Theme` function-of-Appearance approach as an alternative.** Iced's `style: fn(&Theme, Status) -> Style` model is type-safe (the compiler enforces every styleable widget gets a style); it's the simplest viable styling discipline that isn't a stylesheet. Buiy's token system will be richer (semantic names, cascading-equivalent via subtree overrides, OS-preference binding), but Iced's pattern is the floor — any token system that ends up *more verbose* than `style: |theme, status| { ... }` for app-level one-offs has missed the mark. See [`widgets-and-styling.md`](widgets-and-styling.md) § "Styling."
9. **Multi-window pattern: one Model, many winit windows.** Iced 0.12.0 (PR [#1964](https://github.com/iced-rs/iced/pull/1964)) added multi-window with a single `Application`/Model spanning multiple winit windows, each with its own `view` projection. Per-window AccessKit adapter ownership (when Iced gets AccessKit) keys to `WindowId`. Same shape as bevy_ui's per-window adapter pattern. Buiy follows the same key. See [`open-problems.md`](open-problems.md) § "Multi-window support depth."
10. **The `iced_wgpu` per-shape pipeline abstraction.** `iced_wgpu` decomposes drawing into per-shape pipelines (atlas / quad / triangle / gradient / shader) that the runtime composes. This is `wgpu`-direct, not relying on a higher-level retained scene graph. Buiy's render path (plugging into Bevy's render graph) is a different abstraction, but Iced's per-pipeline composition is a useful reference for "what do you need at minimum to render a retained-mode UI on wgpu?" See [`architecture.md`](architecture.md) § "Renderer stack."

## How to use this file

When designing a Buiy feature:

1. **Find the row in `Avoid`** that names a pitfall close to your design. Read the linked file for the original incident.
2. **Find the entry in `Borrow`** that names a primitive close to what you're designing. Read the linked file to understand Iced's shape, then adapt for Buiy's component model (ECS-native, decomposed, observable, AccessKit-first).
3. **Promote any decision into a Buiy spec** under `docs/specs/` — this file is for capturing what we learn from Iced, not for encoding Buiy's own decisions.
