# Lessons for Buiy

This is the consult-this-when-designing file. Other files in this folder are evidence; this is synthesis. When designing any Buiy feature touching declarative authoring, plugin shape, render pipeline, focus, or the bus-factor / maintenance-surface question, start here.

## The headline

**kayak_ui's silent fade — solo maintainer, parallel UI stack, custom DSL, pre-1.0, Bevy quarterly cadence — is the structural failure pattern Buiy's foundation explicitly engineers against.** Where [`../bevy-cosmic-edit/lessons.md`](../bevy-cosmic-edit/lessons.md) is "don't build a bridge crate," this one is **"don't build a parallel UI stack as a solo-maintained third-party crate with its own custom DSL."** They are two flavors of the same root cause: third-party Bevy UI work without funded multi-maintainer stewardship does not survive Bevy's quarterly breaking-release cadence past ~2 years.

Read [`why-abandoned.md`](why-abandoned.md) before anything else in this folder. The Borrow section below is short by design — the architectural shape of the crate is mostly a "don't reproduce" pattern, not a "do reproduce" one.

## Validates

These Buiy design choices are confirmed by kayak_ui's failure trajectory:

- **Buiy is BSN-friendly-by-construction, not custom-DSL** (foundation [`architecture.md` § 2.4](../../specs/2026-05-07-buiy-foundation/architecture.md), [`../bevy-ui/lessons.md` § Top-of-file finding 1](../bevy-ui/lessons.md)). kayak_ui's `rsx!` macro is the canonical example of a third-party DSL paying a recurring tax with every Bevy minor release, while also competing with the engine's own (eventually-landing) declarative-authoring syntax. Buiy components ship small + decomposed + public-fielded + reflection-registered *now* so authoring rides Bevy's official syntax whenever BSN lands — no parallel DSL to maintain.
- **Buiy owns the render pipeline directly, not via a third-party crate** (foundation [`architecture.md` § 2.3](../../specs/2026-05-07-buiy-foundation/architecture.md)). kayak_ui's custom MSDF + quad-shader pipeline was sound engineering for 2022; by 2024 Bevy's render-graph migrations had rendered it unmaintainable for a solo maintainer. Buiy's render pipeline is *first-class Buiy code*, not a separate crate's burden — the maintenance load is single-rooted at Buiy.
- **Buiy uses Taffy, not morphorm or a bespoke layout engine** (foundation [`architecture.md` § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md), per [`../taffy/`](../taffy/)). kayak_ui chose morphorm in 2022, then ate the divergence as Bevy + bevy_ui consolidated around Taffy. Even kayak_ui's successor woodpecker_ui flipped to Taffy.
- **Buiy ships AccessKit-first, every widget with its APG keyboard contract** (foundation [`accessibility.md`](../../specs/2026-05-07-buiy-foundation/accessibility.md)). kayak_ui shipped zero AccessKit integration, no APG patterns beyond a partial Accordion, no `:focus-visible`, no live regions. The accessibility gap was disqualifying for any productivity-app target — the gap is exactly what Buiy's foundation tier was written to close.
- **Buiy's focus tree includes traps, restoration, inert, spatial nav from foundation tier** (foundation [`interaction.md` § Focus](../../specs/2026-05-07-buiy-foundation/interaction.md)). kayak_ui's `FocusTree` was the right shape (single coherent tree) but shallow (no traps despite a `Modal` widget, no restoration on dialog close, no spatial gamepad nav). Buiy's foundation makes these foundation-tier from day one.
- **Buiy is the project, not a third-party plugin** (foundation [`README.md` § Goals](../../specs/2026-05-07-buiy-foundation/README.md)). Buiy's maintenance load is single-rooted. There is no separate "Buiy widgets" or "Buiy text-edit" crate maintained by a different solo volunteer; the entire surface is Buiy's commitment. kayak_ui's failure mode (solo + third-party + parallel + custom-DSL) is structurally unavailable to Buiy.
- **Buiy never embeds React-style hooks in Rust** (foundation [`architecture.md` § Reactivity](../../specs/2026-05-07-buiy-foundation/architecture.md): observers + change detection in v1, signals as a follow-up sub-spec). kayak_ui's React-paradigm port required a parallel reactive runtime over ECS — the very complexity the maintainer cited as the woodpecker_ui rewrite trigger ("*1,000 lines to fewer than 200*"). Buiy stays ECS-native; reactivity rides Bevy's existing primitives.
- **Buiy's status signaling is unambiguous** (foundation README § "Tracks Bevy"). Buiy releases declare which Bevy minor they target; if Buiy stops keeping up, the README says so the same week. kayak_ui's passive abandonment (no archive banner, no deprecation notice, still default-version on crates.io 27 months later) is the inverse signal Buiy commits not to send.

## Avoid

Each row links to evidence. The pitfalls are kayak_ui-specific instances of a broader pattern; the Buiy mitigation is the foundation spec's response.

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **Building a custom DSL outside the host engine's macro system** (kayak_ui's `rsx!`). Every Bevy `Bundle`-shape change forces a macro-expansion-site audit; the DSL must compete with the engine's eventual declarative syntax (BSN) for community attention. | [`architecture.md` § The rsx! macro](architecture.md#the-rsx-macro), [`why-abandoned.md` § The custom-DSL tax](why-abandoned.md), [`critiques.md` § Custom-DSL friction](critiques.md) | Buiy ships **no custom DSL**. Components are BSN-friendly-by-construction now (per [`../bevy-ui/lessons.md` § Top-of-file finding 1](../bevy-ui/lessons.md)); authoring will ride BSN whenever it lands. Plain ECS spawn calls work today against every Buiy component. |
| **Shipping a solo-maintained, third-party, parallel UI stack for a pre-1.0 engine.** Five independent maintenance axes (render + layout + focus + DSL + Bevy compat) × one volunteer × quarterly cadence = unsustainable past ~2 years. | [`why-abandoned.md`](why-abandoned.md), [`critiques.md` § Single maintainer / bus factor 1](critiques.md) | Buiy is the project itself, with bus-factor > 1 by mandate. No load-bearing piece of Buiy ships as a separate, solo-maintained, third-party crate. Foundation [`README.md` § Goal 6](../../specs/2026-05-07-buiy-foundation/README.md) makes Buiy game-and-app-both, single-rooted at this repo. |
| **Pre-1.0 third-party UI as production foundation.** kayak_ui's README itself said "*in the very early stages of development. Important features are missing.*" Consumers who treated it as production-ready ate the 2024 abandonment cost. | [`critiques.md` § Pre-1.0 churn](critiques.md), [`history.md` § The decline](history.md) | Buiy targets a documented Bevy minor per release. Buiy's own version cadence is decoupled from "is this finished" rhetoric; the verification harness (foundation `verification.md`) defines "done" per CI gate. |
| **React-style hooks ported into Rust without compiler support.** Rust's borrow checker fundamentally cannot represent React's "hooks must be called in the same order" rule. kayak_ui worked around this with explicit context + widget-entity-keyed state; the maintainer himself later cited it as the rewrite trigger. | [`architecture.md` § Component model + reactivity](architecture.md#component-model--reactivity), [`api.md` § State + effects](api.md), [`why-abandoned.md`](why-abandoned.md) | Buiy stays ECS-native. Reactivity is observers + change detection (per [`../../specs/2026-05-07-buiy-foundation/architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md)); a signal/computed/effect primitive is a follow-up sub-spec, not v1 foundation. |
| **Custom layout engine (morphorm) instead of Taffy.** A 2022-defensible choice that orphaned kayak_ui from the entire bevy_ui + Bevy + Buiy + woodpecker_ui Taffy-aligned ecosystem. Frozen layout engine = frozen bug-fix stream. | [`architecture.md` § Layout](architecture.md#layout), [`history.md`](history.md), [`critiques.md`](critiques.md) | Buiy uses **Taffy** directly (foundation [`architecture.md` § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md)). Taffy is the upstream both Bevy and Buiy track; the bug-fix / feature-addition stream is shared. See [`../taffy/`](../taffy/). |
| **Custom MSDF text rendering with no fallback / no atlas-sharing.** kayak_ui's MSDF pipeline was sharp-at-arbitrary-scale but isolated from the rest of the Bevy text ecosystem (bevy_ui's text, bevy_text's atlas). When the maintainer pivoted, all consumers had to replace their text rendering too. | [`architecture.md` § Render path](architecture.md#render-path), [`critiques.md`](critiques.md) | Buiy integrates **cosmic-text** directly (foundation [`text.md`](../../specs/2026-05-07-buiy-foundation/text.md)). Single shared glyph atlas across all Buiy text — display and editable. cosmic-text is multi-consumer (Iced, COSMIC Desktop, Zed, Lapce) so the substrate doesn't depend on kayak_ui-style single-maintainer survival. See [`../cosmic-text/lessons.md`](../cosmic-text/lessons.md). |
| **Two-tree event model (kayak widget tree vs Bevy entity tree).** Events bubbled up kayak_ui's widget tree, not Bevy's entity tree. Consumers had to reason about which tree a given event was flowing through. | [`api.md` § Events](api.md), [`architecture.md`](architecture.md) | Buiy events flow as standard Bevy observers along the entity tree. There is no parallel "Buiy tree." Single-tree-only-by-construction. Foundation [`interaction.md`](../../specs/2026-05-07-buiy-foundation/interaction.md). |
| **Plugin nomenclature shadowing.** `KayakContextPlugin` (Bevy `Plugin`) vs `KayakUIPlugin` (kayak_ui-internal trait) vs `KayakWidgets` (second Bevy `Plugin`) is a frequent confusion source in the kayak_ui issue tracker and tutorials. | [`architecture.md` § Plugin shape](architecture.md#plugin-shape) | Buiy reserves `Plugin` for Bevy's `Plugin` trait. Buiy's own extensibility traits do not contain "Plugin" in their name. (Lint cemented at the [`buiy-bsn-integration-design`](../../specs/2026-05-07-buiy-foundation/README.md) sub-spec level.) |
| **No published performance benchmark.** No 1000-node fixture, no per-keystroke latency claim, no perf-gate in CI. Issue #266 ("Input lag", 2023-05-22) was filed but unresolved at archive. | [`critiques.md` § No published performance benchmark](critiques.md) | Buiy's verification harness (foundation [`verification.md`](../../specs/2026-05-07-buiy-foundation/verification.md)) enumerates productivity-app and game fixtures at 1000+ nodes with named CI gates. Performance is a verifiable target, not unstated. |
| **Zero AccessKit integration; APG patterns absent.** No `aria-*` analogue, no focus traps despite a `Modal` widget, no preedit IME, no live regions, no role-name-value surfacing. | [`critiques.md` § Weak APG / WCAG coverage](critiques.md), [`api.md` § Widget vocabulary](api.md) | Buiy ships AccessKit-first; every widget includes APG keyboard contract + AccessKit wiring + WCAG-2.2-AA target from **F**oundation tier (per [`../../specs/2026-05-07-buiy-foundation/accessibility.md`](../../specs/2026-05-07-buiy-foundation/accessibility.md)). |
| **Passive abandonment without an archive banner.** GitHub `archived: false`, still default-version on crates.io 27 months after last release, README has no deprecation notice. New users still land on it via search. | [`README.md` § Why archived](README.md), [`why-abandoned.md` § Passive abandonment vs deliberate archive](why-abandoned.md) | Buiy's status signaling is unambiguous. Releases declare which Bevy minor they target; if Buiy ever stops keeping up, the README will say so. (kayak_ui-style twilight is a reputational hazard Buiy commits not to inflict on its consumers.) |
| **Depending on kayak_ui in any form (Buiy or downstream).** The crate is silently dead; the substrate decisions (morphorm, custom MSDF) are not Buiy-aligned even if it were resurrected. | [`integration.md`](integration.md), [`why-abandoned.md`](why-abandoned.md) | Buiy does not depend on `kayak_ui`. Do not add it to `Cargo.toml`. The same rule applies to any kayak_ui fork that might attempt resurrection — the architectural shape doesn't change just because a fork picks up the name. (Same logic as [`../bevy-cosmic-edit/lessons.md` § Avoid](../bevy-cosmic-edit/lessons.md) row "Assuming a working fork will emerge.") |

## Borrow

Despite the architectural mismatch at the crate level, three narrow patterns from kayak_ui's shape are worth studying for Buiy's work. Borrow these patterns; don't borrow the crate.

1. **The `MaterialUI` extension surface for custom UI shaders.** kayak_ui exposed `MaterialUI` for consumer-provided shaders on UI nodes — the same pattern bevy_ui later shipped as `UiMaterial`. Buiy's render pipeline ships an analogue (the `BuiyMaterial` slot per [`../bevy-ui/lessons.md` § Borrow #9](../bevy-ui/lessons.md)). The shape is right; kayak_ui got there earlier. The lesson is the *pattern*, not the implementation.

2. **Centralized `FocusTree` as a `Resource`.** kayak_ui's 0.5.0 added "focus tree as a resource" — a single canonical focus tree, not split across per-widget focus state. This is the right shape (matches Buiy foundation [`interaction.md`](../../specs/2026-05-07-buiy-foundation/interaction.md) and the [`../bevy-ui/lessons.md` § Avoid row on "Per-app reinvention of a focus model"](../bevy-ui/lessons.md)). Buiy borrows the *shape*; the depth (`:focus-visible`, traps, restoration, inert, spatial nav) is Buiy's to build, not present in kayak_ui's implementation.

3. **`KayakWidgets` as a separable widget-set plugin.** Splitting "core systems" (`KayakContextPlugin`) from "default widget set" (`KayakWidgets`) into two Bevy plugins gave consumers the option to ship their own widget set against the core. The decomposition shape is right — Buiy plans similar opt-in widget plugins (the `buiy-widget-catalog-design` sub-spec is the locus). The kayak_ui-specific naming collision (`KayakUIPlugin` the trait vs `KayakContextPlugin` the plugin vs `KayakWidgets` the second plugin) is the part to **not** borrow.

## The structural lesson, restated

**The biggest single thing this folder teaches:** a third-party Rust crate maintaining a parallel UI stack (its own render + layout + focus + DSL) against a pre-1.0 engine on a quarterly breaking-release cadence has no sustainable equilibrium with a solo maintainer. kayak_ui got 16 months of value out (Nov 2022 → Feb 2024) before the maintainer hit the wall; he chose to start over with simpler internals (woodpecker_ui) rather than push another migration through the existing surface.

The reproduction strategy for Buiy: **own the parallel stack as the project's load-bearing commitment, not as a third-party crate.** The maintenance burden becomes "track Bevy" — the same load Buiy already accepts as its core mandate; no additional bridge layer or solo-volunteer dependency to fund. Buiy is, by design, exactly the shape kayak_ui *needed* to be to survive but couldn't, because it was structured as a third-party crate from a solo maintainer.

Sister case study: [`../bevy-cosmic-edit/lessons.md`](../bevy-cosmic-edit/lessons.md). Same root cause (third-party + solo + parallel-flavored), different failure expression (bridge-crate vs parallel-stack), different exit (deliberate archive vs passive abandonment). Both teach: own the seam.

## How to use this file

1. **Find the row in Avoid** that names a pitfall close to your design. Read the linked file for the evidence. Apply the mitigation.
2. **Find the entry in Borrow** that names a pattern close to what you're designing. Read the linked file for the original shape; adapt for Buiy's component model.
3. **Promote any decision into a Buiy spec under `docs/specs/`.** This file is for capturing what we learn from kayak_ui's silent fade; it is not where Buiy decisions live.
