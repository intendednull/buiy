# Lessons for Buiy

This is the consult-this-when-designing file. The other files in this folder are evidence; this one is decisions. Blink is the canonical *behavior* reference for the CSS modules Buiy implements a typed subset of, so the lessons here are not "use Blink" — they are "the reference implementation made these choices; here is which to adopt, which to avoid, and which primitives to study before Buiy builds the same thing." It is weighted toward **Phase 9** (stacking + top-layer, `PostTaffyOverrides` sub-pass 6f, NEXT, not yet built) because that is the immediate Buiy work Blink most directly informs.

## Top of file: the single most important finding

**Blink spent roughly a decade learning the rule Buiy already enforces: each pipeline stage reads the *finished, immutable* output of the prior stage and never reaches back to mutate it — and the renderer never recomputes what layout already decided.** This is the BlinkNG separation principle ("once a stage has finished, its outputs should be immutable for the remainder of the rendering update"; "accessing the previous state isn't allowed"), and it is *identical* to Buiy's "layout writes, render reads" contract. Blink paid for it the expensive way: a multi-year LayoutNG rewrite-in-place, carrying two layout engines and a legacy/NG boundary bug class, with no public "done" milestone. Buiy gets the output of that lesson for free by starting clean on Taffy with the contract fixed from day one.

The concrete Phase 9 corollary: Buiy's private `StackingContext { painters_z: Vec<Entity> }` (computed once by sub-pass 6f) is the exact analogue of LayoutNG's immutable fragment tree feeding paint — a pre-sorted, write-once render hand-off. Blink's alternative is a per-frame paint-time re-walk of the layer tree, mitigated only by display-list caching and property trees. Buiy explicitly rejected the re-walk; honor that by making 6f the single place paint order is computed and forbidding render from re-sorting. See [architecture.md § 5](architecture.md), [layout.md § 2](layout.md), [stacking-and-paint.md § 2](stacking-and-paint.md), and the Buiy spec [stacking-and-top-layer.md § 5](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md#5-mapping-to-render).

## Validates

Buiy design choices the Blink experience confirms:

- **"Layout writes, render reads" is the right contract, validated at browser scale.** BlinkNG's immutable-output / no-re-entrancy discipline is what made Blink's pipeline parallelizable and hysteresis-free. Buiy's `PostTaffyOverrides` sub-passes writing *private* render-handoff state (Phase 8's `ResolvedTransform`; Phase 9's planned `StackingContext.painters_z`) are the same shape. Keep render a thin read-only consumer. See [architecture.md § 5](architecture.md), Buiy [architecture.md § 3](../../specs/2026-05-08-buiy-layout-design/architecture.md#3-system-pipeline).

- **Pre-sort paint order at layout time; do not re-walk at paint time.** Blink re-walks the layer tree on every paint and pays for it with display-list caching. Buiy's `painters_z: Vec<Entity>` computed once in 6f is the cleaner choice *given Buiy's premise* that most entities form no stacking context and the render side is a thin consumer, not a second rendering engine. Record that perf assumption in the Phase 9 plan so the tradeoff is auditable. See [stacking-and-paint.md § 2](stacking-and-paint.md).

- **Enumerate the stacking-context trigger union in one place.** CSS scatters the triggers across modules; Blink scatters the checks across `LayoutObject` / `PaintLayer`, which is a recurring "why did this element suddenly composite?" source. Buiy's single sub-pass-6f detection of the *union* (positioned + explicit `z-index`, `isolation: isolate`, non-identity transform, `contain: paint`/`strict`, `opacity < 1` / `filter` / `mix-blend-mode`, root) is the deliberate counter-design. Treat *any one* trigger as sufficient. See [stacking-and-paint.md § 1](stacking-and-paint.md), Buiy [stacking-and-top-layer.md § 2](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md#2-stacking-context-formation).

- **Separating transform/opacity from box geometry pays off later.** Blink can animate `transform` and `opacity` without re-running layout *because* those live in property trees, not in box geometry. Buiy's Phase 8 `ResolvedTransform` (`M = T·R·S·M_transform`) already keeps transform off the Taffy geometry path — which is the same separation that would later let a Buiy animation system mutate `ResolvedTransform` without re-running Taffy. Keep that boundary clean. See [architecture.md § 6](architecture.md), [stacking-and-paint.md § 3](stacking-and-paint.md).

- **Decomposed components beat the megastruct.** `ComputedStyle` is the textbook "god object": every CSS property in one large generated struct, with code-generation, rare-data groups, copy-on-write sharing, and field-aware diff logic existing *only* to make that one struct affordable. Buiy's ECS decomposed public-fielded components (`Style`, `UiTransform`, `Containment`, the planned `Stacking`) get the same wins structurally — memory paid per component (no `UiTransform` ⇒ no cost, the win Blink's rare-data groups chase), per-component change detection (`Changed<UiTransform>` doesn't touch color's machinery), additive maintenance (a feature is a new component, not a field threaded through one struct's getters/setters/packing/diff). See [style.md § 7](style.md), [critiques.md § ComputedStyle](critiques.md).

- **A selector-free model removes an entire subsystem.** Blink needs `RuleFeatureSet` invalidation sets that deliberately *over-invalidate* ("err on the side of correctness") because a class toggle could shift any selector's match set; `:has()`, `@scope`, and container-query-conditioned style each add a new dependency edge. Buiy has no cascade, no selector matching, no `var()` substitution — Bevy ECS `Changed<T>` is the whole invalidation story. The cut is deliberate scope, not omission. See [style.md § 5–6](style.md), [open-problems.md § Style invalidation](open-problems.md).

- **Containment SIZE-zeroing with a `warn!` is CSS-faithful and better than the reference.** Blink collapses a `contain: size` element with no declared size to zero *silently* — a frequent author footgun. Buiy reproduces the defined behavior (`ContainFlags::SIZE`/`INLINE_SIZE` + `Auto` sizing ⇒ `Length::px(0.0)`) but adds a `warn!`. Keep it. See [containment-and-queries.md § 1.1](containment-and-queries.md), Buiy [transforms-and-containment.md](../../specs/2026-05-08-buiy-layout-design/transforms-and-containment.md).

- **Bounding the container-query feedback loop is mandatory; Buiy's bound is explicit.** CSS makes size container queries *require* containment specifically to prevent the loop where a child sizes its parent. Blink's loop-breaker is structural (the mandatory layout+style+size containment). Buiy's is the capped same-frame re-layout (`CqActivate` → `TaffyCompute` → `CqFlipCheck` → `CqFlipReRun`, ≤2× Taffy/frame). Both prevent the same oscillation; Buiy's is explicit and bounded. See [containment-and-queries.md § 3](containment-and-queries.md).

- **Anchor positioning belongs as a post-layout pass, not inside the layout solver.** Anchor positioning is a cross-tree post-layout dependency, fundamentally unlike an intra-formatting-context algorithm — so *both* Blink and Buiy bolt it on after main layout (Buiy: sub-pass 6d). Neither Taffy nor LayoutNG's core can express it. Validates Buiy's above-Taffy placement. See [containment-and-queries.md § 4](containment-and-queries.md), [../taffy/open-problems.md](../taffy/open-problems.md) (issue #703 open).

- **Resolve writing mode once, hand physical values forward.** LayoutNG's fragment tree is deliberately *physical* so paint/hit-test never re-derive direction. Buiy resolves direction once in `WritingModeInherit` → `WritingModeResolved` and keeps the post-resolution representation physical. Same discipline, one pass instead of threading it through a monolith. See [open-problems.md § Writing modes](open-problems.md).

## Avoid

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **Re-walking the layer/stacking tree at paint time.** Blink recomputes paint order every frame, then leans on display-list caching + property trees to make it affordable. For a thin-render-side library this is wasted work and breaks the layout-writes/render-reads contract. | [stacking-and-paint.md § 2](stacking-and-paint.md) | Compute `StackingContext.painters_z` once in sub-pass 6f and have render consume it read-only. Render never re-sorts. Document the "most entities form no SC" perf assumption in the Phase 9 plan. |
| **Scattering stacking-context-formation checks across many code sites.** Blink's checks live across `LayoutObject::StyleDidChange` / `PaintLayer`; the result is the most common web-author confusion ("why is this on top?"). | [stacking-and-paint.md § 1](stacking-and-paint.md), [open-problems.md § Stacking](open-problems.md) | One detection point in 6f computing the trigger *union*. Ensure 6f runs *after* 6e so the composed `Transform` is available for the non-identity-transform trigger. |
| **Building the four property trees (transform/clip/effect/scroll) speculatively.** Blink shipped them over years (Slimming Paint v1→v2→CompositeAfterPaint, default ~2021); the migration was a long-running source of paint-invalidation bugs. | [stacking-and-paint.md § 3](stacking-and-paint.md) | Adopt the layout/composite *separation* now (which 6e/6f already give); build distinct clip/effect/scroll trees only when a concrete compositing requirement (e.g. animate opacity without re-layout) forces it. Buiy composites via Bevy's `wgpu` graph, not a `cc`-style compositor. |
| **Modeling top-layer clip-escape as a per-entity "skip clip" flag.** In Blink, escaping ancestor `overflow` clipping falls out of the top-layer element attaching to the *viewport's* clip node, not its DOM ancestor's — a re-parent in the clip tree, not a special case in the paint walk. A flag invites scattered special-casing. | [stacking-and-paint.md § 4](stacking-and-paint.md) | Model Buiy's top-layer escape as "effective clip = window viewport" ([stacking-and-top-layer.md § 4.3](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md#43-escape-from-clip)), matching Blink's clip-tree re-parenting in intent. |
| **Letting `z-index` on a `position: static` element do anything.** A CSS quirk that trips authors; Blink correctly ignores it (no SC formed). | [stacking-and-paint.md § 1](stacking-and-paint.md) | Buiy already asserts this in its `PositionKind::Static` test ([stacking-and-top-layer.md § 6](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md#6-test-surface)). Keep the test. |
| **Un-stubbing `content-visibility: auto` without `contain-intrinsic-size`.** Blink's ~7× initial-render win is real, but a skipped subtree with no intrinsic-size hint forces the engine to lay it out anyway to learn its size → scrollbar jumping and reflows on scroll. | [containment-and-queries.md § 2](containment-and-queries.md) | Buiy's Phase 8 stub already predicates the Taffy-skip on `contain-intrinsic-size`. When un-stubbing, ship `contain-intrinsic-size` *first* or the skip causes the same scroll jank. |
| **Auto-applying paint containment as a side-effect of `container-type`.** CSS bundles layout+style+size containment into `container-type` to break the loop; doing so silently also makes the container a stacking context (paint containment is an SC trigger) — a surprising visual change. | [containment-and-queries.md § 1, § 3](containment-and-queries.md) | Buiy breaks the loop with its bounded same-frame re-layout, so it does *not* need to auto-apply the full bundle. Keep `INLINE_SIZE`-on-`Container` an explicit opt-in; verify this stays intentional when Phase 5/6 lands. |
| **Treating the Chrome-125 anchor-positioning syntax as settled.** Chrome 125 shipped `inset-area` / `position-try-options`; the CSS WG renamed these to `position-area` / `position-try-fallbacks`, shipped in Chrome 129. Code/tutorials from 2024 read with the old names. | [containment-and-queries.md § 4](containment-and-queries.md), [history.md § anchor](history.md) | Buiy uses typed components, sidestepping the literal property-name churn — but should track the CSS WG's resolution of fallback *semantics*, not the Chrome-125 snapshot. |
| **Letting the layout→style feedback edge be open-ended.** Container queries (style depends on resolved layout size) and anchor positioning deepen the dependency the clean "style → layout → paint" ordering tries to keep separable; in Blink, containment exists partly to bound how far that feedback propagates. | [open-problems.md § cq/layout coupling](open-problems.md) | Buiy makes the edge explicit and finite: `CqFlipCheck`/`CqFlipReRun` is the *only* re-entry into Taffy and is hard-capped; anchor positioning (6d) uses a Kahn topological sort with deterministic cycle-edge dropping so anchor chains cannot loop layout. |
| **Adopting the C++ monolith's costs.** ~70% of Chrome's high-severity bugs are memory-safety bugs; Blink is not shippable as a focused library (embedding it = embedding Chromium); the codebase is un-decomposable. | [critiques.md](critiques.md), [open-problems.md § Memory safety](open-problems.md) | Buiy is memory-safe by language and composes separately-versioned crates (Taffy, `cosmic-text`, AccessKit, `wgpu` via Bevy). Adds features *above* Taffy, never forking it. The cost Buiy accepts instead is integration seams across crates. |
| **Treating Blink behavior as the spec.** The monoculture means "ship in Blink" ≈ "standardize"; following Blink bug-for-bug imports Blink-specific quirks. | [governance.md](governance.md), [comparisons.md](comparisons.md) | Cite the W3C modules (Display 3, Positioned Layout, Containment 3, Writing Modes 4, Anchor Positioning 1) as the contract; treat Blink as *an* implementation and use Servo/Stylo ([../servo-stylo/](../servo-stylo/)) as a second Rust witness. Where Blink and the module diverge, follow the module and note the divergence. |
| **Adding a `Tooltip` tier or per-window scope and claiming it is CSS.** Buiy's `TopLayer` adds a `Tooltip` tier (Blink folds tooltips into popovers/hints) and per-window scope (Blink's top layer is per-document). | [stacking-and-paint.md § 4](stacking-and-paint.md) | Keep these visible as *Buiy choices*, not CSS facts, so faithfulness claims stay honest. The tier order `Fullscreen < Tooltip < Popover < Modal` and per-window scope are documented divergences in [stacking-and-top-layer.md § 4](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md#4-top-layer). |

## Borrow

Concrete Blink/CSS primitives worth studying before building the Buiy analogue:

1. **The stacking-context trigger union** (`PaintLayer` / MDN enumeration). The practically-observable set: root; positioned + non-`auto` `z-index`; `position: fixed`/`sticky` unconditionally; `opacity < 1`; `transform`/`filter`/`backdrop-filter`/`perspective`/`clip-path`/`mask` ≠ none; `mix-blend-mode` ≠ normal; `isolation: isolate`; `contain: layout/paint/strict/content`; `will-change` naming a would-be-trigger; top-layer + `::backdrop`. Buiy's 6f union is a typed subset of this — use it as the checklist. See [stacking-and-paint.md § 1](stacking-and-paint.md).

2. **CSS 2.2 Appendix E paint order** — the fixed seven-step order Blink's `PaintLayerPainter` follows (own background/borders → negative-`z-index` SCs → in-flow non-positioned blocks → non-positioned floats → in-flow inlines → positioned `z: auto`/`0` in tree order → positive-`z-index` SCs). Buiy compresses this into the `painters_z` ordering (neg `z`, in-flow non-positioned, floats [tier-O, empty], in-flow positioned `z: auto`, positive `z`); steps for own-box/blocks/inlines collapse because Buiy paints whole entities. This is the canonical correctness reference for the 6f sort. **Equal-`z` ties break by *tree order*, which the ECS does not provide** — 6f must define a stable key (depth-first `Children`-order index) or `painters_z` is nondeterministic; this is a real 6f gap to close. See [stacking-and-paint.md § 2, § 2.1](stacking-and-paint.md), https://www.w3.org/TR/CSS22/zindex.html.

3. **The top-layer model** (`dialog.showModal()`, Popover API, Fullscreen) — a per-document **single LIFO ordered list** across all three sources where most-recently-added paints on top, bypassing normal stacking and escaping ancestor `overflow` clip. Buiy's `TopLayer { None|Modal|Popover|Tooltip|Fullscreen }` + `TopLayerActivation` (`VecDeque<Entity>`) is the typed analogue, but it is **two-level** (tier by *kind*, then recency within a tier) where Blink's is pure recency — so a popover opened after a modal stays *below* the modal in Buiy but *above* it in Blink. The nested-popover study Phase 9 needs is now in [stacking-and-paint.md § 4](stacking-and-paint.md): nested popovers stack in open order off the one list; light-dismiss/`Esc` order off the same list; dialog-inside-popover is where Buiy's tier rule diverges; and `::backdrop` paints *immediately below its owner* (Buiy has no backdrop entity yet — decide whether to model one). See Buiy [stacking-and-top-layer.md § 4](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md#4-top-layer).

4. **The four paint property trees** (transform / clip / effect / scroll) and the pre-paint → paint → commit handoff. Do not build them yet — but study the *separation* (visual effects off the box tree, into trees the compositor can mutate independently) as the target shape if Buiy ever needs to animate opacity/transform without re-laying-out. `ResolvedTransform` (6e) is the seed of the transform tree; `painters_z` (6f) is the seed of the layerization input. See [stacking-and-paint.md § 3](stacking-and-paint.md), [architecture.md § 2–3](architecture.md).

5. **The LayoutNG constraint-space cache key.** Each immutable fragment is stored alongside the `ConstraintSpace` that produced it; on the next layout, an equal constraint space reuses the cached fragment without descending — "brings the complexity back to O(n)." Buiy's analogue is Taffy's frame-to-frame cache gated by Bevy `Changed<T>`; the lesson is that *predictability* (linear, not re-entrant) was the headline goal, not raw speed. See [layout.md § 2](layout.md).

6. **`ComputedStyle`'s size-fighting techniques as a cautionary catalogue.** Code generation from `css_properties.json5`, rare-data groups (lazy heap allocation for uncommon properties), and copy-on-write data sharing. Study these to understand *what a megastruct costs* — every one of them exists only to make the god object affordable, and Buiy gets the same wins structurally via component presence/absence and per-component change detection. See [style.md § 2](style.md).

7. **Invalidation sets / `RuleFeatureSet`** — the conservative, over-invalidating mechanism that maps a DOM/attribute change to the minimal set of elements to recalc. Buiy does *not* build this (no selector engine), but understanding it explains *why* a selector-free authoring model is a large simplification, and what `bevy_flair` ([../bevy-flair/](../bevy-flair/)) takes on when it leases a real cascade via the Servo `selectors` crate. See [style.md § 5](style.md).

8. **Hit-testing as reverse paint order.** Picking traverses paint order back-to-front; the top layer intercepts input first; `pointer-events: none` makes an element fall through to the one beneath. Because Buiy uses `bevy_picking` ([../bevy-picking/](../bevy-picking/)) for input, 6f must decide whether stacking *feeds* the pick order (CSS-faithful: hit-test = reverse `painters_z`, honouring a pickability flag) or whether picking keeps its own ordering and is allowed to disagree with paint — the same "why did this go there?" hazard as scattered SC detection. The same sorted `painters_z` is both the paint list (front-to-back) and the hit-test list (back-to-front). See [stacking-and-paint.md § 5](stacking-and-paint.md).

## How to use this file

- **Phase 9 plan author:** read the "Top of file" finding and the Borrow items 1–4 and 8, then the Avoid rows on re-walking, scattered detection, speculative property trees, and clip-escape-as-flag. Each maps to a concrete 6f / `TopLayer` decision and cross-links the Buiy [stacking-and-top-layer.md](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md) spec section. Four 6f decisions the evidence newly surfaces and the plan must close: (a) the equal-`z` **tree-order tiebreak** the ECS does not provide (Borrow 2, [stacking-and-paint.md § 2.1](stacking-and-paint.md)); (b) keeping the **SC-trigger union and the clip output separate** — `isolation` SC-without-clip vs `contain: paint` SC-and-clip ([stacking-and-paint.md § 1.1](stacking-and-paint.md)); (c) whether **`will-change` counts as a pre-emptive trigger** like Blink (§ 1.1); (d) whether **stacking feeds hit-testing** via `bevy_picking` (Borrow 8, § 5). The "most entities form no SC" eager-sort premise is asserted, not measured — record it as a premise to validate ([stacking-and-paint.md § 6](stacking-and-paint.md)).
- **Anyone else designing a layout/render/style boundary:** the Validates list is the set of Buiy choices Blink confirms; cite them when defending the contract or the decomposed-component model. The Avoid table is the set of Blink choices to *not* reproduce, each with the existing Buiy mitigation.
- **When the W3C text and Blink disagree:** follow the spec, note the divergence (governance lesson). When the W3C text is ambiguous: check what Blink does, then cross-check Servo/Stylo so Buiy is not importing a Blink-only quirk.
- The other files are evidence; do not re-derive their detail here — follow the cross-links.
