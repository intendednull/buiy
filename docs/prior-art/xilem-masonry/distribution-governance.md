# Distribution & governance

This file combines what would otherwise be two short files (distribution + governance) because Linebender is small enough that the two stories are inseparable: the governance shape determines the release cadence determines the distribution posture.

## Linebender as an organization

Per [Linebender's about page](https://linebender.org/about/):

- **Type:** Volunteer-run collective. **Not** a company, foundation, 501(c)(3), or formal nonprofit.
- **Leadership:** Raph Levien informally leads. "The organization was started by Raph Levien, and he informally leads and drives the work forward." No formal board, no incorporated entity.
- **Member coordination:** Zulip chat (full history public).
- **Code license posture:** MIT and Apache-2.0 for code; CC-BY for non-code materials.
- **Funding:** No mention of GitHub Sponsors, grants, or formal funding on the about page. Members appear to contribute on personal time + employer-tolerated time. Raph's role at Google (font rendering, Skia, etc.) is the historical day-job that funded the early Druid work.

The implication: Linebender's bandwidth is **structurally limited**. Multiple projects (Xilem, Masonry, Vello, Parley, Skrifa, Fontique, Kurbo, Peniko, Color, Velato, etc.) are stewarded by overlapping volunteer attention. Major releases tend to stack — 0.4.0 of Xilem + Masonry shipped after months of build-up. The cadence is irregular.

## Bus factor

The named-contributor list for Xilem/Masonry per "This Month in Xilem" bylines:

- Raph Levien (founder, architectural lead)
- Daniel McNab (co-lead, most monthly posts)
- Olivier Faure (co-lead, structural / docs contributions)
- Plus rotating contributors

Three named active leads is **substantially better than the woodpecker_ui / kayak_ui solo-author lifecycle** (see [`../woodpecker-ui/lessons.md`](../woodpecker-ui/lessons.md) Top-of-file finding #1: solo-author Bevy UI crates show a ~15-month half-life). Linebender's collective-of-3-named-leads model is structurally more robust against any single contributor going inactive. But it's still small enough that a coordinated step-back from all three would dormant the project.

## License

**Apache-2.0** on both Xilem and Masonry workspace crates. **Not** the MIT-OR-Apache-2.0 dual that's typical in the broader Rust ecosystem (which AccessKit and most Bevy crates use). The single-Apache-2.0 license is enforced at the workspace level — every crate in the workspace inherits it via `license.workspace = true`.

**Implication for Buiy:**

- Buiy is dual-licensed MIT/Apache-2.0 (Bevy ecosystem convention).
- Code adopted from Xilem/Masonry into Buiy would need to either be re-licensed by the contributor or kept as Apache-2.0-only (incompatible-with-MIT-only consumers downstream).
- The single-license posture is **defensible** but **non-standard**. Apache-2.0 has patent-grant teeth that MIT lacks; some projects (like Slint) also single-Apache. The Rust ecosystem norm is dual, however.

This is a minor incompatibility, not a deal-breaker. For Buiy's purposes, Linebender code is *reference material*, not material we'd lift directly.

## Release cadence

Verified from git tags + release history:

- **Xilem 0.1.0** — 2024-05-07 (first crate published).
- **Masonry 0.2.0** — 2024-05-07 (alongside Xilem 0.1.0; version mismatch reflects masonry's earlier pre-history as Druid-internal code).
- **Xilem 0.3.0** — 2025-05-11 (one year later; cumulative; 500+ PRs).
- **Xilem 0.4.0 + Masonry 0.4.0** — 2025-10-29 (first version-aligned sibling release).

That's **3 minor releases in ~30 months**, averaging 10 months per minor. Compare to:

- Bevy: 4-month minor cadence (3 minors per year).
- AccessKit: irregular, sometimes 3 releases in 3 weeks then 6-month gaps.
- Cosmic-text: ~6-month cadence per minor.

Linebender's cadence is **slow but not pathological**. It tracks roughly with "annual major architectural cleanups." For Buiy planning purposes: counting on Xilem/Masonry hitting 1.0 within 12 months is not safe; 24 months is more realistic; 36 months is plausible.

## Distribution channels

- **crates.io** — primary. `xilem` 0.4.0 (7,596 lifetime DLs per pre-amble), `masonry` 0.4.0 (17,690 DLs). Masonry has 2.3× the downloads of Xilem; the gap reflects (a) Masonry is older as a crate (older release line), (b) some downstream consumers of Masonry don't use Xilem.
- **docs.rs** — autogenerated. Documentation is comprehensive at the trait level; less guidance at the application level.
- **GitHub releases** — annotated tags + release notes per major.
- **Linebender blog** — monthly progress posts (cadence dropped post-2024).
- **Linebender Zulip** — design discussion + RFC-shaped conversations.

There is **no formal RFC process** in the bevy-rfcs sense. Design discussion happens on Zulip + GitHub issues + blog posts. This matches Bevy's "lightweight RFC process" critique ([`../bevy-ui/lessons.md`](../bevy-ui/lessons.md) Avoid row "Lightweight RFC process") — Linebender carries the same risk.

## Documentation posture

- **README**: dense, links-heavy. Assumes reader is somewhat familiar with the Linebender ecosystem.
- **docs.rs**: trait-level documentation is good. Architectural overviews are scattered across Raph's blog rather than in-tree.
- **Examples**: chess, calculator, todo-MVC, Placehero (Mastodon client). The Placehero example is the most non-trivial.
- **Tutorials**: minimal. New users mostly reverse-engineer from examples + blog posts.
- **Migration guides**: per-release notes, no formal migration framework.

This is **typical pre-1.0 documentation** — not a deficiency relative to peers, but a real obstacle to evaluating "would I adopt this." Buiy's docs posture (specs in `docs/specs/`, plans in `docs/plans/`, prior-art folders for upstream dependencies) is more structured than Linebender's. The lesson is to *not* model Buiy's docs on Linebender's.

## Platform support — released

From the README + verified deps:

- **Desktop:** Linux (Wayland + X11), macOS, Windows, BSD systems. All require Vulkan or Metal for Vello.
- **Android:** Examples build as `cdylib`; AccessKit support is pre-1.0; no production reports.
- **iOS:** Not in scope at 0.4.0; AccessKit iOS adapter is also very young.
- **Web:** `xilem_web` (separate crate) uses the DOM directly. The Masonry-Vello-Parley path has no web target.

Buiy's platform support staging (foundation [`architecture.md § 2.9`](../../specs/2026-05-07-buiy-foundation/architecture.md)) is roughly the same shape: desktop in CI, mobile + web at manual release gate.

## What the governance shape means for Buiy

- **Do not depend on Xilem/Masonry.** Single-license, slow cadence, small bus factor, pre-1.0 maturity — none of those individually disqualifies, but together they cap the depth of dependency a serious project can take. Buiy's foundation already commits to this (the Linebender stack is reference material, not dependency).
- **Do study the substrate.** Vello, Parley, Color, Kurbo are independently published and individually mature *as substrate primitives*. The substrate-level adoption (Bevy 0.19's Parley migration; woodpecker_ui's Vello use) confirms the substrate has wider validation than the top-layer framework.
- **Do not model Buiy's docs on Linebender's.** Buiy's `docs/specs` + `docs/plans` + `docs/prior-art` structure is more rigorous; keep it that way.
- **Do calibrate Buiy's own cadence against this baseline.** Buiy is parallel to bevy_ui and tracks Bevy's 4-month cadence; that's faster than Linebender. Buiy's bus-factor planning needs to account for the fact that "named active leads" matter — see [`../woodpecker-ui/lessons.md`](../woodpecker-ui/lessons.md) Avoid row "Solo-maintainer abandonment lifecycle."
