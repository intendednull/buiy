**Status:** active
**Subject:** Slint — the consult-this-when-designing decision file: validates / avoid / borrow

# Lessons

This is the file Buiy spec authors should read first when a design question touches DSL authoring, retained-mode runtime shape, AccessKit producer wiring, embedded-grade allocation discipline, or commercial open-core licensing for Rust UI. Other files in this folder are evidence; this file is the synthesis.

## Validates

Choices Slint's experience confirms Buiy should keep making:

1. **AccessKit-first design.** Slint adopted AccessKit early (PR [#2865](https://github.com/slint-ui/slint/pull/2865) merged 2023-06-15, before Slint 1.1) and has shipped three years of production AccessKit integration on safety-critical industrial UIs (OTIV rail automation, KDAB consulting clients). The pattern works; the bugs are scoped (popup panics fixed in 1.9, list-view virtualization gaps documented, version-pin lag in issue [#8148](https://github.com/slint-ui/slint/issues/8148)). Buiy's AccessKit-first commitment ([`../../specs/2026-05-07-buiy-foundation/architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6) is well-trodden — see also [`accessibility.md`](accessibility.md) and [`../accesskit/ecosystem.md`](../accesskit/ecosystem.md) (Slint is a named verified adopter).

2. **Retained-mode runtime for production UI.** Slint is retained-mode in the textbook sense — properties carry bindings, the dependency graph re-evaluates lazily, the renderer redraws dirty regions. This is the right model for productivity-app UI; immediate-mode alternatives (egui) lose on text editing, IME, focus model, and accessibility-tree continuity. Buiy's parallel-to-bevy_ui retained-mode posture (foundation README goal 1) is validated by Slint's shipped-in-production track record.

3. **A declarative authoring layer above the runtime is a real product.** Slint's `.slint` DSL above its native object tree is precisely the shape Buiy's BSN aspires to — declarative authoring with property bindings, lifted above an underlying ECS / object-tree runtime. Buiy chooses ECS-and-BSN (not a DSL) but the *separation* (authoring layer above runtime) is the right architectural pattern. See [`architecture.md`](architecture.md) and [`dsl-language.md`](dsl-language.md).

4. **Property-binding declarative syntax composes cleanly with accessibility.** Slint's `accessible-role`, `accessible-label`, `accessible-description`, `accessible-checked`, `accessible-action-default` are item-level properties that the runtime maps to AccessKit `Node` fields ([`accessibility.md`](accessibility.md)). This is morally identical to Buiy's decomposed-component shape (`A11yRole`, `A11yLabel`, `A11yStates`, `A11yRelations`) — same separation of concerns, expressed differently. Both designs avoid the [`bevy_a11y::AccessibilityNode`](../bevy-a11y/) megacomponent pitfall ([`../bevy-ui/lessons.md`](../bevy-ui/lessons.md)).

5. **Standard widgets must pre-wire accessibility — the alternative is "third-party widgets are inaccessible by default."** Slint's `std-widgets.slint` ships `Button`, `CheckBox`, `LineEdit`, `Slider`, `TabWidget`, `ListView`, etc. with `accessible-role` pre-set and public properties (`text`, `checked`, `value`) routed to `accessible-*` fields. Custom widgets carry the burden explicitly. Buiy's widget-catalog commitment ([`../../specs/2026-05-07-buiy-foundation/media-and-widgets.md`](../../specs/2026-05-07-buiy-foundation/media-and-widgets.md)) — every APG-shaped Buiy widget ships with AccessKit wiring — is validated by Slint's experience that this is the only viable scope.

6. **Embedded discipline (allocation budgets, no-`std` paths, dirty-region rendering) is achievable in a Rust UI toolkit.** Slint runs on bare-metal STM32 / ESP32 / Cortex-M devices with RGB565 framebuffers, no GPU, and bounded heap usage ([`embedded-focus.md`](embedded-focus.md)). This validates that performance-budget discipline in Buiy's perf work is realistic, even if Buiy targets desktop-and-mobile-not-MCU.

7. **Founder competence is load-bearing for DSL / runtime quality.** Olivier Goffart (Qt moc maintainer) and Simon Hausmann (QtQml lead) bring multi-decade depth on property systems and reactive bindings. A Buiy reactivity sub-spec (foundation README § 5 open question — observers+change-detection v1, signals/computed/effects deferred) that ever lifts to a signals layer will need equivalent depth. Don't dismiss this as "we'll figure it out" — Slint's binding evaluator is what years of QtQml experience looks like.

8. **Open-core commercial licensing is *viable* for a UI library — but it's a procurement gate, not a `cargo add`.** SixtyFPS GmbH funds Slint development via commercial-license revenue from embedded customers. This is genuinely a working business model; the technical product is real ([`history.md`](history.md), [`governance-and-distribution.md`](governance-and-distribution.md)). Buiy explicitly *rejects* this model in favor of MIT/Apache permissive — but "open-core is non-viable" is not the lesson; "open-core makes Buiy's audience inaccessible" is.

## Avoid

Slint pitfalls Buiy has mitigations for or chooses to design around:

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **GPL + commercial dual gate.** Slint ships `GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0`. The royalty-free option excludes embedded/mobile; commercial license is mandatory for proprietary embedded. Locks out open-source consumers under permissive licenses (MIT, Apache-2.0, BSD) from mixing Slint into their stack. | [`governance-and-distribution.md`](governance-and-distribution.md), [`open-problems.md`](open-problems.md) | Buiy ships under **MIT OR Apache-2.0** dual-permissive ([foundation README](../../specs/2026-05-07-buiy-foundation/README.md)), matching Bevy's licensing. No commercial license track; no royalty-free terms to negotiate. |
| **DSL as the *primary* authoring layer.** Slint's `.slint` files are the source of truth; host language is glue. This locks out programmatic UI construction (game inventory grids from runtime data, IDE tree views, dynamic forms) — those fight the AOT-compiled-DSL grain. `slint-interpreter` exists but loses compile-time type checks. | [`architecture.md`](architecture.md), [`dsl-language.md`](dsl-language.md), [`open-problems.md`](open-problems.md) | Buiy makes **ECS + BSN equally first-class**. The ECS world is the source of truth; BSN is one authoring surface among others (direct Rust spawning, runtime-constructed entities, hot-reloaded `.bsn` files). No single authoring layer dominates. |
| **`.slint`-vs-Rust context-switch cost.** Editor support for two languages in one project; refactoring across the DSL boundary is manual; stack traces surface from generated code; LSP for `.slint` is good but not equal to rust-analyzer. | [`dsl-language.md`](dsl-language.md), [`open-problems.md`](open-problems.md) | Buiy keeps **everything in Rust**. BSN authoring uses Rust syntax (macro or `.bsn` files that parse as Rust-compatible). No two-language context switch. Tradeoff: no Live Preview hot-reload of equivalent polish without explicit asset-pipeline work. |
| **Embedded focus shapes feature scope.** Slint prioritizes MCU-friendly features; desktop-readiness gaps (rich text, modal windows, system tray, drag-and-drop, real-OS popups) lag because embedded customers don't need them. | [`embedded-focus.md`](embedded-focus.md), [`open-problems.md`](open-problems.md), [Making Slint Desktop-Ready](https://slint.dev/blog/making-slint-desktop-ready) | Buiy targets **desktop + mobile + game with web-platform feature parity** ([foundation README goal 1](../../specs/2026-05-07-buiy-foundation/README.md)). MCU explicitly out of scope. Feature scope is driven by web-parity, not by allocation discipline. |
| **Language-binding parity drift.** Slint's compiler emits Rust, C++, JS/Node, Python. Feature parity across bindings drifts (Python is newest beta, JS got a 3.0 napi-rs rework in 1.16, async semantics differ per binding). Maintaining a four-language matrix is a continuing cost. | [`architecture.md`](architecture.md), [`open-problems.md`](open-problems.md) | Buiy is **Rust-only**. No cross-language binding maintenance. Tradeoff: no out-of-the-box C++/JS/Python consumers, which is fine because Bevy is Rust-only. |
| **AccessKit version-pin drift.** Slint stays a few `accesskit_winit` minor releases behind upstream; issue [#8148](https://github.com/slint-ui/slint/issues/8148) flags 6–12-month upgrade-blocked windows. Each `accesskit_winit` major release touching event-loop ownership is a Slint integration project. | [`accessibility.md`](accessibility.md), [`open-problems.md`](open-problems.md) | Buiy's policy: **AccessKit major release between Bevy minors triggers a Buiy patch release** with explicit semver ([foundation README § 5 open question](../../specs/2026-05-07-buiy-foundation/README.md)). Plan for upgrade-blocked windows; don't pretend they don't happen. |
| **Stewardship concentration in single vendor.** SixtyFPS GmbH is the sole core-changes contributor at scale. No foundation, no charter, no formal RFC process; funding is commercial-license revenue. Bus factor is acknowledged in [`governance-and-distribution.md`](governance-and-distribution.md). | [`governance-and-distribution.md`](governance-and-distribution.md), [`open-problems.md`](open-problems.md) | Buiy plans **community / foundation-style governance** — no commercial revenue stream; multiple maintainer attention surface; tradeoff is no full-time funded maintainers. Different structural risk, taken deliberately. |
| **Popups, modals, drag-and-drop, system tray are listed desktop-readiness gaps.** Slint's popups render inside the host window (clip instead of overflow); `Dialog` is a styled component not OS-modal; cross-window drag-and-drop is unsupported. | [Making Slint Desktop-Ready](https://slint.dev/blog/making-slint-desktop-ready), [`open-problems.md`](open-problems.md) | Buiy's [`buiy-window-and-surface-design`](../../specs/2026-05-07-buiy-foundation/README.md) sub-spec must address these explicitly. Slint's gap list is a Buiy checklist of must-haves. |
| **Theme system is compile-time-bound styles, not runtime token cascade.** Slint's four styles (Fluent / Material / Cupertino / Cosmic) are build-time selections; no CSS-custom-property equivalent, no global semantic-token cascade. | [`open-problems.md`](open-problems.md), [`dsl-language.md`](dsl-language.md) | Buiy commits to **semantic tokens with OS-preference binding** ([`buiy-theme-tokens-design`](../../specs/2026-05-07-buiy-foundation/README.md)). Runtime token mutation; OS preferences (forced-colors, reduced-motion, prefers-contrast) wired automatically. |

## Borrow

Specific Slint primitives, patterns, and tooling shapes Buiy should adopt or adapt:

1. **Property-direction qualifiers (`in` / `out` / `in-out` / private).** Slint's per-property visibility qualifiers ([`dsl-language.md`](dsl-language.md)) are a clean property-API design — components have an enforced public-input / public-output / private contract. Buiy widgets in [`../../specs/2026-05-07-buiy-foundation/media-and-widgets.md`](../../specs/2026-05-07-buiy-foundation/media-and-widgets.md) should adopt this discipline as a convention: every component-level field is `pub` with a documented input/output role, no private setters, decomposed by concern.

2. **AccessKit producer-integration patterns from PR [#2865](https://github.com/slint-ui/slint/pull/2865).** Slint's per-window `accesskit_winit::Adapter` ownership, the AccessKit `Tree` construction from the live UI tree, `TreeUpdate` push on property change, and the `accessible-role` enum → AccessKit `Role` mapping are all directly borrowable for Buiy's AccessKit-adapter design ([`../accesskit/`](../accesskit/) + [`accessibility.md`](accessibility.md)). The integration shape is the same; Buiy expresses it in ECS components rather than DSL properties.

3. **The states + transitions animation model.** Named states with property settings + named transitions between them (`states [ pressed when ...: { ... } ] transitions [ in pressed: { animate ... } ]`) is a clean declarative state-machine UX primitive ([`dsl-language.md`](dsl-language.md)). Buiy's `buiy-animation-design` sub-spec ([foundation README sub-spec roadmap](../../specs/2026-05-07-buiy-foundation/README.md)) should consider this as one of the surfaces, not just keyframe / spring primitives.

4. **The Slint Live Preview tooling pattern.** A WASM-rendered preview of the authoring source, hot-reloading on save, embedded in the editor (VSCode + standalone web editor at slint.dev/editor) is the gold standard for Rust-ecosystem UI tooling. Buiy's [`buiy-devtools-design`](../../specs/2026-05-07-buiy-foundation/README.md) sub-spec lists inspector / overlay / contrast checker / focus visualizer / theme editor — adding "hot-reload a `.bsn` file with WASM-rendered preview" is the moral equivalent and would be a clear differentiator.

5. **Compile-time DSL → runtime objects compilation pipeline (lifted to BSN-compile-time codegen).** Slint's `slint!` macro / `slint_build` codegen produces typed Rust structs that wrap native runtime objects ([`architecture.md`](architecture.md)). BSN faces the equivalent codegen problem; Slint's pipeline (parse → IR → optimize → emit Rust) is a useful study target for `buiy-bsn-integration-design`.

6. **Embedded-grade allocation discipline (`no_std` paths, dirty-region partial updates).** Even though Buiy's primary targets are desktop and mobile (not MCU), Slint's allocation discipline ([`embedded-focus.md`](embedded-focus.md)) is the right *engineering culture* — bounded heap, dirty-region rendering, no per-frame allocations in hot loops. Buiy's perf budget thinking in [verification.md](../../specs/2026-05-07-buiy-foundation/verification.md) (CI gate #14) benefits from the same discipline.

7. **Triple-licensing transparency.** Slint clearly documents its commercial path: `LicenseRef-Slint-Royalty-free-2.0` and `LicenseRef-Slint-Software-3.0` are named in crates.io metadata; the royalty-free terms are published; the procurement path is explicit. Buiy is permissive-only and has no commercial path, but **the lesson is that license transparency matters** — when Buiy documents its MIT/Apache stance, it should equally clearly say "no commercial license track, no enterprise tier, no royalty terms" so consumers don't wonder.

8. **Property / callback separation in widget contracts.** Slint widgets declare `in property <T>` for inputs, `out property <T>` for outputs, `callback name(args)` for events ([`dsl-language.md`](dsl-language.md)). The split — data-flow properties versus event-emission callbacks — is clean. Buiy widgets in the catalog should adopt the same conceptual split: data-bearing components (`Value`, `Selection`, `Text`) versus event-emission observers / triggers. This is the BSN-friendly equivalent of `in property` versus `callback`.

9. **Per-window state isolation pattern.** Slint owns one `accesskit_winit::Adapter` per window; cross-window concerns (drag-and-drop, focus transfer, popup escape) are explicitly scoped and documented as gaps. Buiy's [`buiy-window-and-surface-design`](../../specs/2026-05-07-buiy-foundation/README.md) sub-spec should adopt the per-window-adapter pattern from day one — same shape, more rigorous on the inter-window edges Slint left for later.

10. **Language Server Protocol DSL tooling (slint-lsp).** The `slint-lsp` binary supports any editor that speaks LSP (Vim, Emacs, Helix, Sublime, VSCode), not just one editor. For Buiy's BSN tooling, a `buiy-bsn-lsp` that's editor-agnostic is the right model — don't lock tooling to one editor. Slint's LSP shape (autocomplete, go-to-definition, refactoring, diagnostics, embedded Live Preview hooks) is a complete reference.
