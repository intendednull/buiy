**Status:** active
**Subject:** bevy_lunex — Validates / Avoid / Borrow decisions for the Buiy foundation

# Lessons for Buiy

This is the consult-this-when-designing decision file. Other files in this corpus are evidence; this file is the synthesis. Three sections — **Validates** (Buiy choices that bevy_lunex's experience confirms), **Avoid** (pitfalls to mitigate), **Borrow** (primitives worth studying).

The single most important framing: bevy_lunex is the only third-party Bevy UI project with the **same parallel-stack posture as Buiy** — no `bevy_ui` dependency, no `bevy_a11y` dependency, direct integration with the substrate crates. Its successes are the clearest evidence that the parallel-stack idea is shippable; its failures are the clearest evidence of what *not* to do once you commit to it. Read this file with that frame.

## Validates

These Buiy design choices are confirmed by bevy_lunex's experience:

- **Parallel-stack as a viable architectural posture (foundation [README goal 4](../../specs/2026-05-07-buiy-foundation/README.md) and [architecture.md § 2.1](../../specs/2026-05-07-buiy-foundation/architecture.md)).** bevy_lunex has shipped 28 versions over 2.7 years against 8 Bevy minors without depending on `bevy_ui` or `bevy_ui_render`. The parallel-stack idea is **not theoretical** — it has a production prior art. The "you can do this" question is settled; the open question is "what do you do *with* the freedom that parallel-stack creates" (see [`architecture.md`](architecture.md), [bevy-ui lessons.md "Parallel-stack rationale"](../bevy-ui/lessons.md)).

- **Direct dependency on `bevy_sprite` + `bevy_text` + `bevy_picking` + `cosmic-text` (foundation [architecture.md § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md)).** bevy_lunex's `Cargo.toml` validates that this exact substrate stack is consumable from a parallel UI library. Buiy's planned dependencies overlap heavily with bevy_lunex's verified-working set. See [`distribution.md`](distribution.md) § "Cargo dependencies."

- **3D-anchored UI as a first-class capability ([cross-cutting.md § 3.17](../../specs/2026-05-07-buiy-foundation/cross-cutting.md)).** bevy_lunex's worldspace-UI feature is the clearest evidence the use case is real in actual Bevy games — `UiRoot3d` + `UiMeshPlane3d` covers HUDs, damage numbers, in-world terminals, diegetic menus. The pattern coverage is real and demonstrated in Bevypunk. Buiy's `buiy_3d` sub-spec inherits the demonstrated use cases without needing to justify them de novo. See [`3d-and-worldspace.md`](3d-and-worldspace.md).

- **General `Transform` as the position primitive for 3D-anchored UI ([cross-cutting.md § 3.17](../../specs/2026-05-07-buiy-foundation/cross-cutting.md)).** bevy_lunex demonstrates that 3D-anchored UI becomes free the moment your component model uses Bevy's general `Transform` instead of a bespoke UI-only transform. bevy_ui's `UiTransform` (2D-only, Bevy 0.17+) closes off this option; bevy_lunex's choice keeps it open. Buiy's foundation explicitly notes "no `UiTransform` / `Transform` divergence to bridge" — that decision is the same one bevy_lunex made and validates. See [`architecture.md`](architecture.md) § "The transform-based layout model."

- **`bevy_picking` backend registration as the hit-testing primitive (foundation [interaction sub-spec roadmap](../../specs/2026-05-07-buiy-foundation/README.md)).** bevy_lunex registers its own `bevy_picking` backend in `PreUpdate::PickingSystems::Backend` (verified in `crate/src/picking.rs`). The backend handles both 2D and 3D UI in a single ray-vs-plane algorithm with z-sorting. Buiy's planned input-events sub-spec uses the same approach. The mechanism is well-trodden. See [`3d-and-worldspace.md`](3d-and-worldspace.md) § "Hit-testing of 3D-anchored UI", and cross-link [bevy-ui lessons.md Borrow #5](../bevy-ui/lessons.md).

- **The "don't extend bevy_ui, replace it" decision ([cross-cutting.md § 3.18](../../specs/2026-05-07-buiy-foundation/cross-cutting.md)).** bevy_lunex demonstrates users will adopt a parallel UI stack when given a reason — in bevy_lunex's case, worldspace UI is the reason and 40K downloads is the receipt. Extending bevy_ui (the `sickle_ui` choice) is a different bet with a different upside. Buiy's commitment to per-window coexistence rather than tree-mixing or layered-on-bevy_ui is validated by bevy_lunex's adoption profile in its niche.

- **Composing per-state property variants for layout/color transitions.** bevy_lunex's `UiLayout` and `UiColor` components carry per-state variants (base / hover / clicked / selected) that the solver lerps between via a normalized state value. This is a clean shape — public-fielded, declarative, observable. Buiy's planned animation sub-spec can adopt the same per-property + per-state shape as the foundation primitive, layered with reduced-motion gating and richer interpolation. See [`layout.md`](layout.md) § "Animations and transitions."

- **System-set partitioning around layout (foundation [architecture.md § 2.8](../../specs/2026-05-07-buiy-foundation/architecture.md) `BuiySet::Layout` → `BuiySet::Render`).** bevy_lunex uses `UiSystems::PreCompute → UiSystems::Compute → UiSystems::PostCompute` in `PostUpdate`. The labeled-system-set pattern is well-trodden in shipping Bevy UI code; Buiy's named sets follow the same architectural posture.

## Avoid

Pitfalls drawn from bevy_lunex's experience, with Buiy's mitigation.

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **Transform-based positioning instead of Taffy.** bevy_lunex's defining bet — UI nodes as `Transform` entities with anchored/percent layout — gives up flexbox, CSS Grid, block flow, margin collapse, intrinsic sizing, `min/max-width/height`, and logical properties. The maintainer's own book says it bluntly: *"lacks flexbox-like layout functionality"* and *"poor fit for desktop application UIs."* | [`layout.md`](layout.md) § "Comparison to Taffy / CSS box model"; [`architecture.md`](architecture.md) § "The transform-based layout model"; [`critiques.md`](critiques.md) § "Transform-based vs Taffy-based: the honest assessment." | Buiy commits to Taffy directly per foundation [architecture.md § 2.2](../../specs/2026-05-07-buiy-foundation/architecture.md). Taffy is production-proven (3.5 years in `bevy_ui`), provides flexbox + CSS Grid + block, and ships container queries / subgrid as upstream advances. The "we get worldspace UI by paying the layout-engine porting cost in Taffy + general `Transform`" tradeoff is the right one for Buiy's "game and app, both" scope. |
| **Ship without AccessKit integration.** bevy_lunex has **zero** accessibility — no `accesskit` dep, no `bevy_a11y`, no role/label/state/relation primitives, no focus ring, no screen-reader path, no live regions, no keyboard-only navigation guarantees. A bevy_lunex UI **cannot** conform to WCAG 2.2 at any conformance level. 2.7 years in and no open issue tracks the gap. | [`open-problems.md`](open-problems.md) § "Accessibility integration (AccessKit)"; [`critiques.md`](critiques.md) § "WCAG / a11y posture." | Buiy is AccessKit-first from day one per foundation [architecture.md § 2.6](../../specs/2026-05-07-buiy-foundation/architecture.md) and [accessibility.md](../../specs/2026-05-07-buiy-foundation/accessibility.md). Decomposed `A11yRole` / `A11yLabel` / `A11yDescription` / `A11yStates` / `A11yRelations` from day one, ACCNAME 1.2, per-widget WCAG SC mapping. bevy_lunex is the prior-art evidence that "we'll add accessibility later" never gets done. |
| **"Blazingly fast" claims without published benchmarks.** bevy_lunex's crate description repeats *"Blazingly fast retained UI layout engine"* on every README iteration. No `benches/` directory, no `criterion` setup, no `bevy-bencher` participation, no comparison against `bevy_ui` / `bevy_egui` / `sickle_ui` / `woodpecker_ui`, no scaling number at 1000+ nodes. The retained-mode argument is plausible but unverified. | [`critiques.md`](critiques.md) § "The 'blazingly fast' marketing claim"; [`open-problems.md`](open-problems.md) § "Performance benchmarks." | Buiy's verification harness ([verification.md](../../specs/2026-05-07-buiy-foundation/verification.md)) includes **perf baselines per fixture** as a CI gate. The fixture set explicitly enumerates productivity-app scenarios at 1000+ nodes. Buiy ships measurable claims, not marketing language. If Buiy uses comparative language ("faster than X"), it links to the bench. |
| **Solo maintainer for a structurally complex UI library.** Bus factor 1, no Bevy Foundation backing, no funding, no co-maintainer, no documented succession plan. Two release gaps of 4–5 months around the maintainer's university semesters. The Bevy 0.17 bump (0.5.0, October 2025) only happened because an external contributor (S4ndf1re, PR #122) stepped up. The kayak_ui precedent (similar shape, archived 2024 at ~900 stars) is the cautionary tale. | [`governance.md`](governance.md); [`distribution.md`](distribution.md) § "Release cadence"; [`critiques.md`](critiques.md) § "Maintainer bandwidth / bus factor." | Document **fork-strategy contingencies** in Buiy's release notes from day one. Buiy's modular subsystem split (foundation [architecture.md § 2.8](../../specs/2026-05-07-buiy-foundation/architecture.md): `buiy_core`, `buiy_text`, `buiy_widgets`, etc.) reduces single-author-risk: a contributor can take on one crate without owning the whole stack. Treat the "solo maintainer + ambitious scope" model honestly — it is the same risk Buiy itself runs as a single-author project. Plan for it. |
| **No theme system / no tokens.** bevy_lunex ships no `Theme` component, no token system, no semantic-color palette, no spacing scale, no variants (light / dark / high-contrast), no OS-pref binding. Bevypunk demonstrates a cohesive visual identity by hand-coded styles across the project; replicating the look requires copying styling code, not consuming a token bundle. | [`styling.md`](styling.md) § "Themability"; [`open-problems.md`](open-problems.md) § "Theme system / token primitives." | Buiy's token-based design system is **foundational, not bolt-on**, per foundation [architecture.md § 2.5](../../specs/2026-05-07-buiy-foundation/architecture.md). Themes are hot-reloadable assets, components consume semantic tokens, OS preferences (`prefers-color-scheme`, `prefers-contrast`, `forced-colors`, `prefers-reduced-motion`) surface as a `UserPreferences` resource. WCAG 2.2 AA contrast is by construction. The contrast linter validates custom themes at load and in CI. |
| **No flexbox / no grid in a 2026 UI library.** Three layout primitives total (`Window`, `Solid`, `Boundary`) — no flow, no gap, no grid track sizing, no flex-basis, no `min/max-width/height`, no margin collapse. Every layout is composed by hand from anchored rectangles. The maintainer's own book confirms: *"lacks flexbox-like layout functionality."* | [`layout.md`](layout.md) § "Layout primitives"; [`open-problems.md`](open-problems.md) § "3D-anchored UI vs 2D UI: ergonomics balance." | Buiy commits to full CSS layout via Taffy per foundation [visuals.md § 3.2](../../specs/2026-05-07-buiy-foundation/visuals.md) — block, flex, grid, multi-column (E-tier), container queries, anchor positioning, logical properties, writing modes, sticky positioning, overflow + scroll-snap. The full surface is named in the foundation feature catalog. |
| **Pin tightly to Bevy minor versions with no LTS, no overlap.** One bevy_lunex minor per Bevy minor. The 0.2 → 0.3 transition was a complete rewrite (Feb 2025, Bevy 0.15). Subsequent minors are smaller but still breaking — renamed components, restructured plugins, new required-components, observer migrations. Cargo feature names also drift between minors with no semver guarantee. | [`history.md`](history.md) § "Bevy version coupling per minor"; [`distribution.md`](distribution.md) § "Bevy version coupling (the migration tax)." | Buiy commits to **rolling-latest-stable Bevy** per foundation [README goal 5](../../specs/2026-05-07-buiy-foundation/README.md) and [architecture.md § 2.9](../../specs/2026-05-07-buiy-foundation/architecture.md), with **explicit migration events** documented at each Bevy minor. Buiy does not promise multi-version compatibility but does promise that each migration is named, scoped, and documented in release notes. Cargo feature names are stable across Buiy minors; if they have to change, it is called out as a breaking change. |
| **No flagship game = no UX battle-testing.** 2.7 years, 40K downloads, 913 stars — and **zero** publicly-named commercial game ships with bevy_lunex outside of Bevypunk (the maintainer's own demo). No Steam release, no major itch.io publication, no recognizable studio adoption. The absence is not proof bevy_lunex *cannot* ship a game; it is empirical evidence that 2.5+ years has not been enough to produce a market validation event. | [`ecosystem.md`](ecosystem.md) § "Production usage (verified)"; [`critiques.md`](critiques.md) § "The 'no flagship game' question." | Buiy's verification harness ([verification.md](../../specs/2026-05-07-buiy-foundation/verification.md)) requires both **productivity-app fixtures** (1000+ nodes, forms, virtualized lists, full keyboard nav) **and game scenarios** (HUDs, in-world UI, gamepad nav). Buiy commits to "Game and app, both" per foundation [README goal 6](../../specs/2026-05-07-buiy-foundation/README.md) — and doesn't outsource the proof to shipping titles. If after 2 years Buiy has no shipped reference application, that is a signal to take seriously, not a metric to soft-pedal. |
| **Documentation drift between book and repo.** The Lunex Book targets v0.4+ and the maintainer notes *"don't expect updates during the semester."* The book documents architecture and primitives; canonical patterns for common UI tasks (modal dialogs, scrolling lists, tab containers, form validation, focus rings, drag-and-drop) are not in the book and are reverse-engineered from Bevypunk. Open issues #10 (DSL) and #11 (hot reload) have been open since 2023-11 with no design doc. | [`critiques.md`](critiques.md) § "Documentation completeness"; [`open-problems.md`](open-problems.md) § "Hot-reload / asset reload." | Buiy's docs/README.md catalog is the **canonical source of truth** per [docs/specs/2026-05-07-docs-organization-design.md](../../specs/2026-05-07-docs-organization-design.md). Every Buiy subsystem ships with its own spec, plan, and verification fixture. Long-form book chapters are derived from specs, not vice versa. |
| **Bus factor 1 + university-student maintainer = abandonment risk.** The kayak_ui precedent (StarArawn, archived 2024 at ~900 stars) is the cautionary tale: ambitious third-party UI kit, single maintainer steps back, no successor emerges, project archives. bevy_lunex is on the same trajectory and has openly carried the "university student" disclosure for its entire life. | [`governance.md`](governance.md) § "Bus factor analysis"; [`critiques.md`](critiques.md) § "Maintainer bandwidth." | Buiy ships with clear governance + reflection-registration ergonomics. Crate-split design (`buiy_core` / `buiy_text` / `buiy_widgets` / `buiy_animation` / etc. per foundation [architecture.md § 2.8](../../specs/2026-05-07-buiy-foundation/architecture.md)) reduces single-author risk per subsystem. Treat bevy_lunex as a design influence, not a long-term runtime dependency. |
| **Cargo feature-flag churn between releases.** `wasm` first appeared post-0.3. `text3d` first appeared at 0.3.2, became default-on at 0.5+. Older audio features (Kira integration from 0.2.0) were removed during the 0.3 rewrite. Consumers cannot `bevy_lunex = "0.X"` and trust their `[features]` line on the next minor. | [`distribution.md`](distribution.md) § "Cargo features"; [`critiques.md`](critiques.md) § "Cargo feature-flag churn." | Buiy's foundation does not yet enumerate Cargo features (a `buiy-distribution-design` sub-spec will). The rule borrowed from this lesson: **feature names are part of the public API** and changes are breaking. Each Buiy release names its feature set in release notes; deletions and renames require a major bump. |

## Borrow

Concrete primitives worth studying and adapting:

1. **`UiLayoutType` 3-variant enum for content-fitting modes.** bevy_lunex's `Window` / `Solid` / `Boundary` enum is a clean, small shape for "how do I fit this rect to its parent." `Solid` in particular — aspect-ratio-locked with `Fit` / `Fill` / `HorFill` / `VerFill` scaling and `align_x` / `align_y` placement — is exactly the API Buiy will want for image fitting, video fitting, and "preserve aspect ratio across window sizes" container queries. Borrowable as a value type for Buiy's container-query and `object-fit` analogs, not as the whole layout model. See [`layout.md`](layout.md) § "Layout primitives" and [`component-model.md`](component-model.md) § "The `UiLayoutType` enum."

2. **First-class 3D-anchored UI via Transform + `UiMeshPlane3d`.** The mechanism is small: a marker component (`UiRoot3d`) declares "this tree lives in 3D"; a second marker (`UiMeshPlane3d`) requests a quad mesh sized to the resolved `Dimension`; parent the root under any 3D entity and the UI tracks it. No projection step, no separate render pass, no "convert UI coords to 3D coords" math. Buiy's `buiy_3d` sub-spec ([cross-cutting.md § 3.17](../../specs/2026-05-07-buiy-foundation/cross-cutting.md)) can borrow the marker-component pattern and the parent-under-3D-entity hierarchy directly. See [`3d-and-worldspace.md`](3d-and-worldspace.md).

3. **`bevy_picking` as the hit-testing primitive for parallel UI.** bevy_lunex registers a single picking backend that handles **both** 2D and 3D UI by ray-vs-plane intersection in node-local coordinates, with `radsort`-based z-sorting and `Pickable::should_block_lower` for opaque-UI semantics. The backend lives in `PreUpdate::PickingSystems::Backend`. Buiy's input-events sub-spec borrows the same shape: one backend, both 2D and 3D modes, `bevy_picking` priority configured per-window. See [`3d-and-worldspace.md`](3d-and-worldspace.md) § "Hit-testing of 3D-anchored UI" and cross-link [bevy-ui lessons.md Borrow #5](../bevy-ui/lessons.md).

4. **`UiLayoutRoot` as the marker entity for layout-tree roots.** bevy_lunex's separation between "marker component for the root" (`UiLayoutRoot`) and "the rest of the tree is normal Bevy hierarchy" is a clean shape. There is no top-level `UiTree` resource; the entity hierarchy is the layout tree. Buiy's planned layout subsystem can adopt the same root-marker pattern: a `BuiyRoot` (or similar) component marks the entity whose subtree is the layout boundary, and standard `Children` / `Parent` propagate. See [`architecture.md`](architecture.md) § "The 'UI tree' pattern."

5. **The Lunex Book documentation pattern.** Long-form prose + per-feature chapters + inline rustdoc, all in one location. The book is openly versioned-against-minor (currently 0.4+, knowingly drifting from 0.6.0) and openly maintainer-bandwidth-constrained. Buiy's `docs/` structure (specs + plans + reports + prior-art) is a different choice for a different reason, but the Lunex Book demonstrates that long-form documentation **for a parallel UI library** is non-optional and that maintainer-bandwidth constraints determine how current the docs stay. Plan Buiy's docs as a first-class deliverable, not an afterthought ([`critiques.md`](critiques.md) § "Documentation completeness").

6. **Custom render path through `bevy_sprite` and `bevy_text`.** bevy_lunex ships **no rendering code of its own** — `bevy_sprite` draws sprites, `bevy_text` draws text, `bevy_pbr` draws 3D meshes, optionally `bevy_rich_text3d` draws 3D text. The library is purely a layout solver writing `Transform` and `Dimension`. This is the load-bearing simplification that makes worldspace UI free; it is also the structural constraint that prevents bevy_lunex from delivering `backdrop-filter`, `mix-blend-mode`, true top-layer compositing, non-rect clipping. Buiy rejects this tradeoff — Buiy owns the render pipeline directly per foundation [architecture.md § 2.3](../../specs/2026-05-07-buiy-foundation/architecture.md) — but the bevy_lunex mechanism is the cleanest existing demonstration of "if you don't need rich compositing, you can skip writing a renderer entirely." Useful reference for future "minimal Buiy" or "Buiy-3D-only" configurations. See [`architecture.md`](architecture.md) § "Render path: there is no render pipeline."

7. **Worldspace UI components that attach to 3D entities.** The pattern is small and well-defined: spawn `UiRoot3d` as a child of any 3D entity, attach layout children with `UiMeshPlane3d`, and the UI tracks the parent's `GlobalTransform`. Despawn the parent, the UI goes. The hit-testing through the picking backend works for both screen-space and worldspace nodes without special-casing. This is the directly-borrowable model for Buiy's `buiy_3d` worldspace UI sub-spec. See [`3d-and-worldspace.md`](3d-and-worldspace.md) § "Worldspace UI."

8. **The `bytestring-net` framing — small focused org, not Bevy Foundation.** bevy_lunex demonstrates that a parallel-UI project can ship without Foundation membership, board oversight, or funding — but also that the absence of those things produces irregular cadence and bus factor 1. Buiy's structural choice (single-author, no Foundation) is the same. The lesson is to acknowledge the resemblance honestly and plan succession explicitly. See [`governance.md`](governance.md).

9. **The "lacks flexbox by design" honesty.** The Lunex Book explicitly states what is **not** in scope: *"No pre-built input components"*, *"Poor fit for desktop application UIs"*, *"Lacks flexbox-like layout functionality"*, *"Not optimized for rapid development iteration."* This is the right tone for any UI library that makes deliberate exclusions. Buiy's foundation already uses the same pattern — explicit `O` tier (out, with reason) for excluded features per foundation [README "Tier legend"](../../specs/2026-05-07-buiy-foundation/README.md). bevy_lunex validates the practice.

10. **The parallel-stack PR pattern (one-PR-per-Bevy-minor migration).** S4ndf1re's PR #122 for the Bevy 0.17 bump is a clean single-PR migration: bump deps, fix breaking-change call sites, run examples, ship a minor. Buiy's planned rolling-stable-Bevy posture per foundation [architecture.md § 2.9](../../specs/2026-05-07-buiy-foundation/architecture.md) can borrow the pattern: each Bevy minor is a single labeled migration PR with explicit before/after diff, named in release notes. See [`history.md`](history.md) § "0.5.0: contributor-driven Bevy 0.17 bump."

## How to use this file

When designing a Buiy feature:

1. **Find the row in `Avoid`** that names a pitfall close to your design. Read the linked file for the original incident. Cross-link to the bevy-ui prior art if the same pitfall appears there too.
2. **Find the entry in `Borrow`** that names a primitive close to what you're designing. Read the linked file to understand the bevy_lunex shape, then adapt for Buiy's component model (decomposed, public-fielded, observable, reflection-registered, token-aware, AccessKit-aware).
3. **Promote any decision into a Buiy spec** under `docs/specs/` — this file is for capturing what we learn from bevy_lunex, not for encoding Buiy's own decisions.
