# Lessons for Buiy

This is the **consult-this-when-designing decision file**. The other files in this corpus are evidence; this file is the synthesis. Three sections — **Validates** (Buiy choices that RmlUi's 18-year cumulative experience confirms), **Avoid** (pitfalls to mitigate), **Borrow** (primitives worth studying and adapting).

## Top-level framing

RmlUi is the **closest open-source precedent for "HTML+CSS in a game engine"** that Buiy targets. It has been doing what Buiy aims for — web-platform-like UI in a non-web embedder context — for 15+ years (libRocket era 2008–2014, RmlUi era 2018–present). The lessons are deep and load-bearing.

But the **structural choices differ**: RmlUi is C++, single-maintainer, no foundation, no accessibility, custom DSL diverging from CSS spec, own-built layout engine. Buiy is Rust, parallel-stack within Bevy + Bevy Foundation governance, AccessKit-first, web-spec-fidelity-committed, Taffy-substrate-borrowing. The lessons read as **what RmlUi proves is shippable, what RmlUi made permanent commitments on that Buiy chose differently, and what concrete primitives RmlUi designed well enough to study.**

## Validates

These Buiy design choices are confirmed by RmlUi's experience:

- **The "HTML+CSS in a game engine" pattern is shippable as open source.** 15+ years of libRocket + RmlUi production use across indie + AA games (Nightdive's KEX engine, Cfx.re's Alchemist, Unvanquished, ROSE Online, TruckersMP) is the empirical proof. Buiy's foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 1 web-platform-parity goal is not a green-field bet — it is a re-bet on a proven pattern.
- **An RML+RCSS-flavored subset of HTML/CSS is sufficient for game UI.** 18 years of customers shipping production HUDs / menus / settings / minimaps / inventories / overlays on RCSS proves the *minimum viable surface*. Buiy's foundation [`visuals.md`](../../specs/2026-05-07-buiy-foundation/visuals.md) tier list (**F** + **C** features) is a strict superset of RmlUi's shipped surface — the foundation is buying real ground covered by an existing project, plus the deltas (Grid, container queries, anchor positioning, modern color, a11y).
- **The embedder-interface pattern is the right shape for engine integration.** RmlUi's five interfaces (Render / System / File / FontEngine / TextInputHandler) cleanly separate library responsibilities from embedder responsibilities, and have survived 18 years of GPU API churn (GL2 → GL3 → Vulkan → DX12 → SDL_GPU) and platform churn (Windows / Linux / macOS / Android / iOS / Switch). For Buiy's foundation open question [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 *"Render-to-texture surface API contract"* — RmlUi's embedder pattern is the canonical reference.
- **Spatial controller navigation is solved.** RmlUi (and libRocket before it) shipped console-controller UI navigation since the early 2010s. Buiy's spatial-gamepad-nav (foundation [`accessibility.md`](../../specs/2026-05-07-buiy-foundation/accessibility.md) keyboard interaction + spatial nav patterns) is consistent with 15+ years of industry practice, not novel.
- **Open-source MIT positioning is commercially viable.** RmlUi is MIT-licensed, royalty-free, commercially-unrestricted, and has a real (if small) commercial user base. Buiy's MIT-OR-Apache-2.0 dual permissive license shares this positioning with the additional patent-grant coverage. **The proprietary-cousin model (NoesisGUI tiered licensing) is not the only path** — open-source can ship game UI middleware.
- **Animations, transitions, transforms, filters, masks, box-shadow are achievable** in a non-browser game UI library. RmlUi 3.x added animations / transitions / transforms; 6.0 added filters + masks + box-shadow + custom properties + render layers. The expressiveness of the modern web platform's visual language is *not* unreachable in a game engine UI library — it just took 16 years of cumulative work in RmlUi's case.
- **Data binding works.** RmlUi's `data-bind` / `data-model` / `data-for` / `data-event` family (since 4.0, 2021-05-09) is comparable in shape to React signals / Bevy observers / SwiftUI bindings. Validates the pattern; Buiy's foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.7 commits to Bevy observers + change detection (with a future signals layer open).

## Avoid

Pitfalls drawn from RmlUi's experience, with Buiy's mitigation.

| Pitfall | Source | Buiy mitigation |
|---|---|---|
| **C++ embedder integration friction.** Every non-C++ engine pays binding-layer cost; bindings lag RmlUi releases; the 6.0 render-interface redesign forced every embedder to port. | [`distribution-and-governance.md`](distribution-and-governance.md) § "Build / packaging ecosystem"; [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § "C++-embedder integration friction." | Buiy is **Rust-native + Bevy-only** (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.9). No FFI cost. The "cross-engine portability" axis is not a Buiy concern; Bevy-coupling is the explicit choice. |
| **Custom DSL deviation from web spec (RCSS decorators, RML-specific tags).** RmlUi invented `decorator:` to replace CSS `background-image` / `background-position` / `border-image`; this is a permanent ecosystem-divergence cost (no Stylelint, no MDN reference applies). | [`rml-rcss-coverage.md`](rml-rcss-coverage.md) § "Decorators — RmlUi-specific"; [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § 8. | Buiy commits to **CSS-spec semantics** for all features it ships (foundation [`visuals.md`](../../specs/2026-05-07-buiy-foundation/visuals.md) tier list maps to CSS feature names verbatim). No custom names for CSS-spec features. If Buiy ships a future CSS-flavored stylesheet (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 open question), it must commit to CSS-spec property names + semantics rather than inventing equivalents. |
| **Own-built layout engine misses modern CSS features for decades.** RmlUi's hand-rolled engine still has no Grid, no container queries, no anchor positioning, no subgrid, no logical properties — 15+ years in. The engineering cost is real. | [`layout-and-styling.md`](layout-and-styling.md) § "NO CSS Grid"; [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § 3. | Buiy uses **Taffy** as the layout substrate (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.2). Taffy ships Grid, subgrid (roadmap), block layout, float; Buiy inherits these without building them. Container queries + anchor positioning are Buiy-extension passes above Taffy. |
| **Accessibility as afterthought (or absent).** RmlUi has no AccessKit, no ARIA, no `:focus-visible`, no accessible-name computation, no live regions, no forced-colors, no `prefers-reduced-motion` — after 18 years. Retrofitting is years of work that may never happen. | [`accessibility.md`](accessibility.md); [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § 4. | Buiy commits to **AccessKit-first** (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6) + **WCAG 2.2 AA as the floor** (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 1.2). Decomposed `A11yRole` / `A11yLabel` / `A11yDescription` / `A11yStates` / `A11yRelations` components from day one. ACCNAME 1.2 name computation in `buiy_core`. Per-widget APG keyboard contract. |
| **Single-primary-maintainer bus factor.** RmlUi depends on `mikke89` continued availability. The 2014–2018 libRocket dormancy is the precedent. No corporate steward, no foundation, no co-maintainer. | [`distribution-and-governance.md`](distribution-and-governance.md) § "Bus factor"; [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § 1. | Buiy is positioned within the **Bevy ecosystem** (Bevy Foundation 501(c)(3) public charity, 5 board members, multiple paid SMEs). Buiy itself benefits from the foundation's contributor + governance infrastructure. Document the bus-factor risk explicitly when it appears; do not soft-pedal it. |
| **No published performance benchmarks at productivity-app scale.** RmlUi's "lightweight + performant" claim is not backed by 1000+-node benches. | [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § 7. | Buiy commits to verification fixtures at productivity-app scale (foundation [`verification.md`](../../specs/2026-05-07-buiy-foundation/verification.md) CI gate; foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 open question on concrete budget numbers). |
| **HarfBuzz as a sample, not a built-in.** RmlUi's complex-script story depends on embedders adopting + maintaining a sample plugin. BiDi paragraph algorithm not in core. | [`text-and-input.md`](text-and-input.md) § "HarfBuzz is a *sample*, not a built-in"; [`critiques-and-open-problems.md`](critiques-and-open-problems.md) § 5. | Buiy uses **cosmic-text** (harfrust + skrifa + unicode-bidi) directly (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.2). Complex scripts + BiDi paragraph algorithm are first-class. |
| **No theme tokens, no OS-preference plumbing.** RmlUi has CSS variables (since 6.0) but no semantic-token vocabulary, no `prefers-color-scheme` / `prefers-contrast` / `prefers-reduced-motion` / `forced-colors` honoring. | [`layout-and-styling.md`](layout-and-styling.md) § "Theming approach"; [`accessibility.md`](accessibility.md). | Buiy commits to **token-based theming** with OS-preference-bound variants (foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.5). `UserPreferences` resource surfaces `prefers-color-scheme`, `prefers-contrast`, `forced-colors`, `prefers-reduced-motion`, `prefers-reduced-transparency`, `inverted-colors`. |
| **No CSS top layer, no `<dialog>` modal-correct stacking.** Modals are positioned with `position: absolute` + high `z-index`, get clipped by scrolling containers, can't escape parent stacking context. | [`layout-and-styling.md`](layout-and-styling.md) § "Stacking & paint." | Buiy commits to **true top layer for modals / popovers / dialogs / fullscreen** (foundation [`visuals.md`](../../specs/2026-05-07-buiy-foundation/visuals.md) § 3.2 tier **F**). |
| **Render-interface designed without effects scope = breaking redesign later.** RmlUi 6.0 (2024-08-26) had to break the render interface to add filters / masks / shadows / custom shaders. Every embedder ported. | [`history.md`](history.md) § "6.0"; [`architecture.md`](architecture.md) § "The render pipeline." | `buiy-render-pipeline-design` sub-spec (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 4) must design the render-interface surface for **filters + masks + `backdrop-filter` + `mix-blend-mode` + top layer + custom shaders from day one**. No incremental ratchets. |
| **Slow major-release cadence.** 5.0 → 6.0 was 2 years; 6.0 → 6.1 was 8 months; 6.1 → 6.2 was 9 months. Single-maintainer pace. | [`history.md`](history.md) § "Release cadence observations." | Buiy tracks Bevy's release cadence (rolling latest-stable; ~3 months/minor). The pace is set by Bevy, not by Buiy's single maintainer. Validates the foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 2.9 rolling-stable strategy. |

## Borrow

Concrete primitives worth studying and adapting:

1. **The five-interface embedder pattern (Render / System / File / FontEngine / TextInputHandler).** The single best primitive in RmlUi's design. 18 years of production use across multiple GPU APIs + platforms + studios validate the decomposition. For Buiy's `buiy-3d-anchored-ui-design` (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 4) and render-to-texture surface API (open question § 5), this is the canonical reference. The interfaces aren't directly portable to Rust + Bevy ECS, but the **decomposition is** — separate render submission, system queries (time, clipboard, cursor name, log), asset I/O, font loading, and IME text input into discrete extension points the embedder owns. See [`architecture.md`](architecture.md) § "Embedder interfaces."

2. **The decorator extension pattern (`DecoratorInstancer`).** Custom user-defined visual primitives registered by name + class registration, then referenced from RCSS by name. This is the right shape for **Buiy's future custom-shader / `BuiyMaterial` extension** (lessons-list in [`../bevy-ui/lessons.md`](../bevy-ui/lessons.md) § Borrow entry 9). Buiy doesn't adopt the RCSS-decorator-replacing-CSS-background-image divergence (Avoid above), but the *extension mechanism* (named, instancer-registered, per-element-applied custom visual layers) is sound. See [`layout-and-styling.md`](layout-and-styling.md) § "Decorators."

3. **The spatial controller navigation primitive (`nav-up`, `nav-down`, `nav-left`, `nav-right` attributes + auto resolution).** RmlUi ships this since libRocket era — *before* AccessKit, *before* bevy_ui's `AutoDirectionalNavigation` (Bevy 0.18, 2026-01-13). For Buiy's `buiy-focus-model-design` (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 4), the manual-edges-with-auto-fallback shape is directly portable. See [`text-and-input.md`](text-and-input.md) § "Spatial navigation."

4. **The Context concept (multi-context per app).** RmlUi `Context` is *"an independent collection of documents"* with its own input + focus + RCSS cascade + render pass. Validates the Buiy foundation [`architecture.md`](../../specs/2026-05-07-buiy-foundation/architecture.md) § 2.6 *"per-window AccessKit adapter ownership"* + foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 *"Multi-window, render targets, render-to-texture contracts"*. The shape — independent UI hierarchies that can render to a window or to a texture for 3D-anchored use — is correct. See [`architecture.md`](architecture.md) § "Context model."

5. **The styleable scrollbar pseudo-elements.** RmlUi exposes scrollbars as DOM-visible child elements with their own pseudo-element selectors (`::scrollbar`, `::sliderbar`, `::sliderarrowinc`). This is a richer customization surface than CSS's `scrollbar-color` / `scrollbar-width` / `scrollbar-gutter` properties (which only offer indirect knobs). For Buiy's future custom-scrollbar work in `buiy-widget-catalog-design`, the pattern of "scrollbar parts are real elements with real styling" is worth studying. See [`layout-and-styling.md`](layout-and-styling.md) § "Overflow + scrolling."

6. **The `data-model` + `data-bind` + `data-for` declarative binding system.** RmlUi's data binding (since 4.0) is shaped close to Vue.js / SwiftUI / React. The pattern of "declarative bindings in markup, registered C++ data models in code, observable updates flow both ways" is portable. For Buiy's future reactivity sub-spec (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 open question on signals/computed/effects), RmlUi's data-model API is a useful reference for what *minimum declarative bindings* look like. See [`architecture.md`](architecture.md) § "Data binding."

7. **Library-as-a-runtime posture.** RmlUi *"strictly runs as a result of calls to its API, never in the background"* — no background threads, no event loop ownership, no async work, no GC. The embedder owns the loop. For Buiy operating inside Bevy's ECS scheduler (which is itself a "library-as-runtime") the posture is similar; the *commitment* to never-run-without-being-called is worth carrying forward as a Buiy invariant (no background threads, no implicit hot-reload pollers, etc.). See [`architecture.md`](architecture.md) § "One-line summary."

8. **The libRocket → RmlUi fork as a cautionary tale for project revival.** Concrete case study: 4 years dormancy (2014–2018), single maintainer (`mikke89`) picks up, ~18 months to first official release (2.0, 2019-10-13), then 8 years of consistent shipping. The pattern is **possible but slow, and depends on durable single-maintainer commitment**. The lesson for Buiy: design for governance succession from day one. Don't rely on a single individual; don't lock institutional memory into one person's head; document architectural decisions in `docs/specs/` rather than in Discord. See [`history.md`](history.md) § "Era 2 — Dormancy" and [`distribution-and-governance.md`](distribution-and-governance.md) § "Bus factor."

9. **The RCSS subset as a feasibility study for "what CSS subset is practical to ship in a game engine."** RmlUi has empirically iterated on a CSS subset for 18 years. The current shipping subset (CSS 2.1 block/inline + Flexbox + transitions/animations/transforms + filters/masks/shadows + custom properties) is the **empirically feasible floor**. Conspicuously missing: Grid, container queries, anchor positioning, modern color, `:has()`, CSS Nesting, scroll-driven animations. **If Buiy ever ships a CSS-flavored stylesheet** (foundation [`README.md`](../../specs/2026-05-07-buiy-foundation/README.md) § 5 open question), the RmlUi shipping surface is the minimum-viable scope to target; Buiy's foundation [`visuals.md`](../../specs/2026-05-07-buiy-foundation/visuals.md) tier list is the maximum-viable scope. See [`rml-rcss-coverage.md`](rml-rcss-coverage.md).

## How to use this file

When designing a Buiy feature:

1. **Find the row in `Avoid`** that names a pitfall close to your design. Read the linked file for the original incident.
2. **Find the entry in `Borrow`** that names a primitive close to what you're designing. Read the linked file to understand the RmlUi shape, then adapt for Buiy's Rust + Bevy ECS + AccessKit-first context.
3. **Promote any decision into a Buiy spec** under `docs/specs/` — this file is for capturing what we learn from RmlUi, not for encoding Buiy's own decisions.
