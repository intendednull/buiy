**Date:** 2026-05-22
**Status:** active
**Subject:** Floem — Validates / Avoid / Borrow decision file for Buiy

This is the consult-this-when-designing file. Other files in the folder are evidence; this is the synthesis. When designing any Buiy feature that touches reactivity, dogfooding strategy, release process, the Parley-vs-cosmic-text divergence, or single-flagship UI libraries — start here.

## Validates

These Buiy design choices are confirmed by Floem's experience:

- **§2.7 "no signal layer in v1" is defensible.** Floem demonstrates that a signal layer is implementable in Rust at production quality (Lapce ships it), but it also demonstrates that signal-runtime maintenance is real work that competes with everything else. Buiy's foundation chose observers + change detection in v1 — that lets Buiy ship UI before owning a reactive runtime. The Floem path remains available later. See [`fine-grained-reactivity.md`](fine-grained-reactivity.md) and Buiy foundation `architecture.md` §2.7.
- **AccessKit-first is non-negotiable.** Floem's accessibility status (zero, after 3+ years with an open issue) is the strongest possible case for designing accessibility into the foundation rather than as an addendum. Buiy foundation §2.6 commits to AccessKit-first. Stay the course. See [`accessibility.md`](accessibility.md).
- **Single-renderer commitment.** Floem maintains four rendering backends (vger / vello / skia / tiny-skia) and the maintenance cost is visible in the release cadence. Buiy commits to one (Bevy's render graph through wgpu). Foundation `architecture.md` §2.2's single-renderer stance is validated by Floem's struggle with the multi-renderer surface. See [`critiques.md`](critiques.md) § 6.
- **Token-based theming over closure-style overrides.** Floem's "theme is a closure that applies styles" is simpler than Buiy's token + variant + OS-binding model — but Floem's approach can't deliver semantic-token semantics or contrast linting. Buiy's richer theming is the right pick for WCAG 2.2 AA. See [`layout-and-styling.md`](layout-and-styling.md).
- **No custom winit fork.** Floem's `lapce/winit` fork is a debt that compounds. Buiy depends on Bevy's winit pin; if changes are needed they go upstream. Foundation `architecture.md` §2.9 commits to "rolling latest-stable Bevy" — implicit in this is Buiy does not fork winit. Validated. See [`critiques.md`](critiques.md) § 4.
- **The cosmic-text choice for Buiy.** Floem chose Parley + Swash + Fontique (the Linebender stack). Buiy chose cosmic-text. Both are pure-Rust; both have the same gaps (no vertical writing, no hyphenation, no COLRv1). The deciding factor is **renderer alignment** — Buiy's rasterized-atlas pipeline composes more cleanly with cosmic-text. Foundation `architecture.md` §2.3's cosmic-text commitment is independent of the Parley momentum (Bevy 0.19-dev + Floem are both Parley-aligned). See [`text-and-parley.md`](text-and-parley.md), [`../cosmic-text/lessons.md`](../cosmic-text/lessons.md).
- **Taffy as the layout substrate.** Floem uses Taffy 0.9.2 (with `grid`). Buiy uses Taffy. This is a non-controversial validation — Taffy is the de facto Rust layout engine. See [`layout-and-styling.md`](layout-and-styling.md), [`../taffy/`](../taffy/).
- **AccessKit-first widget trait design.** Floem's `View` trait does not have an accessibility-node method. This is why retrofitting AccessKit onto Floem would be a major refactor. Buiy's component / widget trait must include accessibility-node construction as a **required** method, not optional. See [`accessibility.md`](accessibility.md) § "The technical surface that's missing."

## Avoid

| **Single-flagship dogfooding.** Floem outside Lapce is unverified at scale. At least one early adopter must require accessibility (WCAG 2.2 AA), or the foundation drifts. Track this explicitly in the `buiy_verify` manual-release-gate cadence. |
| **Slow release cadence on a foundational substrate.** 3 versions in 4 years; 17+ months silent on crates.io. Crates.io users get stranded on stale snapshots. | [`distribution.md`](distribution.md), [`history.md`](history.md), [`critiques.md` § 1](critiques.md) | Buiy commits to a release cadence policy *before* v1.0. Owner: a section in `buiy-verification-design` or a `buiy-release-policy-design` sub-spec. Default proposal: a Buiy release per Bevy minor, plus patch releases between for security / AccessKit major bumps. |
| **Custom winit fork at the UI-library layer.** Floem holds `lapce/winit`. Forks drift; security fixes lag; ecosystem fragments. | [`architecture.md` § Windowing](architecture.md), [`critiques.md` § 4](critiques.md) | Buiy depends on Bevy's winit pin. Changes go upstream (via Bevy or directly). No Buiy-owned winit fork. This is implicit in foundation `architecture.md` §2.9 ("rolling latest-stable Bevy"); make it explicit in any future windowing/surface sub-spec. |

With no full-time devs, this is unsustainable. | [`architecture.md`](architecture.md), [`critiques.md` § 6](critiques.md) | Buiy commits to one renderer (Bevy's render graph through wgpu). Foundation `architecture.md` §2.2. Validated; do not revisit. |
| **AccessKit as future work.** Floem's issue #8 has been open since 2023-04-14. "We'll add accessibility later" predictably becomes "we never added accessibility." | [`accessibility.md`](accessibility.md), [`critiques.md` § 3](critiques.md) | AccessKit-first is foundation `architecture.md` §2.6. The `View` / component / widget trait carries a required accessibility-node method. ACCNAME 1.2 path lives in `buiy_core`. The adapter is owned per-window by Buiy. None of this is deferred. |
| **Closure-style themes that can't express semantic tokens.** Floem themes are "shared style closures." Cannot deliver token semantics, contrast linting, OS-pref binding. | [`layout-and-styling.md` § Theme system](layout-and-styling.md) | Buiy's token-based theming (foundation `architecture.md` §2.5 + `cross-cutting.md`) is the right structure. Floem is a *negative* reference here; don't model on it. |
| **Documentation as separable concern.** Floem ships docs.rs API docs + 27 examples + README. No book; no long-form guide. For a non-trivial library this is thin. | [`ecosystem.md` § Documentation](ecosystem.md), [`critiques.md` § 5](critiques.md) | Buiy treats documentation tier as part of foundation. Each sub-spec lists its documentation deliverables (rustdoc + book chapter + example). Owner: foundation `verification.md` or a follow-up. |
| **Releasing only when the flagship needs it.** Lapce consumes Floem as a git dep; crates.io versions get cut sporadically. External users are second-class. | [`distribution.md`](distribution.md), [`history.md`](history.md) | Buiy's external users are *first-class*. Any internal-flagship dogfooding must produce crates.io releases on a defined cadence regardless of flagship readiness. |
| **Treating "view-function" as a complete reactivity story.** Floem's view function runs once; signals drive updates. This is elegant but inverts most Rust developers' mental model (which assumes view rebuild). The ergonomic delta is real. | [`fine-grained-reactivity.md` § Rust constraints](fine-grained-reactivity.md) | If Buiy ever adds signals (post-§2.7-revisit), document the model shift explicitly with examples comparing to coarse-render React-ish patterns. Don't assume users know. |
| **Assuming Floem can be picked up by Buiy users as a familiar substrate.** Floem and Buiy are different design spaces (standalone vs Bevy-embedded). Surface similarities (Taffy, reactive primitives) do not translate to runtime compatibility. | [`comparisons.md` § Buiy specifically](comparisons.md) | Document the divergence explicitly in any Buiy material that mentions Floem. "Floem is the conceptual reference for reactivity, not a migration source." |

## Borrow

Concrete primitives, patterns, and design choices from Floem worth studying directly and possibly adapting into Buiy:

1. **The `RwSignal<T>` + `create_effect` + `create_memo` + `batch` API surface.** If Buiy adds a signal layer in a follow-up sub-spec (foundation §5 open question), this is the API shape to start from. Specifically: `Copy` signals when `T: Copy`, `.with(|t| ...)` callbacks for non-`Copy`, scoped ownership tied to a parent lifetime. The shape has years of bug-find in JS and now Rust. See [`fine-grained-reactivity.md`](fine-grained-reactivity.md).
2. **The closure-into-property pattern.** `label(move || format!("count: {}", c.get()))` — a value-or-closure overload that lets a property be either a static value or a reactive expression. Buiy's BSN authoring could borrow this for ergonomic reactive bindings without ECS round-tripping. Note: requires §2.7 to be reopened.
3. **`Scope`-tied signal lifetimes.** Floem disposes signals when their owning view scope drops. Buiy's analog would be per-`Entity` or per-`SystemSet` scope. The pattern is the right shape; the substrate (ECS vs view tree) differs. See [`fine-grained-reactivity.md`](fine-grained-reactivity.md).
4. **The hover/active/focus pseudo-style hooks.** Floem's `.hover(|s| ...)`, `.active(|s| ...)`, `.focus(|s| ...)` builder methods are a clean way to express CSS-pseudo-class semantics without a selector engine. Buiy's component style API can adopt the same shape (flat overlay closures, not cascade rules). See [`layout-and-styling.md`](layout-and-styling.md).
5. **The full keyframe + spring animation surface (0.2.0).** Floem ships transitions + keyframes + springs in one module. Buiy's `buiy-animation-design` sub-spec roadmap commits to all three; Floem's API shape (`animate` module, spring physics on style properties) is worth direct study. See [`layout-and-styling.md` § Animation](layout-and-styling.md).
6. **The `Action` / event-into-editor pattern.** Editing-capable views consume an enum of `Action`-style events (Insert, Motion, Delete, etc.). This composes well with Buiy's input-events sub-spec, which already plans an `Action`-like enum for text-edit dispatch. See [`text-and-parley.md`](text-and-parley.md) and [`../cosmic-text/lessons.md`](../cosmic-text/lessons.md) Borrow item 10 (same pattern; cosmic-text exposes it directly).
7. **The View trait's separation between `build`, `update`, `layout`, `paint`, and event hooks.** Floem's `View` trait factors the per-frame work into named lifecycle methods. Buiy's component / widget trait can borrow the factoring (build/update separation; layout/paint separation; event hooks as separate methods, not a single `handle_event`). See [`architecture.md`](architecture.md).
8. **The Lapce-as-flagship dogfooding pattern *with the proviso* that Lapce's accessibility gap leaked into Floem.** The pattern itself (build a real app on the library) is sound; the lesson is that *the flagship's quality requirements transfer to the library.* If Buiy's flagships require WCAG 2.2 AA, Buiy gets WCAG 2.2 AA. If they don't, it drifts. Pick flagships accordingly. See [`ecosystem.md`](ecosystem.md), [`critiques.md` § 2](critiques.md).
9. **The "responsive breakpoint" hook style (`.responsive_breakpoint(SM, |s| ...)`).** Simpler than CSS Container Queries; covers the 80% case. Buiy's responsive sub-spec can offer this as a baseline before Container Queries become absorbable. See [`layout-and-styling.md`](layout-and-styling.md).
10. **The 27-examples-as-documentation pattern (with a book layered on top).** Floem ships 27 examples covering practical patterns. The examples *work* — they are not a substitute for a book, but they are an effective shape for "show me the idiomatic answer to X." Buiy should commit to a comparable examples corpus alongside its book.

## How to use this file

When designing a Buiy feature: (1) Find the row in **Avoid** that names a pitfall close to your design, follow the linked file for full evidence, and apply the mitigation. (2) Find the item in **Borrow** that names a primitive close to what you're designing, read the Floem source for shape, then adapt for Buiy's ECS-rooted component model. (3) Confirm via **Validates** that the Buiy foundation decision touching this design is upheld by Floem's experience.

Promote any decision into a spec under `docs/specs/` — this file captures what we learn from Floem, not what Buiy commits to.
