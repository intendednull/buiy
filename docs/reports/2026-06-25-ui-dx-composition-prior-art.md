# UI Developer-Experience & Composition — Prior-Art Research

## 1. The question

"Easy to use and compose" for Buiy is not a vague aspiration — it is a specific bet that an ECS-native, retained-mode, AccessKit-first Rust UI library can match the *authoring ergonomics* of declarative frameworks (SwiftUI, Compose, React) and signal libraries (Solid/Leptos) without adopting their runtimes. The corpus is unanimous that this is possible, but only if we separate two things the discussion usually conflates: the **API surface** (the shapes authors touch — constructors, events, state reads, style spellings, tokens) and the **runtime mechanism** (recomposition, snapshot signals, VDOM diff, property wrappers tied to view identity). Across SwiftUI, Compose, Flutter, React, and Leptos the verdict is the same — the *patterns* port, the *mechanisms* mostly do not, because Bevy's `Changed<T>` change detection, entity identity, observers, and required-components already occupy the runtime slots those frameworks fill with their own machinery.

The eight frictions this research must inform are: **F1** the state model *is* the accessibility tree (no domain layer); **F2** one untyped `OnPress(Entity)` sink for ~5 widget kinds; **F3** silent-wrong failure modes (`#[require]`-suppression, typo'd token → magenta, forgotten `Camera2d` → blank, `EventReader` vs `MessageReader`); **F4** the fluent `Style` builder is a `Bundle`, so `bsn!` cannot author it; **F5** one widget has up to four spellings; **F6** stringly-typed, half-wired theme tokens; **F7** retained-mode boilerplate (17 marker structs, hand-rolled tree-walks, dual-writes, no data/dynamic content in scenes); **F8** verbosity (no `text("..")`, manual child wiring, value towers like `Sizing::Length(Length::Px(340.0))`).

Three hard constraints bound the option space and must be stated up front, because several attractive directions fight them: Buiy **stays ECS-native + retained-mode** (no wholesale immediate mode, no foreign reactive runtime as the substrate); **AccessKit-first stays** — the a11y tree is non-negotiable as an *output* (the live question is only whether app-facing *state* should be a separate layer that *projects into* it); and **`bsn!` is Bevy's macro** — we build on/around/beside it, we do not fork the grammar. The most important single finding, repeated independently by five corpora (Flutter, Compose, Slint, Godot/Slate/Unity, bevy_ui #17644, AccessKit/Flutter/Compose semantics), is that **every mature retained-mode system keeps app state as the source of truth and derives the a11y tree from it — never the reverse.** Buiy is the lone outlier that inverted this, and bevy_ui's issue #17644 is the ecosystem's own post-mortem of exactly that mistake on exactly Buiy's substrate.

## 2. Cross-cutting patterns (the design vocabulary)

### 2a. State: local, shared, and the controlled `value`+`onChange` convention

The surveyed systems span five mechanisms but converge on one *architecture*. **React** colocates state in hooks under a single-source-of-truth rule, with a sharp controlled/uncontrolled axis: a controlled widget renders a `value` prop and reports intent via `onChange`; the owner applies it. **Compose** formalizes this as *state hoisting* — replace internal `remember` with `value: T` + `onValueChange: (T)->Unit`, "state down, events up." **SwiftUI** uses `@State`/`@Binding`/`@Observable` with property-level tracking; `Toggle(isOn: $on)` stores a plain `Bool`. **Flutter** lifts state up, passes data down, callbacks up; `ChangeNotifier`/`ValueNotifier<T>` are observable cells. **Leptos/Solid** put state in `Copy` arena signals separate from the view. **ECS** already *has* the state cells (components) and the change signal (`Changed<T>`, a coarse, polled, frame-granular dirty bit — no dependency graph, no memoization, no glitch-free diamonds, per Bevy discussion #10212).

The load-bearing point for **F1**: in Flutter the Semantics tree is *compiled from* RenderObjects' `SemanticsConfiguration`; in Compose `Modifier.semantics` is a parallel tree; AccessKit "does **not** compute accessible names" — it is explicitly a producer-side output the toolkit pushes into. **bevy_ui_widgets is the existence proof on Buiy's own substrate**: it stores `Checked`, `SliderValue`, `SliderRange`, `SelectedValue<T>`, `Pressed`, `InteractionDisabled` as decomposed *domain* components and runs sync systems (`AccessibilityNode::set_toggled()`) that project them into the AccessKit tree. Slint routes `CheckBox.checked` into `accessible-checked`; Godot/Slate/Unity all expose `button_pressed`/`IsChecked()`/`isOn` as the public API with a11y as a derived, separately-wired layer (and Unity/Godot's bolt-on-late a11y is the *opposite* failure — a parallel tree maintained by hand, the same dual-write smell as Buiy's F7 `Text`+`A11yLabel`).

> **For Buiy (ECS+bsn!): HIGH.** Store a domain component (`Checked(bool)`, `SliderValue(f32)`) as the queried API; run a `BuiySet::A11yUpdate` system that derives `A11yToggled`/`Toggled::True` from it. App code reads `Checkbox::checked()`, never `Toggled::True`. This is a near-drop-in port (bevy_ui_widgets does it on identical Bevy/AccessKit plumbing) and is the single highest-leverage move in the corpus. The controlled/uncontrolled axis ports as a *policy choice* — but heed bevy_ui_widgets' own critique (open-problems §11): pure controlled-state with no escape hatch made a 50-field form ~5× React's size; ship per-widget self-update observers **on by default**, let live-data apps opt out.

### 2b. Events & change propagation

The spectrum: **callbacks** (SwiftUI `Button(action:)`, Compose/Flutter/React `onChange`), **typed messages** (Elm/iced central `Message` enum), **two-way binding** (SwiftUI `@Binding`, Slint `<=>`, MVVM `{Binding}`, UMG/Noesis), **fine-grained reactivity** (signals: write a cell, dependents auto-update, *no change event at all*), and Buiy's **single untyped `OnPress(Entity)`**.

Two facts dominate. First, **per-widget typed, value-carrying events are universal and separable from paradigm**: iced `checkbox(state.done, Message::Toggled)` / `on_input(String)` / `slider(.., Message::Changed)`; Compose `onCheckedChange:(Boolean)`; Flutter `ValueChanged<bool>`/`<double>`/`<String>`; Godot `toggled(bool)`/`value_changed(float)`; woodpecker `TextChanged`/`ToggleChanged`; Slint typed `callback`s. WAI-ARIA APG *proves per-widget verbs are mandatory*: Button activates on Enter+Space, Checkbox toggles on Space (Enter does **not**), Radio moves *and* auto-selects on arrow, Slider increments on arrow — a single sink **structurally cannot** express this. Second, **the central-enum routing is the part to avoid**: iced's one `Message` enum hits friction at ~200+ variants (COSMIC, Halloy), and the whole reconciliation/keyed-state subsystem it needs (`Tree`/`tree::Tag`/`keyed::column`) is *machinery ECS eliminates* via stable entity identity.

The cleanest ECS-native answer is in the corpus twice: **bevy_ui_widgets' two-event vocabulary** — `Activate{entity}` + `ValueChange<T>{source, value, is_final}` — where `is_final:bool` collapses the whole interim-vs-commit ceremony (drag tick = `false`, release = `true`), plus per-widget `Set<X>{entity,value}` command events to drive widgets from gamepad/scripts/tests, all delivered through **observers attached inline** via `observe(...)` in the spawn tuple. Xilem's **id-path routing** (events route up the entity path, each ancestor may consume/transform with access to its slice) and gpui's **typed-action structs + keymap-as-asset dispatched over the focus path** generalize this; both map onto Bevy observers, which the Bevy team explicitly markets as "the easiest way to write one-off logic for UI." The two-layer distinction matters (AccessKit/Flutter): the closed AT-action vocabulary (`Click`/`SetValue`/`Increment`) is the *input* verb set and is **not** the app-command surface — app transitions ("open settings") need a separate typed command/event layer.

> **For Buiy (ECS+bsn!): HIGH.** Replace `OnPress(Entity)` with typed per-widget entity events (`Activate`, `ValueChange<T>{is_final}`, or `Toggled{entity,bool}`/`SliderChanged{entity,f32}`) observed inline at spawn via an `observe(...)` bundle-effect (put the helper in `buiy_core`, not a widget crate). **Avoid** stored-closure `EventHandler<T>` callbacks (Freya/Dioxus) — they carry the `'static` tax and aren't Reflect/`bsn!`-authorable; the *concept* ports as events/observers, the closure mechanism does not. Mine APG for the typed-event *taxonomy*: it pre-specifies the verb per widget.

### 2c. Composition & slots

Three slot idioms recur: **single `children`/`content` slot** (SwiftUI `@ViewBuilder`, Compose `content: @Composable ()->Unit` placed last for trailing-lambda, Flutter `child:`/`children:`, React `props.children`), **named slots** (Slate `SLATE_NAMED_SLOT` → `Card{Header,Body,Footer}`; Compose `Scaffold{topBar, bottomBar, fab}`; XAML/UXML named slots; React named-element props), and **compound components** (Radix `<Select><Select.Trigger/><Select.Option/></Select>` sharing implicit state via context; React Aria's context+named-slot wiring with `slot="increment"` matched against a slots map). Dynamic/data-driven lists are authored via dedicated constructs — SwiftUI `ForEach`, Compose `for`/`if` (first-class, tree regenerated), Leptos/Solid keyed `<For each= key=>`, Flutter `ListView.builder`, belly `<for>`, RmlUi `data-for`. Critically, **belly/Bevy BSN `<for>` is one-shot at spawn, not reactive** — honest about the limit. Unity's **UQuery** (`element.Q<Button>(name, class)`) and sickle's **`UiContext::get(name)->Entity`** address widgets/sub-entities *without* per-widget marker structs — the direct counter to F7's 17-marker boilerplate. Compose's **merged/unmerged semantic projection** shows the a11y layer can *collapse an authored subtree* into one focusable node, so authors don't hand-merge.

> **For Buiy (ECS+bsn!): HIGH for named slots & compound widgets.** Slate's named slots map to Bevy relationship components (`HeaderOf`/`BodyOf`) or a `Slot{which}` discriminator + `bsn!` `children!`. Compound components map to a `select(...)` scene-fn seeding shared state on a parent entity that `option(...)` children read via hierarchy/relations — killing consumer-side option↔select wiring (F5/F7). UQuery + `UiContext::get` port as a name/class-filtered query (`Name` + class component) to replace marker sprawl. **MEDIUM/honest gap:** *reactive* data-driven children (a `Vec` change re-spawning entities) is the unsolved half of F7 — `bsn!`/belly `<for>` are spawn-time only, and Bevy itself ships **no** reactivity layer (deferred to Quill/bevy_reactor). This needs either observer-driven reconciliation Buiy hand-rolls or a signal layer (§2g, §4).

### 2d. Styling & modifiers

Four attachment models. **Modifier chain** (SwiftUI `ModifiedContent` wrapping; Compose flat ordered `Modifier` element list passed as a normal `modifier: Modifier = Modifier` param) — uniform, reusable, order-significant, *reachable from every authoring site identically*. **Wrapper widgets** (Flutter `Padding(child: DecoratedBox(child:...))`) — one idiom but the textbook cause of "nesting hell," a **cautionary** model for `bsn!`'s nesting, not one to adopt. **Style-props** (Chakra: styling is props on the node). **CSS cascade** (flair/USS/RCSS) — rejected by Buiy and by Floem (flat `.hover`/`.active`/`.focus` overlay closures, no selector engine/specificity).

Buiy's **F4 is self-inflicted and the corpus diagnoses it precisely**: a fluent builder is ergonomic *only if its output is authorable everywhere*; because Buiy's `Style` is a `#[derive(Bundle)]`, the one path users are steered to (`bsn!`) can't reach it. The exact same trap is logged across the corpus as the strongest "known dead end" signal: woodpecker's 50-field `WoodpeckerStyle` megacomponent (can't patch `background_color` independent of `display`), sickle's `DynamicStyle` `Vec<DynamicStyleAttribute>` built by chained builder calls (`bsn!` can't patch into it; two templates can't merge), and bevy_a11y's private-setter `AccessibilityNode` (#17644). **Bevy's own fix is the cleanest port**: it collapsed the old separate `Style` struct *into* the `Node` component so `bsn!` patches `Node { width: px(100.) }` directly — styling-as-component, not styling-as-Bundle.

> **For Buiy (ECS+bsn!): HIGH (structural fix), MEDIUM (chain mechanism).** Make styling **`bsn!`-authorable components** (Buiy's decomposed `Background`/`Border`/`BoxShadow`/`TextColor` already are — the gap is the fluent `Bundle` builder the macro can't see). Keep a fluent builder only as thin *sugar* that produces the same components (gpui's lesson: fluent setters are fine as convenience over a typed token model, never *as* the model). The SwiftUI/Compose chain mechanism doesn't port verbatim (`bsn!` patches components, not a fluent receiver) — but the *principle* (one uniform styling channel reachable from every idiom) is the cure. egui's per-state `Widgets{noninteractive,inactive,hovered,active,open}` decomposition is the right *substrate shape* a token system resolves into. **Caution (belly/flair):** when tokens, `bsn!`, inline, and programmatic writes can all hit the same render component, specify precedence up front — belly/flair both silently clobber programmatic writes with undocumented precedence (an F3-class seam bug).

### 2e. Design tokens, typed not stringly

This is the **clearest open ground** in the corpus: across belly, RmlUi, Coherent, Slint, egui, iced, Godot, feathers, flair, shadcn — *nobody shipped a typed, checked, OS-preference-bound semantic-token vocabulary*. They bottom out at literals, stringly CSS `var(--name)`, or string-keyed maps; typos fail silently (Buiy's magenta is the industry norm, not an aberration). The web styling ecosystem points the way out: **vanilla-extract `createThemeContract`** (a compiler-enforced contract every theme must *fully* implement — eliminates both typos *and* half-wired scales in one move), **Panda** tiered tokens (primitive → semantic → component, build-time TS types), **Tailwind** constrained scales ("constraint is strength"), **Stripe Apps** (no arbitrary values, only token names, un-overridable a11y presets — the closest philosophical neighbor for an a11y-first lib), and **DTCG 2025.10** (first stable token-interchange spec, could codegen Rust enums). On Buiy's substrate, **feathers' typed `ThemeToken`/`UiTheme`/`ThemeBackgroundColor` + change-detection observers resolving token→color** is the reference implementation — its only flaw is a *flat SCREAMING_SNAKE string namespace* (still typo-able) and *color-only scope* (spacing/radius/typography/motion hardcoded in `constants.rs`), which is *exactly* Buiy's "half-wired" F6.

> **For Buiy (ECS+bsn!): HIGH.** Replace `HashMap<String,Color>` with **typed token keys** — a closed `enum`/newtype (Rust API guidelines C-CUSTOM-TYPE; clap's `ValueEnum` exemplar) so a typo can't compile and tokens autocomplete. Resolve at **load time, hard-error** (flair's lesson: string `var()` type-checked only at the consumer fails late). Cover **spacing/radius/typography/motion**, not just color (Godot/feathers prove the color-only gap forces widget forks). A vanilla-extract-style **theme contract trait** the compiler forces every theme to satisfy completely is the strongest single model. Add a **CI contrast lint** (every consumer is explicit, so it's runnable) for the WCAG 2.2 AA floor.

### 2f. Hard-to-misuse / ergonomic Rust

The Rust API canon is the direct F3/F5/F8 toolkit. **Typestate builders** (bon 3.9.3, typed-builder) make "forgot a required field" a *compile* error; **make-invalid-states-unrepresentable** (enums/newtypes/bitflags) kills the token→magenta path by construction; **newtype + `From`/`Into`** make literals ergonomic without losing type distinction (`Length::px(340.0)`, `impl Into<String>` args, bon `#[builder(into)]`) — the antidote to value towers; **C-CTOR/C-METHOD/C-CONV** give one canonical spelling per operation. The honest limits matter for the `bsn!` path: a **typestate builder object cannot live inside `bsn!`'s component-patch grammar**, so on that path "hard to misuse" must be expressed as *required-components + non-suppressible scene-fns*, not a fluent builder. egui's stated goal "**Friendly: difficult to make mistakes**" as an explicit acceptance bar — and its `DebugOptions::warn_if_rect_changes_id` (loud-warn the structural footgun that can't be a compile error) — is the design discipline to adopt for F3's residue (forgotten `Camera2d`, `#[require]`-suppression). React's loud DEV warning on controlled↔uncontrolled switch is the same template.

> **For Buiy (ECS+bsn!): HIGH for naming/tokens/literals, MEDIUM for typestate.** Collapse the four spellings to one canonical scene-fn (pure convention, zero runtime cost). Type the tokens (enum/newtype). Add `From<f32>`/`px()` to dissolve `Sizing::Length(Length::Px(340.0))` — keep conversions **one level deep** (bon's documented nested-`Into` inference stall). For the suppression trap and forgotten-camera class: where Rust's types can't carry it, make it a **loud startup/debug diagnostic**, never silent magenta/blank. **Caution (SwiftUI):** over-clever inferred chaining trades a visible footgun for an invisible compile-time blowup — don't chase max terseness past legibility.

### 2g. Authoring layer & the `bsn!` question

Bevy BSN (shipped 0.19, PR #23413) is what Buiy already rides: required-components, `Template`/`Construct` (asset strings → handles with World access during init), partial **patches** (write only named fields, later patches override field-by-field), `bsn!`/`bsn_list!`, first-class `Children[...]`/relations, and observers co-located via `on(...)`/`observe(...)`. The **highest-leverage finding: almost everything is buildable *with* `bsn!`, not around it** — feathers converged every widget on **one scene-fn returning `impl Scene`** (markers + `#[require]` are the internal contract, the scene-fn is the public face), which directly kills F5. But two honest gaps: **(1) no shipping reactivity/data-binding** — Bevy explicitly defers the dynamic/derived half of F7 to the ecosystem; (2) **no `.bsn` asset loader in 0.19** (code-driven only, so no from-disk hot-reload yet). The two-language DSL tax is the recurring warning (Makepad `.live`, Slint `.slint`, belly `eml!`): errors against generated code, manual cross-boundary rename, rust-analyzer/IDE degradation — which *validates* Buiy's `bsn!`-as-Rust choice but warns that **any sugar layered on `bsn!` must preserve go-to-def/rename and not become a bespoke grammar** (belly's `eml!` custom grammar degraded rust-analyzer). Dioxus's `rsx!` wins Buiy can't author directly (format-string interpolation, statement `if`/`for`/`match`) are upstream-Bevy asks, not Buiy's to fork.

> **For Buiy (ECS+bsn!): HIGH (build on it), with one deferred decision.** Adopt scene-fn-as-canonical (feathers), styling-as-`Node`-like-components (Bevy), typed tokens on render components (feathers), inline observers (`observe`), `px()` + implicit `.into()` + `Children[...]` (kills F8 child-wiring). The deferred decision Buiy **cannot inherit**: its reactivity story (§4) — Bevy signals the direction but hasn't shipped it.

## 4. Design directions for the brainstorm (OPTIONS, not decisions)

**D1 — Domain-state components with an a11y projection system.** *Core idea:* every widget owns small decomposed domain components (`Checked(bool)`, `SliderValue(f32)`, `Expanded(Option<bool>)`) as the queried API + `Checkbox::checked()` accessors; one `BuiySet::A11yUpdate` system derives `A11yToggled`/`Toggled::True` as a *write-only output*. *Kills:* F1 (directly), enables F2/F7. *Costs/fights:* none structural — it *aligns* with AccessKit-as-output; the only work is a domain enum per stateful widget (own `CheckState{Unchecked,Checked,Mixed}`, don't re-export accesskit's `Toggled`). *Lineage:* bevy_ui_widgets #17644, Flutter/Compose/Slint semantics-as-projection, React/Leptos domain-state. **This is the consensus pick and the prerequisite for D2.**

**D2 — Typed two-event vocabulary over ECS observers (`Activate` + `ValueChange<T>{is_final}`).** *Core idea:* retire `OnPress(Entity)`; every widget emits a typed entity event observed inline via `observe(...)`; `is_final` collapses interim/commit; `Set<X>{entity,value}` command events drive widgets from tests/gamepad. *Kills:* F2; eases F8 (inline observers). *Costs/fights:* must pick controlled-vs-uncontrolled default (ship self-update *on*, opt out — bevy_ui_widgets §11); APG keyboard contracts pin the verb taxonomy. *Lineage:* bevy_ui_widgets, woodpecker `on_change`, iced typed handlers (minus the central enum), gpui typed-actions, APG. **Highest H-rated, lowest-risk, ECS-native.**

**D3 — Styling as `bsn!`-authorable components + thin fluent sugar.** *Core idea:* make `Style` a Component (or keep decomposed render components) authorable in `bsn!` like Bevy's `Node`; the fluent `.flex_column().width_px()` builder survives only as sugar producing the *same* components. *Kills:* F4; helps F5. *Costs/fights:* the SwiftUI/Compose *chain* doesn't port verbatim; must specify precedence when bsn!/token/inline/programmatic writes collide (belly/flair clobber warning). *Lineage:* Bevy `Style`→`Node` collapse, Slint/belly "style = same surface," anti-patterns: woodpecker/sickle megacomponents.

**D4 — Typed token system with a theme-contract trait.** *Core idea:* closed token enums/newtypes (color *and* spacing/radius/typography/motion), resolved at load with hard-error; a `Theme` contract the compiler forces every theme to fully implement; per-subtree override component; CI contrast lint. *Kills:* F6 (typo→magenta and half-wiring both). *Costs/fights:* enumerating tokens is upfront work (a feature for a design system); per-subtree override is a Bevy-Resource-vs-inherited-component design call. *Lineage:* vanilla-extract `createThemeContract`, Panda tiers, Stripe constraint, feathers typed tokens, Godot/Slate typed registries.

**D5 — Scene-fn-as-canonical + a written API style guide.** *Core idea:* one blessed spelling per widget (the parameterized scene-fn, feathers-style); markers + `#[require]` become *internal* contract, not a public path; deprecate `::new`/raw-patch/`_scene` dual-names; publish a Compose-style `api-guidelines.md`. *Kills:* F5; helps F8. *Costs/fights:* choosing the canonical form given `bsn!`'s marker model; the suppression trap (#18779) still needs a loud diagnostic. *Lineage:* feathers BSN migration, Compose API guidelines, Flutter named-ctor, Noesis two-tier surface; anti-pattern: Slate-vs-UMG two parallel stacks.

**D6 — A fine-grained signal layer over `Changed<T>` (for the dynamic/derived half of F7).** *Core idea:* a `reactive_graph`-style layer (memos/effects flush on a Bevy schedule tick) for derived state and reactive `<For>` children, *over* `Changed<T>`. *Kills:* F7's derived-state re-walks and "no data in scenes." *Costs/fights — this is the direction that most fights the constraints:* the signal scheduler is serial/topological while Bevy's is parallel/access-ordered — an **explicitly unsolved bridge** (Dioxus/Bevy #10212); layering VDOM-style diff on ECS double-counts `Changed<T>`; one-frame cascade lag per marker level; `bevy_reactor`/`bevy_lazy_signals` are alpha. Floem's persistent-graph model (no diff) composes with ECS; a coarse re-render layer does not. *Lineage:* Leptos/Solid/Floem, `bevy_reactor`. **Treat as a research spike, not a v1 commitment** — Bevy itself deferred it.

**D7 — Dirty-bit / derived-component systems as sugar over change detection (the conservative alternative to D6).** *Core idea:* model "reactivity" as thin syntactic sugar over `Changed<T>` — `update()->bool` runners, derived-component systems, observer-driven sync — keeping the scheduler tiny (woodpecker's lesson: "complexity in the reactive runtime is a self-inflicted wound; lean on Bevy Schedule + observers + `Changed<T>`"). *Kills:* the *static* and derived-not-dynamic parts of F7 without a parallel runtime. *Costs/fights:* doesn't give true reactive lists/`bind:` ergonomics; field-level subscription ("one field on one component") needs decomposition. *Lineage:* woodpecker dirty-bit, Xilem Memoize (which `Changed<T>` already subsumes), bevy_ui `Node`/`ComputedNode` split. **The constraint-respecting default; D6 is the ambitious upgrade.**

## 5. Prior-art promotion recommendations

Per the using-prior-art "Promote" format. The corpus is currently strong on Bevy-native (bevy_ui/widgets/feathers/flair/sickle), Rust-UI (Floem/Xilem/Dioxus/iced/egui), game-engine (Godot/Slate/Unity/Noesis), DSL (Slint/Makepad/belly/RmlUi/Coherent), and semantics/automation (Flutter/Compose/AccessKit/APG/gpui) lenses. The web findings surface gaps where the *declarative-DX composition lens* is thin or absent.

- **SwiftUI** — *new folder.* Load-bearing for D3 (modifier-chain uniformity), F1 (`@State`/`@Binding`/`@Observable` separation), F6 (`@Entry`/typed environment defaults). Corpus has it only as a passing contrast inside other folders. Sources: developer.apple.com SwiftUI docs, WWDC25/26 notes, hackingwithswift. **Priority: now** — it is the canonical reference for the modifier/controlled-binding patterns three directions lean on.

- **Jetpack Compose (composition lens)** — *extend existing a11y-only folder.* Load-bearing for D2 (controlled `value`+`onValueChange`), D3 (`Modifier` as uniform value param), D5 (the *published API style guide* — a directly transferable artifact), F6 (`MaterialTheme` typed accessors). The existing folder covers semantics/merged-tree only; the composition/state-hoisting/modifier material is absent. Sources: developer.android.com compose docs, compose-api-guidelines.md. **Priority: now.**

- **Design-token systems (typed/tiered)** — *new folder* (vanilla-extract, Panda, Tailwind, Stripe Apps, Style Dictionary/DTCG, cva/tailwind-variants). Load-bearing for D4 — the *only* place in the whole corpus with a typed, completeness-checked token model, and F6 is high-leverage open ground. Sources: vanilla-extract.style, panda-css.com, designtokens.org (DTCG 2025.10), cva.style, tailwind-variants.org. **Priority: now.**

- **Leptos/Solid fine-grained signals (+ ECS bridge)** — *new folder.* Load-bearing for D6/D7 — the decision of whether to build a signal layer vs lean on `Changed<T>` is the corpus's biggest open tension. Sources: book.leptos.dev, `reactive_graph` docs, Bevy discussion #10212, bevy_reactor write-up. **Priority: after** D1–D5 land — it informs the *hardest* decision but the others are unblocked and higher-confidence.

- **React + Radix/React-Aria composition** — *new folder.* Load-bearing for the compound-component / headless-primitive + named-slot patterns (F5/F7) and the controlled/uncontrolled vocabulary (F1). React Aria is the explicit a11y-first neighbor (behavior+ARIA via context, state as queryable data). Sources: react.dev, radix-ui.com, react-spectrum.adobe.com/react-aria, shadcn changelog. **Priority: after** — overlaps heavily with the Compose/SwiftUI conventions; promote once those expose remaining gaps.

- **Flutter (composition lens)** — *extend existing folder* (currently semantics-only). Useful as the *cautionary* model (wrapping hell, runtime context-lookup failure) and for typed `ThemeData`/`ValueChanged<T>`. **Priority: low** — its positive lessons duplicate SwiftUI/Compose; its unique value is the negative example, already captured in the findings here.

**Shortlist (2–4 highest-leverage): SwiftUI (now), Compose composition-lens extension (now), and the typed design-token folder (now).** These three are load-bearing for D1–D5 — the directions that respect every hard constraint and carry the highest transferability. Leptos/Solid is the deliberate *fourth*, promoted **after**, because D6/D7 is the one decision where getting the prior art right matters most *and* where rushing risks importing the unsolved scheduler bridge. React/Radix and Flutter-composition can wait: their highest-value patterns (compound components, controlled convention, typed callbacks) are already well-covered by the Compose/SwiftUI promotions plus the Bevy-native corpus.

## 6. Open questions for the brainstorm

- **Does a domain-state layer duplicate the a11y tree or replace its authority?** The corpus says project domain→a11y (D1), but Buiy already invested in decomposed `A11yToggled`/`A11yLabel`/`A11yStates`. Do those become pure write-only outputs of a sync system, or does some app-facing read stay on them during migration? (Risk: two half-sources of truth — the worst of both poles, per Unity/Godot bolt-on vs Buiy's fusion.)

- **Controlled vs uncontrolled default.** bevy_ui_widgets ships controlled-only and pays 5× form code; React/Compose make controlled the *teaching* default but allow uncontrolled. Which is Buiy's default, and is the opt-out per-widget self-update observer **on** by default?

- **Signals-over-ECS (D6) vs dirty-bit-over-`Changed<T>` (D7).** This is the single sharpest tension: fine-grained signals give the best F7 ergonomics but the serial/parallel scheduler bridge is unsolved and the runtime is alpha; `Changed<T>`-sugar respects every constraint but can't deliver reactive `<For>`/`bind:`. Spike D6, ship D7, or commit to one?

- **How far to ergonomically wrap `bsn!` vs wait for Bevy.** Format-string interpolation, statement `if`/`for`, `.bsn` hot-reload, and reactive BSN are all upstream-Bevy territory Buiy can't fork. Which do we build a thin wrapper for now (preserving rust-analyzer go-to-def, belly's lost affordance), and which do we wait on?

- **Typed tokens: enum vs newtype vs theme-contract trait — and how closed?** Stripe's un-overridable a11y presets enforce the WCAG floor but forbid the 5% a flexible library needs. How constrained is Buiy's token set, and does the contract trait (vanilla-extract) force *total* themes (no `undefined`) at the cost of theme-author friction?

- **Where does the suppression trap (#18779) get caught?** It's silent-wrong by construction and Bevy hasn't fixed it upstream. Is the answer a non-suppressing scene-fn (D5) that never exposes the bare component patch, a loud debug diagnostic (egui's discipline), or both — and does that make `bsn! { Button BoxModel{width} }` a *warning* or simply unidiomatic?

- **One canonical spelling — but which one, given the marker+`#[require]` model?** Scene-fn-as-public-face (feathers) is the corpus answer, but markers must stay authorable in `bsn!` for composition. How do we keep the marker an internal contract without it becoming a second public spelling (the F5 we're trying to kill)?

- **Per-subtree theme override: Resource or inherited component?** Compose `CompositionLocal`/Flutter `InheritedWidget` scope theme to subtrees; ECS offers a global `Resource` (simpler) or an inherited component read by hierarchy query (true per-subtree). Does Buiy need subtree theming in v1, or is a global theme + explicit overrides enough?
