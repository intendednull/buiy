# Buiy render — effect-group compositor

**Parent:** [README.md](README.md)

This file specifies pillar 6: the off-screen effect-group compositor. It owns the target state of `EffectGroup` ([README § 3.2](README.md#32-render-owned-this-spec-introduces)) — how an entity whose subtree must composite atomically gets an off-screen render target, how those targets are allocated, pooled, and evicted, how the per-`EffectGroup` results composite back into the per-window node group, and exactly what v1 carries (group `opacity` + `isolation`, both *correct*) versus what is reserved (`Filter` / `BackdropFilter` / `MixBlendMode`, component + boundary now, shader later).

It does **not** own: the typed-primitive batched node, the per-window node group placement in `Core2d`, or the extract/handoff — those are [architecture.md](architecture.md). It does **not** own paint order or top-layer membership — that is [paint-order-and-top-layer.md](paint-order-and-top-layer.md); the compositor *consumes* `StackingContext.painters_z` to know which entities paint into a group's target and in what order. It does **not** own the texture atlas — atlas allocation, warmup, and eviction are [atlas-and-text-seam.md](atlas-and-text-seam.md). The two are *separate pools with separate mechanisms* (§ 2.3): the atlas uses `guillotiere` + a tunable-grace LRU, while this file's render targets use Bevy's `TextureCache` `frames_since_last_use` pool described below — analogous return-to-baseline discipline, not a shared one.

## 1. The identity: effect-group set ⊇ effect-forming stacking-context set

The decisive, settled fact (pillar 6, [README § 2](README.md#2-architectural-pillars-one-line-summaries)): **the set of entities that need an off-screen render target is the set of *effects* — the stacking-context triggers that are effects, plus `backdrop-filter` (an effect that composites but forms no stacking context, § 1.1).** This is not a coincidence to be re-derived per feature — it is a structural property of compositing, observed independently by WebRender ([prior-art/servo-stylo/rendering.md](../../prior-art/servo-stylo/rendering.md) "Effects force off-screen passes") and Blink's effect property tree ([prior-art/blink/stacking-and-paint.md § 3](../../prior-art/blink/stacking-and-paint.md)): anything that can't be expressed in a single forward shader pass — `opacity < 1` over a group, `filter`, `backdrop-filter`, `mix-blend-mode`, isolation — *must* first rasterize its whole subtree to an intermediate target, then apply the effect to that target as a unit. Stacking-context boundaries **are** the GPU's natural render-pass boundaries.

Layout's stacking sub-pass 6f already enumerates the full SC-trigger union in one place ([layout stacking-and-top-layer.md § 2](../../specs/2026-05-08-buiy-layout-design/stacking-and-top-layer.md)). The compositor does **not** re-enumerate it. It consumes its own marker: an entity carries `EffectGroup` iff it forms a compositing boundary for an **effect** reason.

**Canonical predicate (this file owns it — every other mention cites here).** An entity forms an `EffectGroup` **iff any** of:

1. `Opacity` with `opacity < 1` (**v1, carried**);
2. `Stacking.isolation == Isolation::Isolate` (**v1, carried**);
3. `Filter` non-empty (**reserved**, component ships, no shader);
4. `MixBlendMode != MixBlendMode::Normal` (**reserved**, component ships, no shader);
5. `BackdropFilter` non-empty (**reserved**, component ships, no shader, plus a backdrop-sample seam — § 6).

Of these five formers, **four also form a stacking context** (all but `BackdropFilter`), and **three are render-owned SC-trigger components** — `Opacity` / `Filter` / `MixBlendMode`. The remaining two formers are asymmetric: **isolation is the layout-owned `Stacking.isolation` *field*** (`Isolation::Isolate`), read off the existing `Stacking` component — *not* a render-owned SC-trigger component — and **`BackdropFilter` is `EffectGroup`-only** (a render-owned component that forms a compositing boundary but **no** stacking context, so it is not in layout 6f's SC-trigger union). So the count of distinct *render* SC-trigger components is **three**; isolation contributes a fourth *reason* but no fourth component, and `BackdropFilter` a fifth reason via its own render-owned component. The effect-group former set is therefore a *superset* of the effect-forming SC triggers; the two predicates are deliberately distinct ([component-model.md § 10](component-model.md)). Every other mention (architecture § 5.2, component-model § 8/§ 10) cites this numbered predicate and uses the spelling `Isolation::Isolate`.

Predicate former 5 — `BackdropFilter` — is **the one effect that forms an `EffectGroup` but is *not* a stacking-context trigger**: it forms a compositing boundary (it needs an off-screen target) **without** Buiy treating it as a stacking-context trigger, so it lives in the `EffectGroup` set but not in layout 6f's SC-trigger union. To be precise about the divergence from CSS: **Buiy treats `backdrop-filter` as an effect-group former only; CSS additionally makes it form a stacking context, which Buiy does not rely on because `EffectGroup` membership is derived render-side** (by `WriteEffectGroups`, § 1.1) — the compositor needs only the off-screen-target boundary, not the SC participation, so it derives the boundary directly rather than routing through layout 6f's SC union.

The triggers that form an SC but are *not* effects — positioned + `z_index`, non-identity `Transform`, `contain: paint`/`strict` — do **not** carry `EffectGroup`. They reorder and clip, both of which the forward typed-primitive pass already expresses (paint order via `painters_z`, clip via `ClipRect` from [clip-and-transform.md](clip-and-transform.md)); neither needs an intermediate target. This is the same separation Blink draws between its transform/clip trees and its effect tree, and the same one the layout prior-art insists 6f keep distinct: `Isolation::Isolate` is an effect boundary (→ `EffectGroup`) but does *not* clip, while `contain: paint` clips but is *not* an effect boundary (→ no `EffectGroup`) ([prior-art/blink/stacking-and-paint.md § 1.1](../../prior-art/blink/stacking-and-paint.md)).

### 1.1 Who writes `EffectGroup`

`EffectGroup` (**F**) is a render-owned component carrying `EffectReason`, written by the render-prep system `WriteEffectGroups` ([architecture.md § 5.2](architecture.md)) that runs alongside `WriteClipRects` ([clip-and-transform.md](clip-and-transform.md)) reading only the effect components above. It is *derived state*, not author-set: an author sets `Opacity(0.5)`, and `WriteEffectGroups` inserts/removes the `EffectGroup` component as the effect crosses the trigger threshold (`opacity` rising back to `1.0` removes it). Deriving it render-side (rather than having layout 6f emit it) keeps the marker on the side of the boundary that owns the compositor and avoids a second layout→render component edge; layout 6f independently reads the same `Opacity`/`Filter`/`MixBlendMode` components for its *SC-formation* clause (README § 4 unblock #2), so the two derivations share inputs but not the output.

`WriteEffectGroups` only writes the *boundary* (the `EffectGroup` component). The per-group **geometry** the compositor consumes — each group's painted bounds, its bucketed `TextureDescriptor`, and its post-order index — together with the off-screen render targets themselves, is produced by a separate **prepare-phase system** (`RenderSystems::Prepare`, [architecture.md § 5.2](architecture.md)), **not** at extract time. This split is forced by Bevy's schedule: the `ViewTarget` and the GPU view do **not** exist until `prepare_view_targets` (`RenderSystems::ManageViews`, *after* `ExtractSchedule`), so neither the group render targets nor the GPU instance buffers can be allocated during extract. Concretely:

- **Extract (`ExtractSchedule`)** produces only CPU-side per-view data: it partitions main-world `Node` instances by their target view/window into `ExtractedNodes`, writing them onto the **render-world view entity** obtained via Bevy's main↔render entity mapping (the camera/view extraction maintains that mapping; `RetainedViewEntity` is the *key* into it, **not** an attach target — there is no "keyed alongside `ViewTarget`," because `ViewTarget` does not exist yet). The extracted `EffectGroup` entities, their `GlobalTransform`/`ClipRect`, their `painters_z` member boxes, and the ink-expansion components (`BoxShadow` / `Outline` / reserved `Filter`) are carried across this CPU partition.
- **Prepare (`RenderSystems::Prepare`)** then, with `ViewTarget` available, builds the GPU artefacts: the `BuiyInstanceBuffers`, and the per-`EffectGroup` prepared store (each group's bounds, bucketed `TextureDescriptor`, and post-order index) as a **prepare-phase per-view component on the view render entity** (parallel to `ExtractedNodes` / `BuiyInstanceBuffers`, which [architecture.md § 4](architecture.md) makes per-view components, not global resources). The off-screen targets are acquired here/in the node from `TextureCache`, which likewise needs the render device of the prepared view.

**`BuiyNode::run` reads this prepared per-view store (off the matched view entity); it does *not* walk main-world ancestors from `&World`.** Every "the compositor reads / unions / post-orders" claim below (§ 2, § 3) refers to that already-prepared per-view store, not to a main-world traversal inside the node.

The struct itself is **owned by [component-model.md § 10](component-model.md)**; this file uses it verbatim — the compositor reads `reason` to choose the composite op without re-querying the five effect components per frame:

```rust
bitflags::bitflags! {
    /// One entity can carry several reasons at once (opacity<1 AND isolate).
    pub struct EffectReason: u8 {
        const OPACITY         = 1;  // v1: carried
        const ISOLATION       = 2;  // v1: carried
        const FILTER          = 4;  // reserved: marks the group, no shader in v1
        const BACKDROP_FILTER = 8;  // reserved: marks the group, needs backdrop sample (§ 6)
        const MIX_BLEND       = 16; // reserved: marks the group, no shader in v1
    }
}

/// Render-owned: this entity's subtree composites to its own off-screen
/// target before its effect (opacity / isolation / reserved filter|blend) applies.
/// Derived by `WriteEffectGroups`; never author-set. NO `Default` — absence of
/// the component == no group.
#[derive(Component, Clone, Copy, Debug)]
pub struct EffectGroup {
    /// Which effect(s) made this a group, so the composite step knows what to apply.
    pub reason: EffectReason,
}
```

The `reason` bitflags answer the composite step's only question: *what do I do with this group's target once it's filled?* In v1 the answer is "alpha-composite it at `opacity` (default `1.0`) with `SrcOver` blend." `ISOLATION` alone changes *nothing* about the composite math — an isolated group with `opacity == 1` composites identically to no group at all; isolation's whole effect is what it does to descendants' blending *within* the target (§ 5.2), not to the parent composite.

## 2. The off-screen target lifecycle

Each `EffectGroup` whose subtree is non-empty and not skipped (`Display::None`, `ContentVisibility::Hidden`, or an off-screen `Auto` — see [paint-order-and-top-layer.md](paint-order-and-top-layer.md)) acquires **one** off-screen color target per frame it paints. The lifecycle is acquire → paint subtree → composite → release, all within the render node's execution, all reusing Bevy's existing pooling primitive.

### 2.1 Sizing: painted bounds, not viewport

A group's target is sized to the **group's painted bounds**. **This section is the single source of the painted-bounds formula; every other file defers here ([architecture.md § 5.2](architecture.md)).** The formula is:

> **painted bounds** = ( group **root box** ∪ **transitive descendant boxes** ∪ **ink expansion** ), every term folded through `GlobalTransform`, then **clipped by the group's `ClipRect`** — where the descendant term is the *transitive* union over the group's whole subtree (a nested effect-group child contributes its own composited target's bounds, not its raw subtree; see below).

where **ink expansion** is the per-term margin by which paint escapes the box:

- `BoxShadow`: blur radius + spread;
- `Outline`: `max(0, outline.width + outline.offset)` — a negative/inset offset must **not** enlarge the target;
- `Filter` (reserved): the blur's bleed (margin reserved now so the future blur fits — § 6).

It is emphatically **not** sized to the window. A 24×24 icon at `opacity: 0.6` allocates a ~32×32 target (box + shadow ink), not a 4K render target. This is the single most important sizing decision for gate #15: viewport-sized intermediates are the classic way a compositor's memory blows past a flat budget the moment several groups are live.

Painted bounds come from layout's already-resolved geometry, unioned by the prepare pass (§ 1.1) — the node does not measure. The group root's box is `ResolvedLayout { position, size }`; the descendant union is the bounding box of `painters_z` entries' boxes (each folded through the group-local `GlobalTransform`, [clip-and-transform.md](clip-and-transform.md)); ink expansion reads `BoxShadow`/`Outline`/`Filter` from [component-model.md](component-model.md), with the `Outline` term taken as `max(0, outline.width + outline.offset)` (inset offsets do not grow the target). A group whose `contain: paint` also clips it (the root may be both an effect group *and* a paint-containment box) intersects the painted-bounds union with the group's own `ClipRect` last — clipped descendants cannot enlarge the target.

**The descendant union is *transitive* over the group's whole subtree, not just its direct `painters_z` slice.** A group's `painters_z` slice names the entities that paint *directly* into the group target, but those entities may themselves have descendants whose ink escapes the group root box (a deeply-nested `BoxShadow`, an absolutely-positioned child that overflows). The union therefore recurses the full subtree: it folds in every descendant's box + ink, not only the top-level `painters_z` entries. The one place the recursion *stops* is at a **nested effect-group boundary**: a nested-SC effect-group child does **not** contribute its raw subtree boxes here, because it composites to *its own* pooled target first (§ 3 step 1) and appears to this group as a single composited sample. Such a child contributes via **its own composited target's bounds** — the nested group's already-computed painted-bounds rect (folded through the group-local transform), which itself transitively covers *its* subtree's ink. So nested-SC ink that escapes the root box is never under-sized: it is accounted either directly (non-group descendants fold into this union) or by reference (a nested group contributes its own target's bounds, computed by the same recursion one level down).

**The ink-expansion terms must already be resolved px before the sizing pass runs.** `Outline.width`/`Outline.offset`, `BoxShadow.blur`/`BoxShadow.spread`, and `Radius` are `Length`s, and `Length` includes `Percent`/`Cq*` variants that the sizing pass — which works in resolved-px rects — **cannot** resolve on its own (a `Cq*` term needs the container-query context the layout pass owns, a `Percent` term needs the relevant base). So the prepared store (§ 1.1) holds **resolved-px ink terms**, not raw `Length`s: the same unit resolution [component-model.md](component-model.md) cites for these paint fields runs upstream, and the compositor's painted-bounds union reads only the already-resolved px values. This keeps the sizing pass a pure geometry fold with no `Length`-resolution dependency.

**Logical → physical: fold in `scale_factor` CPU-side.** `GlobalTransform` is **logical px** ([clip-and-transform.md § B.4](clip-and-transform.md)), so the union above is a logical-px rect. The off-screen target is a GPU texture measured in *physical texels*, so the prepare pass multiplies the logical painted-bounds rect by the window's `scale_factor` — read **explicitly CPU-side** from the extracted view/window (the same `scale_factor` clip-and-transform § B.4 folds into the GPU view uniform; here it is also read CPU-side for target sizing). The product is snapped out to integer texel bounds, giving the `Extent3d` the `TextureDescriptor` (§ 2.2) uses. This is the one place the logical-px convention is converted to device texels on the CPU; the GPU pass then renders the group's subtree at physical resolution into the correctly-sized target. (On a 2× display the 24×24-logical icon above allocates a ~64×64-physical target.)

> **Open — sub-pixel/transform-scaled bounds calibration.** When a group root carries a `scale()` or non-axis-aligned `rotate()`, the *tight* painted bounds in target space versus the *device* bounds it composites into is a quality/memory tradeoff (render at target-local resolution then transform, vs. render pre-magnified). v1 sizes the target to the group-local untransformed bounds and applies the group transform at composite time; the magnified-quality variant is deferred. Flagged against [README § 5 #4](README.md#5-open-questions) (per-fixture perf/leak calibration).

### 2.2 Allocation + pooling: the `frames_since_last_use` pool

Targets are **pooled and reused**, never allocated fresh per group per frame in steady state. Buiy reuses Bevy 0.18's existing render-target pool — `bevy_render::texture::TextureCache` (`crates/.../bevy_render-0.18.1/src/texture/texture_cache.rs`) — rather than inventing a parallel one. `TextureCache::get(&render_device, descriptor)` returns a `CachedTexture { texture, default_view }`, reusing any non-`taken` texture whose `TextureDescriptor` matches exactly (same size, format, usage), or creating one on a miss. This is the right primitive because:

- **Descriptor-keyed reuse** means two groups that resolve to the same snapped size + format share the pool bucket and recycle each other's targets frame-to-frame. The compositor snaps painted bounds to a small set of **bucket sizes** (next-power-of-two per axis) precisely so the descriptor matches across frames and across groups — a continuously-resizing target would defeat reuse by minting a fresh descriptor every frame. **The cap rule:** next-pow2 bucketing is capped at the view's physical size — a group whose painted bounds exceed the viewport on an axis is capped to the **view size on that axis** (one stable bucket) rather than pow2-rounded past the viewport. Capping to the view dimension (not to the group's *exact* clipped bounds) is deliberate: a per-group exact size would mint a fresh `TextureDescriptor` for every distinct near-viewport size and defeat `TextureCache` reuse, whereas the view-size cap collapses all overflowing groups on that axis onto a single shared bucket that recycles frame-to-frame. Rounding a near-viewport group up to the *next* power of two, by contrast, would allocate a target larger than the window for no reuse benefit. This bucket-size cap is a **calibration knob distinct** from README's per-fixture perf/leak thresholds ([README § 5 #4](README.md#5-open-questions)): the cap governs *per-target* sizing geometry, the README thresholds govern *aggregate* live-set memory and slope. **The bucket *rule* — next-pow2 per axis, capped at the view's physical size — is committed here**; what is deferred to README § 5 is only (a) the *numeric* pow2 thresholds (the smallest bucket, the rounding steps) and (b) the transform-magnification quality variant (§ 2.1's open — render pre-magnified vs. render-then-transform). The rule's shape is fixed; only those two knobs calibrate.
- **Eviction is automatic and bounded.** `TextureCache::update()` (run by `update_texture_cache_system` in the render app's cleanup, which Buiy's per-window node group does **not** override) increments every entry's `frames_since_last_use`, marks all `taken = false`, and `retain`s only entries with `frames_since_last_use < 3`. So a target unused for 3 consecutive frames is dropped and its GPU memory returns. A group that stops being a group (`opacity` animates back to `1.0`, `EffectGroup` removed) frees its target within three frames with zero bespoke bookkeeping. **Settle time is pool-specific:** this RT pool settles in 3 frames, while the glyph atlas ([atlas-and-text-seam.md § 2.4](atlas-and-text-seam.md)) settles only after its tunable `config.eviction_grace`. A gate-#15 fixture asserting return-to-baseline across *both* pools must therefore wait `> max(atlas eviction_grace, RT-pool 3 frames)` before sampling — the two pools have independent settle windows and the shorter one settling does not imply the other has.

  **Dependency note.** This pooling discipline assumes the `bevy_render` texture-cache plugin (`TexturePlugin`) is present, since it is the plugin that registers `update_texture_cache_system` into `RenderSystems::Cleanup` — the only thing that increments `frames_since_last_use` and `retain`s the pool. That holds **under `DefaultPlugins`** (`TexturePlugin` ships in `RenderPlugin`'s default set), so no extra wiring is needed for the normal app. It is, however, a **tracked dependency for any reduced plugin set**: an app that strips the texture-cache plugin would leave taken-but-never-returned targets and break both the eviction guarantee above and gate #15's return-to-baseline. Buiy does not add its own copy of this system; it relies on the standard one.

The target descriptor is fixed:

```rust
TextureDescriptor {
    label: Some("buiy_effect_group_target"),
    size: Extent3d { width, height, depth_or_array_layers: 1 }, // bucketed painted bounds
    mip_level_count: 1,
    sample_count: 1,
    dimension: TextureDimension::D2,
    format: TextureFormat::Rgba16Float, // FIXED linear — NOT view_target.main_texture_format()
    usage: TextureUsages::RENDER_ATTACHMENT  // group subtree renders into it
         | TextureUsages::TEXTURE_BINDING,   // composite pass samples it
    view_formats: &[],
}
```

The group/intermediate target format is **pinned `Rgba16Float` (linear), FIXED regardless of the view's SDR/HDR setting** — it is *not* `ViewTarget::main_texture_format()`. The view's actual working target is `Rgba8UnormSrgb` SDR by default (`Camera2d` does not add `Hdr`; [color-and-forced-colors.md](color-and-forced-colors.md)), but a group target must be linear `Rgba16Float` so that group `opacity` and `isolation` composite in **linear space** — the only space where the off-screen group-opacity/isolation composite is correct (a sub-unity group alpha applied in an encoded/sRGB attachment would composite wrong). The descendant subtree renders into this linear group target, then the **final composite of a group back into its parent target `SrcOver`-blends in the parent target's space** (the next enclosing group's linear `Rgba16Float`, or the window's actual attachment — `Rgba8UnormSrgb` SDR by default — at the root). The whole tree then participates once in whatever tonemapping the view enables at the end (`None` by default for `Camera2d`; § 4, [color-and-forced-colors.md § 1.2](color-and-forced-colors.md)).

**Pipeline per target format (a wgpu constraint, not a choice).** A `RenderPipeline`'s fragment `ColorTargetState.format` is fixed at pipeline creation and **must equal the bound attachment's format** — one pipeline cannot target both `Rgba8UnormSrgb` (the view) and `Rgba16Float` (a group target). Because Buiy's typed-primitive batched pass ([architecture.md § 1.4](architecture.md)) paints into *both* — the view attachment for the main pass and a group's `Rgba16Float` target for an effect group's subtree — **each typed-primitive pipeline (`quad` / `shadow` / `glyph` / `path`) is a `SpecializedRenderPipeline` keyed (at least) on the target `ColorTargetState` format.** Buiy therefore builds each primitive for **both** formats it targets: the view format (`Rgba8UnormSrgb` by default) for the main pass and `Rgba16Float` for effect-group targets. The specialization key carries the target format so `specialize()` emits the correct `ColorTargetState` per pass; architecture § 1.4 and [color-and-forced-colors.md § 1.1](color-and-forced-colors.md) cite this same per-format-specialization rule.

**The blend-space seam (bounded, accepted v1 approximation).** The flip side of pinning group targets linear while the default view attachment is encoded SDR is a blend-space discontinuity: **a child quad painting direct-to-window blends in the attachment's encoded (sRGB) space, while the same quad inside an effect group blends in linear.** So wrapping content in an `opacity: ~1` group subtly changes how its overlapping pixels blend (overlaps darken/lighten differently when blended linearly vs. encoded). v1 accepts this as a **documented approximation** — the seam is bounded to *grouped vs. ungrouped* content and is invisible for the common case of non-overlapping or single-layer content. The only fully-correct alternative — **paint *all* content into linear intermediates and resolve once at the end** (no direct-to-window encoded blending anywhere) — is noted as the **revisit path**: it removes the seam at the cost of an always-on full-view linear intermediate, which v1 declines because the default `Camera2d` view is SDR and most content paints direct-to-window. The seam is recorded here so the discontinuity is understood as *accepted*, not accidental, with a known fix.

### 2.3 Why this makes gate #15 satisfiable

Gate #15 ([foundation verification.md gate #15](../2026-05-07-buiy-foundation/verification.md), [README § 5 #4](README.md#5-open-questions)) requires RSS slope `< 1 MB/min` after warmup and **atlas/target entries to return within ε of baseline** after a long-running fixture settles to idle. The pooling design satisfies it by construction, not by a leak-hunt:

1. **Bounded working set.** Live target memory is `Σ (bucketed painted-bounds area × bytes/texel)` over *currently-painting* groups, plus at most a few frames of slack from not-yet-evicted buckets. It is a function of how many groups are simultaneously on-screen, not of frame count or session length — so the slope is flat once the scene stops changing.

   **The aggregate live-set budget — `rt_pool_budget` (committed here).** The per-target bucket cap (§ 2.2) bounds *each* target's size, and `frames_since_last_use < 3` eviction (§ 2.2) bounds how long a *transient* target lingers — but neither caps the **concurrent-groups axis**: N simultaneously-painting groups allocate N live targets, and nothing above forbids N from being unbounded. So this file commits an explicit aggregate cap, `rt_pool_budget` (**bytes**; v1 default **64 MiB**), parallel to the atlas `page_budget` ([atlas-and-text-seam.md § 2.4](atlas-and-text-seam.md)): the *shape* — a byte budget on the concurrent live target set, with a defined degradation under pressure — is fixed here; only the *tuned number* defers to `buiy-verification-design` (exactly like the atlas `page_budget`'s tuned page count, [README § 5 #4](README.md#5-open-questions)).

   **Degradation under pressure (forward-compositing fallback).** When acquiring the next group's target in the prepare pass would push live target bytes past `rt_pool_budget`, the lowest-cost effect groups **fall back to direct-to-parent forward compositing** instead of allocating a target: the group's subtree paints directly into its parent target and the group `opacity` is applied **per-instance** (each painter's alpha multiplied by `group.opacity` in the forward pass) as the **documented approximation** — exactly the per-child approximation § 4 rejects for the *correct* default, accepted here *only* under budget pressure as the graceful-degradation path rather than failing to render. "Lowest-cost" ranks groups by reuse cost — smallest painted-bounds area and `OPACITY`-only reason first (an `OPACITY`-only group degrades to a visible-but-approximate overlap; an `ISOLATION`/reserved group degrades last because its boundary is structural, not just an alpha multiply). This brings the RT pool to parity with the atlas page-budget + LRU-under-pressure story: a hard byte ceiling, plus a defined behavior when the working set would exceed it, rather than unbounded growth or an allocation failure.
2. **Return-to-baseline.** When activity stops, no new `EffectGroup`s appear; within 3 frames every transiently-allocated target's `frames_since_last_use` reaches 3 and `update()` drops it. Bucket count returns to the steady-state working set, which *is* the baseline. The glyph atlas ([atlas-and-text-seam.md](atlas-and-text-seam.md)) gives gate #15 the *same return-to-baseline guarantee* but through a **distinct pool with a distinct mechanism** — these are two pools, not one shared eviction model: render targets ride Bevy's `TextureCache` (`frames_since_last_use < 3` retain), while the atlas uses `guillotiere` allocation plus a tunable-grace LRU (`config.eviction_grace`). Both satisfy "entries return within ε of baseline"; neither shares the other's allocator or policy.
3. **No unbounded growth path.** Because sizing is painted-bounds (§ 2.1) not viewport, and reuse is descriptor-keyed, an adversarial fixture that opens and closes a thousand opacity groups over ten minutes never accumulates a thousand live targets — it recycles a handful of buckets. This is the explicit counter to WebRender's documented cost ("GPU memory for atlases and intermediate targets … a real ceiling," [prior-art/servo-stylo/rendering.md](../../prior-art/servo-stylo/rendering.md)).

Concrete per-fixture numbers (max live targets, bucket cap, ε) are owned by `buiy-verification-design` and calibrate over time ([README § 5 #4](README.md#5-open-questions)); this file commits the *mechanism* that keeps them achievable.

## 3. Composite pass ordering within the per-window node group

The compositor's passes execute **inside** the per-window `BuiyRenderLabel` node group — they are `BuiyNode::run`'s ordered passes (group-subtree, group-composite, top-layer steps below), or a sibling pass within that same node group, **not** a separate competing `ViewNode` added to `Core2d`. The compositor never registers its own graph node. `compositor::register` registers **only pipelines and resources** (composite pipeline, bind-group layouts, the `TextureCache` is already global) — it adds **no** node and **no** edge to the render graph. The node group itself, and its edges, are owned by [architecture.md § 1.3](architecture.md), which pins it into `Core2d`. That section is the single owner of the graph edges; this file cites them and does not re-own them. The pinned edges are: an after-anchor `add_render_graph_edge(Core2d, StartMainPassPostProcessing, BuiyRenderLabel)` and the load-bearing `add_render_graph_edge(Core2d, BuiyRenderLabel, Tonemapping)`, plus a conditional `add_render_graph_edge(Core2d, Bloom, BuiyRenderLabel)` that is inert unless a 2D bloom plugin adds the `Bloom` node. `Node2d::Bloom` and `Node2d::PostProcessing` are **optional-plugin nodes** — reserved labels with no edges in the base `Core2d` graph — that only appear in the graph when their owning plugin adds them; the conditional `Bloom → BuiyRenderLabel` edge ensures that *if* a 2D bloom node is present Buiy paints after it. The consequence (approved pillar 2): Buiy paints inside the post-processing window, before tonemapping, so it does **not** bloom — when a bloom node is present, bloom processes the scene first and Buiy paints on top, so text and edges stay crisp. Buiy paints into the view's actual color attachment — `Rgba8UnormSrgb` SDR by default (`Camera2d` adds no `Hdr`), with the hardware OETF running at the attachment write — so it **participates** in whatever tonemapping / color-management the view enables. On the default `Camera2d` (`Tonemapping::None`) there is no shared encode pass; the placement before `Tonemapping` is the **seam** for opt-in HDR / wide-gamut (where the attachment becomes linear `Rgba16Float`) rather than a claim that v1 tonemaps the UI ([color-and-forced-colors.md § 1.2](color-and-forced-colors.md)). The effect-group intermediate targets remain pinned linear `Rgba16Float` regardless (§ 2.2), so group compositing is linear-correct even on the SDR view.

**Why one `ViewNode`, not a small fixed subgraph.** The composite runs as ordered passes inside the single `BuiyRenderLabel` `ViewNode` rather than as a small fixed subgraph of one render-graph node per pass (subtree-rasterize node → composite node → top-layer node, wired with explicit edges). The runner-up — the fixed subgraph — is *not* foreclosed lightly: it would let the render graph schedule the passes and manage inter-pass texture-state transitions for us. We choose the single node because the number of group passes is **data-dependent** (one per live `EffectGroup`, varying per frame), which a static subgraph of fixed nodes cannot express without re-building edges per frame; a single node iterating the prepared post-order handles a varying group count naturally. **The accepted cost of this choice:** the inter-pass texture-state transitions (render-attachment ↔ texture-binding as a group target flips from being written to being sampled) and the target-reuse hazards (§ 2.2 pooling within one frame) are **hand-rolled and managed manually inside `run()`**, not delegated to the graph's automatic dependency tracking. We take that cost because the passes are linear and their dependency order is exactly the prepared post-order; the manual transitions are mechanical, not a scheduling problem.

**Target residency across the run (no mid-run recycling).** All effect-group targets for the frame are **acquired up-front** — in the prepare pass (§ 1.1) or at the very start of `run` before any subtree pass — and **held for the whole composite**, then released after the run completes. This is load-bearing: a child group's target is filled in an early post-order iteration and then **sampled** by its parent's composite in a later iteration, so it must stay resident the whole time. If targets were acquired and released per-iteration, the `TextureCache` could recycle a just-released child target into a same-descriptor sibling before the parent samples it — a use-after-recycle within a single frame. Holding every group's `CachedTexture` (marked `taken` for the frame by `TextureCache::get` in `bevy_render`'s `texture/texture_cache.rs`) from acquisition through the final composite forbids that. Release happens implicitly at frame end via `update_texture_cache_system` (§ 2.2), which marks all entries `taken = false` again for the next frame.

Within one window's node execution, ordering is:

1. **Group subtree passes, innermost-first (bottom-up).** For each live `EffectGroup`, in an order that resolves children before parents (a group nested inside another group must be fully composited before its ancestor rasterizes, because the ancestor samples the child's *composited* result, not its raw subtree), the node:
   - uses the group's pooled target (acquired up-front per the residency rule above, § 2.2);
   - clears it transparent;
   - runs the typed-primitive batched pass ([architecture.md](architecture.md)) over the group's `painters_z` slice, into the group target instead of the window target. Nested `EffectGroup` descendants are *not* re-rasterized here — they appear as a single composited sample (step handled when their own, earlier, iteration ran).
2. **Group composite into parent target.** Each filled group target is drawn as one textured quad into its **parent target** (the next enclosing group's target, or the window's `ViewTarget::main_texture_view()` at the root), at the group's device position, applying the effect named by `EffectReason` — in v1, multiply sampled alpha by the prepared `group.opacity` (the value of `Opacity.0`, accessed as the tuple field — `Opacity` is `pub struct Opacity(pub f32)`, no `.value`) and blend `SrcOver`. This is the per-group equivalent of GPUI's "scene-level draw-order" composite ([prior-art/gpui/gpu-rendering.md](../../prior-art/gpui/gpu-rendering.md)), but with a real intermediate target so the group is alpha-composited as a unit (§ 5.1).
3. **Top-layer composite pass.** After the root window target holds the fully-composited normal-flow tree, the one ordered top-layer composite pass ([paint-order-and-top-layer.md](paint-order-and-top-layer.md)) draws top-layer entries above it in top-layer order. Top-layer entries that are *themselves* effect groups (a modal at `opacity: 0.9`) composite their own target in step 1 like any other group, then draw in this step in top-layer order — the two mechanisms compose without special-casing. **`::backdrop` is OPEN for v1** ([paint-order-and-top-layer.md § 4](paint-order-and-top-layer.md)): v1 ships **no** dimming `::backdrop` box — this step draws only the top-layer entries themselves, not a backdrop pseudo-element behind each. The verification golden for this step (the modal-over-popover fixture, § Verification / [paint-order-and-top-layer.md § 6](paint-order-and-top-layer.md)) therefore asserts **tier order only** (modal paints above popover paints above normal flow), **not** `::backdrop` nesting or dimming. When the `::backdrop` model is settled it slots in as an extra draw *before* each top-layer entry within this same pass; nothing in the pass structure changes.

The "bottom-up, children before parents" order is the compositing inverse of `painters_z`'s forward paint walk, and it is derivable from the same structure: a group's target depends on its descendant groups' targets, so a post-order traversal of the effect-group nesting (itself a sub-forest of the stacking tree `painters_z` encodes) yields the dependency-correct order. **The node does not compute this order at run time** — the prepare pass (§ 1.1) already post-orders the `EffectGroup`-bearing entities by their position in the stacking nesting and stores each group's post-order index in the prepared per-view store; `BuiyNode::run` iterates that precomputed index, never walking the main world from `&World`.

```rust
/// Runs inside the per-window BuiyRenderLabel node group, pinned after
/// Node2d::StartMainPassPostProcessing and before Node2d::Tonemapping
/// (load-bearing BuiyRenderLabel -> Tonemapping; architecture.md § 1.3 owns the edges).
/// Sketch of `ViewNode::run`. The prepared per-view store (§ 1.1) is read
/// off the matched view entity (a per-view component, not a global resource) —
/// already post-ordered, sized, and descriptor-bucketed;
/// `run` does NOT walk main-world ancestors from `&World`.
fn run(&self, graph, render_context, (view_target, prepared): QueryItem, world) -> Result<(), NodeRunError> {
    let groups = &prepared.effect_groups; // post-ordered, with bounds + descriptor (§ 1.1)
    // 0. acquire ALL group targets up-front and hold them resident for the whole
    //    composite — a child target filled in step 1 is sampled by its parent in
    //    step 2, so it must NOT be recycled mid-run (§ 3 residency rule).
    let targets: Vec<CachedTexture> = groups.iter()
        .map(|g| texture_cache.get(device, &g.descriptor)) // pooled (§ 2.2), marked `taken`
        .collect();
    // 1. innermost-first: each group's subtree → its (already-acquired) pooled target
    for group in groups.post_order() {                      // children before parents
        let target = &targets[group.index];
        render_context.command_encoder()... // clear + typed-primitive pass into `target`
    }
    // 2. composite each group target into its parent target, applying EffectReason
    for group in groups.post_order() {
        composite_quad(group.parent_target, &targets[group.index], group.opacity, SrcOver);
    }
    // (targets stay resident until end of run; `update_texture_cache_system` un-`taken`s
    //  them in RenderSystems::Cleanup for next frame — § 2.2)
    // 3. top-layer composite into the root window target (see paint-order-and-top-layer.md)
    // ... still pre-tonemapping; Node2d::Tonemapping consumes the result.
    Ok(())
}
```

## 4. v1 semantics: correct group opacity (not the rejected approximation)

The settled, user-approved decision (pillar 6 runner-up explicitly rejected): **v1 group opacity is correct, not a forward per-child approximation.**

- **Correct (shipped):** the whole group rasterizes to its target at full opacity, *then* the entire target is alpha-composited into the parent at the group's `opacity`. Overlapping children inside the group blend among themselves at full alpha first; the group's translucency applies once, to the composed result. A button label overlapping its background inside an `opacity: 0.5` group shows the *group* at half opacity — the overlap region does not double-darken.
- **Rejected (the approximation we do not ship):** multiplying each child's own alpha by the group `opacity` in the forward pass and skipping the intermediate target. This is cheaper (no off-screen pass, stays batched) but **wrong** wherever group descendants overlap: each overlapping pixel composites twice at reduced alpha, so the overlap shows through. CSS group opacity is defined as the former; the user chose correctness-from-day-one over the forward-pass speed, accepting the off-screen pass cost. This is recorded so the cost of the intermediate target is understood as *bought*, not accidental.

`isolation` in v1 is the second carried effect and is even simpler: it forms an `EffectGroup` (so its subtree rasterizes to an isolated target) but applies **no** parent-composite effect beyond `SrcOver` at `opacity` (default `1.0`). Its entire observable v1 behavior is the *isolation* itself — § 5.2.

## 5. What v1 actually guarantees

### 5.1 Group opacity over overlapping children

Given an `EffectGroup` with `EffectReason::OPACITY` and `Opacity(a)`, every entity in the group's `painters_z` slice paints into the group target at its own resolved alpha; the target is then composited into the parent once at `a`. The verification target (gate #2, [verification.md](verification.md)) is a golden fixture with two overlapping opaque children inside an `opacity: 0.5` parent: the overlap region must equal the single-layer color at 50%, **not** a doubled composite. That golden is the regression guard that the off-screen pass — not the rejected approximation — is what shipped.

### 5.2 Isolation creates an isolated group

`Isolation::Isolate` makes the group target the blending root for its descendants: any descendant `MixBlendMode` (a reserved C-tier effect) blends only against siblings *within* the isolated target, never against content painted behind the group in the parent. In v1, with no blend shader, isolation's *visible* effect is nil for a tree that uses only `SrcOver` — an isolated group of straight-alpha children composites identically to the same children un-isolated. The v1 guarantee is structural, not pixel-visible: the group **boundary** exists and the descendants rasterize into a separate target, so when `MixBlendMode` lands (§ 6) its blend is already correctly scoped without re-architecting. This is exactly why the compositor is built in v1 even though only opacity is pixel-observable: isolation reserves the blend-isolation seam.

## 6. Reserved seams: filter / backdrop-filter / mix-blend-mode

These three are **C-tier reserved** ([README § 3.2](README.md#32-render-owned-this-spec-introduces), foundation [visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering)). v1 ships their **component model** ([component-model.md](component-model.md): `Filter`, `BackdropFilter`, `MixBlendMode`) and their **`EffectGroup` boundary** (each sets its `EffectReason` bit and allocates a target exactly as opacity/isolation do), but **no shader**. The deferral is deliberate and the seam is shaped so adding the shader later needs no re-architecture:

- **`filter` (`EffectReason::FILTER`).** The group already rasterizes to its own target. A filter (blur, brightness, drop-shadow, …) is a fragment-shader pass applied to that target *before* the composite quad in step 2 — a new pass slotted between "target filled" and "target composited," reading the target, writing a filtered target (a second pooled allocation from the same `TextureCache`), then compositing. v1 already sizes the target with filter-blur ink expansion in painted bounds (§ 2.1) so the future blur has the margin it needs. **Adding a filter is: write the shader, insert one pass.** No change to allocation, pooling, ordering, or the marker.
- **`mix-blend-mode` (`EffectReason::MIX_BLEND`).** The composite quad in step 2 already chooses a blend op (`SrcOver` in v1). A blend mode is a *different blend op* on that same quad against the parent target, scoped correctly because isolation (§ 5.2) defines the blending root. **Adding a blend mode is: extend the composite blend-op selection.** The isolation boundary it needs already ships v1.
- **`backdrop-filter` (`EffectReason::BACKDROP_FILTER`) — the one seam that needs more than v1's machinery.** A backdrop filter blurs the *content behind* the element, not the element's own subtree. So unlike `filter`, it cannot be expressed by sampling only the group's own target — it must **sample the parent target's region under the group** *before* the group's descendants paint over it, filter that sample, then composite the group on top. The seam this file reserves: the composite step has access to the parent target (it composites *into* it), and Bevy's `ViewTarget` already provides the ping-pong primitive this needs — `ViewTarget::post_process_write()` (verified in `bevy_render-0.18.1` `view/mod.rs`) hands a read-source/write-destination pair so a pass can sample what's already drawn while writing forward. **Adding backdrop-filter is: before step 1 rasterizes the backdrop group's subtree, sample the parent region (via the post-process-write source), run the filter shader into a backdrop scratch target, and use it as the group's cleared background instead of transparent.** The note to carry forward: backdrop-filter is the only reserved effect whose *input* is the parent rather than the subtree, so it is the one that must read the parent target — every other effect reads only its own group target. The component and `EffectReason::BACKDROP_FILTER` bit ship v1 precisely so this ordering constraint (backdrop group composites against an already-painted parent region) is reserved now, not retrofitted.

  **Honest caveat — the nested-parent case is *not* solved by the v1 primitive.** The ping-pong above (`ViewTarget::post_process_write`, verified in `bevy_render-0.18.1` `view/mod.rs`) is a method on **`ViewTarget`** — it exists only for the window's main color attachment, where the read-source/write-destination pair lives. When a backdrop group's **parent is another group's pooled `Rgba16Float` target** (a nested effect group, not the window `ViewTarget`), there is **no** `post_process_write` ping-pong to sample the already-painted parent region: a pooled `TextureCache` target is a single texture with no swap pair, and sampling a render-attachment you are also writing is forbidden. Resolving this nested case needs an **extra scratch target** — a copy of the parent group's painted region taken *before* the backdrop group paints over it — which the reserved `BACKDROP_FILTER` descriptor must later add (a second pooled allocation, sized to the backdrop group's bounds, read as the filter input). So the "no re-architecture" claim is honest only for the **window-attachment-parent** case; the nested-group-parent case is a *known, scoped* addition (one extra scratch target + the copy pass), reserved here rather than silently assumed away — it changes neither the marker nor the pool's mechanism, but it *is* more than "one shader," and this file records that rather than overclaiming.

No reserved effect changes the marker, the pool, the sizing, or the pass *structure*; each is "one shader + (for backdrop) one parent-sample" — with the single scoped exception above: a backdrop group whose parent is *another pooled group target* additionally needs one extra scratch target (since `post_process_write` is `ViewTarget`-only). That exception is the one place a reserved effect adds an allocation rather than just a shader, and it is recorded explicitly so the seam test stays honest.

## Verification

How the claims here are proven, mapped to the CI gates ([foundation verification.md](../2026-05-07-buiy-foundation/verification.md), [verification.md](verification.md)):

- **Group-opacity correctness (gate #2 visual-regression).** The overlapping-children-under-`opacity:0.5` golden (§ 5.1) is the regression guard that the off-screen pass shipped and the rejected per-child approximation did not. A second golden with three nested opacity groups verifies the bottom-up composite order (§ 3).
- **`EffectGroup` derivation (gate #1 unit + gate #5 layout-snapshot adjacent).** `WriteEffectGroups` is headless-testable with no GPU: assert that `Opacity(0.5)` yields `EffectGroup { reason: OPACITY }`, `opacity` back to `1.0` removes the marker, `Isolation::Isolate` yields `ISOLATION`, and `contain: paint` / positioned-`z_index` yield **no** `EffectGroup` (the § 1 separation). This is the headless half — no wgpu adapter needed ([README goal #6](README.md#goals)).
- **Pooling + return-to-baseline (gate #15 RSS/atlas).** The long-running fixture opens and closes opacity groups, then idles; the assertion is RSS slope `< 1 MB/min` and live target-bucket count returning within ε of the steady-state working set after the pool settles — for the RT pool alone that is `frames_since_last_use < 3` (§ 2.3), but because gate #15 also covers the atlas, a fixture asserting return-to-baseline across both pools must sample only after `> max(atlas eviction_grace, RT-pool 3 frames)` of idle (§ 2.2, [atlas-and-text-seam.md § 2.4](atlas-and-text-seam.md)). The bucket count is observable as the `TextureCache` entry count for the `buiy_effect_group_target` descriptor family.
- **No re-architecture for reserved effects (review-time, not a runtime gate).** The seam claims in § 6 are verified structurally: the `EffectReason` bits, the painted-bounds ink expansion, and the parent-target access in the composite step exist in v1 code, so the C-tier follow-up PRs add shaders and (for backdrop) one parent-sample without touching the marker, pool, sizing, or pass structure.
