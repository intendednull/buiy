# Buiy — render-pipeline design

**Date:** 2026-06-03
**Status:** draft
**Parent:** [`2026-05-07-buiy-foundation`](../2026-05-07-buiy-foundation/README.md) — sub-spec graduated from [foundation/visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering) and the foundation roadmap row [`buiy-render-pipeline-design`](../2026-05-07-buiy-foundation/README.md#4-sub-spec-roadmap).

## Purpose

Define the target shape of Buiy's render pipeline: the GPU paint and compositing layer that consumes the immutable geometry the layout subsystem produces and turns it into pixels. This covers the render/paint/compositing rows of [foundation/visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering) — per-element clipping, top-layer compositing, atlasing, box-shadow, opacity, borders, backgrounds, outlines — plus the Bevy render-graph integration and the render-side component model that the layout subsystem's stacking-context formation already reaches for.

This spec describes the **target state** — what the render subsystem looks like once complete. Phase 0 ships a minimal real subset (a single instanced SDF rounded-rect `ViewNode` in `Core2d`, extracting `(Visual.background_token, border_radius, ResolvedLayout.position/size)`); the migration from Phase 0 to target lives in plans, not here.

### The contract, in one sentence

**Layout writes immutable paint inputs; render reads them and never re-derives paint order, stacking, or geometry.** This is the BlinkNG "immutable outputs" principle ([prior-art/blink/lessons.md](../../prior-art/blink/README.md)) — Buiy enforces it from day one rather than retrofitting it over a decade. Every architectural decision below serves that contract.

## 1. Goals and non-goals

### Goals

1. **Cover the [foundation visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering) render rows end-to-end at their tier.** Every tier-F paint/compositing item maps to a concrete component, pass, or render-graph node in this spec. Tier-C items are named with a deferral marker and a reserved seam so the deferred work does not require re-architecting. Tier-E items are named only.
2. **Render is a thin read-only consumer of layout's immutable output.** Render never re-sorts `painters_z`, never re-derives stacking, never recomputes geometry. If render needs a derived value (clip rect, composed transform), layout (or a layout-adjacent render-prep pass that reads only layout output) computes it and writes it to a component render extracts.
3. **Integrate with Bevy 0.18's render stack, not bevy_ui's.** Buiy owns its render passes inside Bevy's render graph (`RenderApp` + `ExtractSchedule` + `Core2d` node group), reusing `bevy_render` primitives (`PipelineCache`, `RenderDevice`, `ViewNode`) but none of bevy_ui's renderer — exactly because bevy_ui caps non-rect clipping, backdrop-filter, mix-blend-mode, isolation, and true top-layer compositing.
4. **Per-window by construction.** Render-graph node ordering, instancing, and top-layer root attachment are owned by a per-window node group keyed by winit `WindowId`. No global render state assumes a single Buiy window. *v1 scope:* Buiy UI is painted only into the **primary** window — a second window's view runs `BuiyNode` but receives **no** extracted instances until the per-window instance partition is wired (the structure is reserved here; the wiring is the per-window-routing tracked dependency, § 5 #1).
5. **Unblock three render-gated layout follow-ups outright, and reserve the seam for the fourth.** Landing this spec's component model and passes lets the layout subsystem wire **three** outright: `UiTransform` paint + `Containment` PAINT clip + perspective/backface; render-side SC formers (`opacity`/`filter`/`mix-blend-mode`); and the `Transform`/`GlobalTransform` bridge. Non-px translate resolution is **not** in this set — it is pure layout-side (resolve percent/`Cq*` `Translate` against the entity's own `ResolvedLayout` box; needs neither the `Transform` bridge nor the coordinate contract), so this render spec does not gate it. The **fourth** — `will-change` layer-promotion + SC-former — is only *reserved* here (its promotion-hint seam), not unblocked: the `will-change` SC-former stays tier-E / deferred per the layout spec. See § 4.
6. **Verifiable headless and on GPU.** The device-free set is unit/integration-testable headless (no wgpu adapter on CI runners): the component model, `ClipRect` / `AncestorClip` geometry, the instance/coordinate math, and main-world system schedule membership/ordering. Pipeline **and** render-graph node/edge registration are **not** device-free — they need the `RenderApp` sub-app that only exists once `RenderPlugin::build` acquires a wgpu adapter, so those assertions ride the `#[ignore]` GPU e2e path (architecture.md § 7, verification.md § 2.1). Pixel correctness is proven by a golden-image e2e harness on a canonical CI GPU (gate #2). The spec defines which layer proves which property.

### Non-goals

- **Phase planning.** Plans (`docs/plans/`) decide what subset ships when. This spec is target-shape only.
- **Glyph shaping and text layout.** `buiy-text-rendering-design` owns cosmic-text integration, shaping, font fallback, and BiDi. This spec owns *only* the shared texture atlas and the glyph-alpha primitive seam that text paint plugs into.
- **Layout geometry.** `buiy-layout-design` owns `ResolvedLayout`, `ResolvedTransform`, `StackingContext`, `Containment`, `Overflow`, `ScrollOffset`, and the stacking-context trigger union. This spec *consumes* them and *contributes* the render-side trigger-5 components layout reads back.
- **Animation.** `buiy-animation-design` owns interpolation and the property-tree question (foundation § 5 'Animation library substrate'). This spec ships **no property trees** in v1 (see pillar 7) and renders the current frame's resolved values.
- **Hit-testing mechanism.** `buiy-input-events-design` owns picking. This spec fixes the *ordering identity* (hit-test order = paint order reversed) so the two cannot diverge, but picking's backend lives there.
- **The C-tier effect shaders.** `filter`, `backdrop-filter`, `mix-blend-mode`, gradients, masks, and `clip-path` are deferred. This spec ships their component model and the off-screen compositor they will ride, but not their shaders.
- **Window and surface lifecycle.** `buiy-window-and-surface-design` owns window creation, per-window top-layer routing, and the render-to-texture surface contract. This spec reserves the per-window node-group structure and an RTT target seam but does not build window management.

### Deliberate tier deviations from [foundation visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering)

v1 does not ship every row at exactly its foundation tier. Each deviation below is a deliberate choice, not an accident of scope:

- **`isolation` ELEVATED from C to shipped.** Foundation tiers `isolation` at C, but it rides the same F-tier compositor machinery this spec builds for group opacity (an effect group is an effect group), so shipping it now costs no extra mechanism. Pillar 6.
- **`content-visibility` paint-skip ELEVATED from C to shipped.** The off-screen `auto` paint-skip rides the F-tier subtree-skip machinery; shipping it now is free given that machinery. § 3.1 (`OffscreenAuto`, tracked dependency), Phase 11.
- **F-tier "per-element arbitrary-shape clipping" delivered as RECTANGULAR AABB only.** The full F-tier arbitrary-shape row ships in v1 as rectangular AABB clip (`ClipRect`). Rounded-rect clipping is **down-tiered to C** (`ClipRadius` reserved sibling, § 3.2), and `clip-path` (arbitrary shapes) stays **C** (matching [foundation visuals.md](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering)) — a reserved C-tier seam carried by the `path` primitive (architecture § 1.4), not built in v1. This is a deliberate down-tier of the hardest part of the row, not a silent omission.

## 2. Architectural pillars (one-line summaries)

Each pillar is detailed in [architecture.md](architecture.md) or the named child; this section is the index and the record of the decisions taken during brainstorming (2026-06-03).

1. **Immutable layout output, thin render consumer.** Layout writes; render reads. `painters_z` is walked forward for paint and backward for hit-test; never recomputed. The decisive principle ([blink/lessons.md](../../prior-art/blink/README.md)).
2. **Typed-primitive batched node + top-layer composite pass.** A small set of typed SDF primitives (quad / shadow / glyph / path) batched per primitive + layer, plus one ordered composite pass for the top layer, inside a per-window `BuiyRenderLabel` node group in `Core2d`. The node is placed after `StartMainPassPostProcessing` and before `Node2d::Tonemapping` via explicit render-graph edges (canonical in [architecture.md](architecture.md) § 1.3); `Bloom` / `PostProcessing` are optional-plugin nodes with no base-graph edges, so Buiy is not bloomed by default and stays crisp (a conditional `Bloom → BuiyRenderLabel` edge is inert unless a 2D bloom plugin adds the `Bloom` node). The main Buiy paint pass renders into the **view's color attachment**, whose format is the view's actual target — `Rgba8UnormSrgb` (SDR sRGB) by default for `Camera2d`, `Rgba16Float` only on an opt-in HDR view (the camera entity carrying the `Hdr` marker component). Effect-**group** intermediate targets are pinned `Rgba16Float` (linear) regardless of the view setting, so group opacity + isolation composite in linear space — but this is a per-group intermediate, **not** a default linear shared working target for the whole UI. On the default `Camera2d` view (`Tonemapping::None`) the `Node2d::Tonemapping` edge is **inert** — no tone curve runs — and the only transfer applied is the sRGB OETF at Buiy's `Rgba8UnormSrgb` attachment write. The placement before the tonemapping node is therefore the seam for the opt-in HDR/wide-gamut path; the "participates in tonemapping" framing has teeth only on that opt-in HDR (the `Hdr` marker component on the camera) / non-`None` path, and v1 does not tonemap the default UI (SDR pass-through). The shape two production Rust GPU UIs converged on ([prior-art/gpui](../../prior-art/gpui/README.md), [prior-art/makepad](../../prior-art/makepad/README.md)). **Runner-up:** a single grow-in-place node (rejected — cannot express the intermediate targets top-layer/effect compositing need); a full slimming-paint sub-graph (rejected — over-built before a concrete C-tier need).
3. **Hybrid handoff.** Persistent GPU buffers + atlas + view-uniform (the Phase-0-closeout-named upgrade that retires per-frame allocation and the per-instance y-flip/radius hack), with the per-frame instance set rebuilt from a `Changed<T>`-gated `Extract<Query>`. Damage tracking is the ECS change-detection Buiy gets for free; **no screen-space damage-rects in v1**. **Runner-up:** full immediate rebuild (rejected — wastes the gate-#14 budget); full retained scene (rejected — premature invalidation complexity, the classic stale-paint bug source).
4. **`ClipRect` computed in a render-prep pass, not in render extract.** Clip inputs (overflow, scroll viewport, containment:paint boundary, the box) are all layout-owned, so a `WriteClipRects` pass reading only layout output computes per-entity clip rects and writes a `ClipRect` component — keeping render a thin consumer and making clip geometry testable under the layout-snapshot gate (#5). A separate `Changed<ScrollOffset>` recompute keeps scroll responsive without re-running full layout. **Runner-up:** ancestor-walk in render extract (rejected — pushes tree traversal across the render boundary where it can silently drift from layout semantics and is invisible to gate #5).
5. **Layout owns the transform tree; render reads `GlobalTransform`.** Layout composes `ResolvedLayout.position` + `ResolvedTransform.matrix` into a Bevy `Transform`; `TransformSystems::Propagate` owns `GlobalTransform`; render reads `GlobalTransform`. Reuses Bevy's battle-tested hierarchical propagation and hands picking and the future 3D-anchored-UI/RTT path `GlobalTransform` for free. **Runner-up:** render reads `ResolvedTransform` directly (rejected — re-implements propagation Bevy already provides and diverges from picking/3D expectations).
6. **Off-screen effect-group compositor, built now, opacity + isolation only in v1.** The set of effects that form an `EffectGroup` — the SC-forming effects **plus** `backdrop-filter` — is the set that forces off-screen render targets. This `EffectGroup`-former set is a strict **superset** of the *effect-forming* SC-trigger subset: `backdrop-filter` forms a compositing boundary (it needs an off-screen target) but **not** a stacking context — and conversely the full SC-trigger set has non-effect formers (transform, positioned + `z-index`, `contain: paint`, root) that are **not** `EffectGroup` formers — so the two sets are deliberately distinct (canonical predicate in [effect-compositor.md](effect-compositor.md) § 1). So the compositor machinery (a render target per `EffectGroup`, GPU composite) is built in v1 and carries group `opacity` and `isolation` correctly. `filter` / `backdrop-filter` / `mix-blend-mode` get their component model and a reserved boundary but no shader in v1 (C-tier fast-follow). **Runner-up:** v1 forward-pass approximation of group opacity (rejected by the user — group opacity over overlapping children is subtly wrong, and correctness from day one was preferred).
7. **No property trees in v1.** `ResolvedTransform` and `painters_z` are the seeds; distinct clip/effect/scroll property trees are deferred until a concrete compositing need forces them. **The trigger condition that would revisit this is named: animating opacity (or transform) without re-running layout.** Until then, render paints the current frame's resolved values and relies on ECS change-detection. ([blink/lessons.md](../../prior-art/blink/README.md) "avoid building property trees speculatively".)

## 3. The component contract

This is the canonical list of the components on the layout↔render boundary. Children elaborate fields; this table is the single source of truth for names and ownership so the child files stay consistent. "Owner" is the subsystem whose spec defines the type; "render reads" / "render writes" is this subsystem's relationship to it.

### 3.1 Layout-owned, render reads (already exist)

| Component | Owner | What render reads it for |
|---|---|---|
| `ResolvedLayout` { position, size } | layout | Box geometry (folded into `Transform` by the bridge; see pillar 5). |
| `ResolvedTransform` { matrix } | layout | Composed transform (present iff non-identity); folded into `Transform`. |
| `UiTransform` | layout | `backface_visibility` (per-primitive cull) + `perspective` / `transform-style` (render-side channel, [clip-and-transform.md](clip-and-transform.md) § B.5); its non-identity transform also feeds the SC trigger sub-pass 6f reads off `ResolvedTransform` presence (composed from `UiTransform` by 6e — 6f does not query `UiTransform` directly). |
| `StackingContext` { painters_z: Vec<Entity> } | layout | Forward paint order; reversed hit-test order. Never re-sorted. |
| `Stacking` { z_index, isolation, top_layer } | layout | Top-layer membership + tier; isolation as an effect-group boundary. |
| `Containment` { contain, content_visibility, will_change } | layout | `contain` PAINT flag → clip boundary (consumed via `ClipRect`); STYLE/LAYOUT inform. (Its `content_visibility` field is the next row.) |
| `Overflow` { x, y } + `ScrollOffset` { x, y } | layout | Clip viewport + scroll translation (consumed via `ClipRect`). |
| `Containment.content_visibility` (Visible/Auto/Hidden) | layout | Hidden → skip subtree; Auto off-screen → skip paint (render half of Phase 11). |
| `Display::None` (enum variant) | layout | Render *extract/paint* never sees these — layout excludes `Display::None` entities from `painters_z`, so the extract/paint path reads no `Display`. The `WriteClipRects` render-prep pass is the one exception: its `Children`-walk reads `Option<&Display>` to prune `Display::None` subtrees ([clip-and-transform.md](clip-and-transform.md) § A.3). |
| `OffscreenAuto` | layout | Render skips paint for off-screen `content-visibility: auto` subtrees (layout-written, render-read; F-tier — named concretely in [component-model.md](component-model.md) § 12.2). **Layout marker not yet emitted — tracked dependency (§ 5).** |

> **Owner is logical-subsystem ownership, not module location.** `Owner = layout` names the *subsystem* whose spec defines and writes the type, **not** a claim that the type lives in a `layout` Rust module. The file homes differ: `ResolvedLayout`, `ResolvedTransform`, and `StackingContext` live in `components.rs` at the **crate root** (`crates/buiy_core/src/components.rs`), while `Stacking` lives in `layout/components.rs`. The § 6 crate-split reasoning turns on which *subsystem* reads/writes a type, so it must not be read as "everything layout-owned sits in the layout module."

### 3.2 Render-owned, this spec introduces

| Component | Tier | Purpose |
|---|---|---|
| `Background` | F | Solid color token (v1); reserved layered/gradient fields (C). Replaces `Visual.background_token`. |
| `Border` | F | Per-side width/style/color longhands; elliptical per-corner radius. Replaces `Visual.border_radius`. |
| `BoxShadow` | F | Ordered list; multiple, inset, spread, blur, color. |
| `Opacity` | F | Group opacity; non-1 forms an `EffectGroup` and an SC trigger (layout reads it back via pillar 6). |
| `Outline` | F | Focus indicator: color/style/width/offset. Painted outside the border box; never clipped by the element's own clip. |
| `Filter` | C (reserved) | Filter function list. Component + SC-trigger participation ship v1; shaders deferred. |
| `BackdropFilter` | C (reserved) | Backdrop filter list. Component + boundary ship v1; backdrop-sampling shader deferred. |
| `MixBlendMode` | C (reserved) | Blend mode. Component + SC-trigger participation ship v1; blend shader deferred. |
| `CssVisibility` | F (render-owned) | `visible`/`hidden`/`collapse`. Deliberately **not** `bevy::prelude::Visibility` (which has different variants/semantics — `Inherited`/`Hidden`/`Visible` — and its own visibility systems; same name-collision rationale as the `Transform`-reuse note). `Hidden` paint-skip (keep layout box) ships v1; `collapse` is a deferred (table-row/flex-item) marker, named-only. Defined field-level in [component-model.md](component-model.md) § 12; per-CSS `hidden` is also not hit-tested (picking interaction owned by `buiy-input-events-design`). |
| `WillChange` (promotion hint) | open / reserved | Render-side layer-promotion hint for the `will-change` follow-up (§ 4 item 3); not a committed v1 component — the contract lists it as reserved pending the layout-6f SC-forming-property clause. |
| `ClipRect` | F | Computed clip AABB {min,max}; fields + algorithm in [clip-and-transform.md](clip-and-transform.md). Written by `WriteClipRects`, read by render and picking. |
| `AncestorClip` | F | Companion clip AABB holding the intersection of **ancestor** clip boxes only (without the own-box step); fields + algorithm in [clip-and-transform.md](clip-and-transform.md) § A.2. Written by `WriteClipRects`, read by render for `Outline` painting ([component-model.md](component-model.md) § 7) so the focus ring is cropped by ancestor clips but not by the element's own clip. |
| `ClipRadius` | C (reserved) | Rounded-clip corners, deferred — the sibling carrier for rounded-corner clipping not built in v1. |
| `EffectGroup` | F | Carries `EffectReason` flags (opacity/isolation/filter/backdrop/blend); absence == no group. Read by the compositor to choose the composite op and allocate a render target. |

> **Crate-placement constraint (foundation § 5 'Crate-split refinement' / 'Final crate split').** The three SC-trigger components (`Opacity`/`Filter`/`MixBlendMode`) plus `BackdropFilter` (which shares the crate home for `EffectGroup` reasons — Buiy treats `backdrop-filter` as an **effect-group former only**; CSS additionally makes it form a stacking context, which Buiy does not rely on because `EffectGroup` membership is derived render-side, so layout 6f does not read it) must live where **both** layout sub-pass 6f and render can read them. If the workspace later splits `buiy_render` out of `buiy_core`, this dependency edge points layout → these components → render and must not be inverted. [architecture.md](architecture.md) pins their crate home.

### 3.3 The `Visual` migration

`Visual` (Phase 0: `background_token`, `foreground_token`, `border_radius`) was a temporary carrier. It was replaced by the render-side `Background` + `Border` (`render/components.rs`); `foreground_token` (reserved, unused) moved to `buiy-text-rendering-design`. The migration was a plan concern; this spec defines only the target (`Visual` deleted).

## 4. What this spec unblocks

Of the render-gated entries in [`docs/plans/follow-ups.md`](../../plans/follow-ups.md), **three resolve outright** once the matching piece of this spec lands; the **fourth is reserved-only** (its render seam exists here, but the work stays deferred). Non-px translate resolution, though listed in follow-ups, is **not render-gated** — it is pure layout-side and this spec does not gate it (see below):

1. **`UiTransform` paint + `Containment` PAINT clip + perspective/backface** (unblocked) → pillar 5 (bridge consumes `perspective`/`transform-style`/`backface-visibility`) + pillar 4 (`ClipRect` enforces PAINT).
2. **Render-side SC formers (`opacity`/`filter`/`mix-blend-mode`)** (unblocked) → § 3.2 reserved components; layout 6f gains its trigger-5 clause reading them.
3. **`Transform`/`GlobalTransform` bridge** (unblocked) → pillar 5.
4. **`will-change` layer-promotion + SC-former** (**reserved only, not unblocked**) → the render-side `WillChange` promotion hint (§ 3.2) is *reserved*, not a committed v1 component, and the `will-change` SC-*former* stays tier-E / deferred per the layout spec. This is a distinct, longer timeline from the near-term C-tier trigger-5 component clause (opacity / filter / mix-blend-mode, item 2 above) — do not conflate them. This spec only holds the seam open.

**Not render-gated: non-px translate units.** Resolving percent/`Cq*` `Translate` against the entity's own `ResolvedLayout` box is a pure layout-side computation — it needs neither the `Transform`/`GlobalTransform` bridge nor the render coordinate contract. It rides the layout follow-up backlog on its own, not on this spec.

## 5. Open questions

Decisions deferred to a sibling spec or to implementation calibration. Each names its owner.

1. **Per-window top-layer routing.** v1 ships a single global `TopLayerActivation` resource reading the primary window (the layout Phase-9 D2 simplification). True per-window routing is owned by `buiy-window-and-surface-design`. This spec reserves the per-window node-group structure; the global-activation simplification is a tracked dependency, not a final decision.
2. **Render-to-texture surface contract.** The RTT target abstraction (C-tier, feeds `buiy_3d`) is foundation § 5 'Render-to-texture surface API contract'. This spec reserves a render-target seam the `ViewNode` can target but does not commit the `buiy_3d` boundary.
3. **`::backdrop` modeling.** Whether modal/popover dimming is a render-synthesized backdrop (internal sort key `owner_index − ε` in top-layer order) or an app-spawned scrim entity. [paint-order-and-top-layer.md](paint-order-and-top-layer.md) § 4 *proposes* render-synthesized; this is **not-yet-committed**. The `owner_index − ε` `painters_z` materialization is part of that proposed model only — if accepted it would be a layout (sub-pass 6f) deliverable, not a settled v1 mechanism. Confirm against `buiy-window-and-surface-design`.
4. **Per-fixture perf and leak numbers.** Gate #14 (per-frame time vs main baseline, ±10% default slack) and gate #15 (RSS slope < 1 MB/min, atlas entries return to baseline) mechanisms are committed; the concrete per-fixture numbers are owned by `buiy-verification-design` and calibrate over time. The aggregate live-target budget is **committed as a mechanism** — `rt_pool_budget` (bytes; v1 default 64 MiB) with a degradation path (lowest-cost groups fall back to direct-to-parent forward compositing rather than allocating a target when the live set would exceed it), mirroring the atlas `page_budget` + LRU-under-pressure story (effect-compositor § 2.2/§ 2.3); only its *tuned* value is deferred to `buiy-verification-design`, exactly like the atlas `page_budget`. **Gate #14 is the *combined* layout+render+a11y per-frame measure — its ±10% slack/budget belong to the whole gate, not to render alone.** This spec owns and keeps-satisfiable only its render-time *component* of that gate (it is not a render-only gate); it defines atlas eviction/warmup and buffer pooling so that component stays within budget.
5. **Crate split.** Foundation § 5 'Final crate split' / 'Crate-split refinement' — whether `buiy_render` splits out of `buiy_core`. This spec's component-placement constraint (§ 3.2) holds under either outcome.
6. **Animation substrate.** Foundation § 5 'Animation library substrate'. v1 takes no dependency (no property trees); the revisit trigger is named in pillar 7.
7. **UI tonemapping vs authored-color/WCAG-contrast fidelity — opt-in-HDR path only.** `Camera2d` sets `Tonemapping::None` by default, so the default 2D view is SDR pass-through and the `Node2d::Tonemapping` node does not shift authored theme-token colors: the gate-#9 authored-contrast guarantee holds **unconditionally for the default view**. The open question is scoped to the *opt-in* path — an app that enables a non-`None` tonemapper or HDR on the UI view, where the curve would shift authored colors before store. Whether that path needs a UI-safe curve so the gate-#9 contrast guarantee still holds end-to-end is owned by `buiy-verification-design` / color-management. [color-and-forced-colors.md](color-and-forced-colors.md) references this open question where it discusses contrast.
8. **`OffscreenAuto` marker emission (tracked cross-spec dependency).** The `OffscreenAuto` marker this spec reads (§ 3.1, defined in [component-model.md](component-model.md) § 12.2; referenced by name in [paint-order-and-top-layer.md](paint-order-and-top-layer.md) § 5.3) does **not** exist in layout today (grep-confirmed). Its emission — placing the marker on entities whose `content-visibility: auto` subtree is currently off-screen — is the layout-side deliverable of the render half of Phase 11 and is owned by `buiy-layout-design`. Until layout emits it, render's `Auto` off-screen paint-skip has no input to read; this is a tracked dependency, not a final decision.
9. **`ColorToken::CurrentColor` resolution (tracked cross-spec dependency).** `CurrentColor` resolves to an inherited-text-color carrier that does **not** exist yet — it is owned by `buiy-text-rendering-design`. Until that spec exposes an inherited-text-color component, this spec ships an explicit v1 **fallback**: `CurrentColor` on a v1 `Border`/`Outline` resolves to the theme default foreground token (`CanvasText` / `color.text.primary`). The carrier swap-in is a tracked dependency, not a re-design; behavior and fallback are pinned in [color-and-forced-colors.md](color-and-forced-colors.md) § 2.0.
