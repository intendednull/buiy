# Buiy render — color correctness and the forced-colors contract

**Parent:** [README.md](README.md)

This file pins three things: how Buiy renders **color-correctly** (Buiy writes *linear* color values; on the default SDR `Rgba8UnormSrgb` view the hardware sRGB OETF runs at Buiy's own attachment write, and effect-**group** compositing is linear-correct because group targets are pinned `Rgba16Float`; Buiy painted into the post-processing window via the pinned `BuiyRenderLabel → Node2d::Tonemapping` load-bearing edge that [architecture.md § 1.3](architecture.md#13-node-placement-viewnode--viewnoderunnerbuiynode-in-core2d-after-post-processing-before-tonemapping) owns); how render **resolves theme tokens** against `Res<Theme>` at extract time and re-extracts on a theme switch; and the **forced-colors contract** (gate #11) — the two static checks that keep Buiy usable under Windows High Contrast and equivalent OS modes. It closes with the **boundary** against deferred C-tier color management, naming exactly where color-space conversion slots in without committing that work.

It owns no shaders the other children own: the typed-primitive node lives in [architecture.md](architecture.md), the off-screen compositor (where group `opacity` blends) in [effect-compositor.md](effect-compositor.md), the atlas (where gradient/mask samples will land) in [atlas-and-text-seam.md](atlas-and-text-seam.md), and the component fields in [component-model.md](component-model.md). This file is about *what color values flow through those pieces and in what space*.

Tier markers follow the foundation legend (**F** = foundation, **C** = core, **E** = extended); see [foundation/visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering).

## 1. The color pipeline: linear-light render, sRGB output

### 1.1 The invariant

> **Buiy writes *linear* color values; per-primitive alpha blends in the color attachment's space. On the default SDR `Rgba8UnormSrgb` view that attachment is an `*Srgb` surface, so the hardware OETF runs at Buiy's own attachment *write* (the main-pass SrcOver is therefore in encoded space — an accepted approximation, identical to `bevy_ui`). Effect-*group* compositing is linear-correct because group targets are pinned `Rgba16Float` linear.** Colors are converted sRGB → linear on the CPU before they reach the GPU; Buiy's fragment shader emits linear-light values into `ViewTarget`'s color attachment, whose format is `view_target.main_texture_format()` — the **format/edge seam whose API contract is declared once by [architecture.md § 1.4](architecture.md#14-pipelines-pipelinecache--stable-uuid-shaders)** (this file only references it). It is `TextureFormat::bevy_default()` = `Rgba8UnormSrgb` **SDR by default** (`Camera2d` does not add the `Hdr` marker, so the default 2D working target is SDR sRGB, not `Rgba16Float`). **F**

This is the target contract. Phase 0 happens to use a hardcoded `Rgba8UnormSrgb` color target — that re-encodes inline in a standalone node; the target Buiy node's `ColorTargetState` format is `view_target.main_texture_format()` so it shares the view's actual target (§ 1.2, [architecture.md § 1.4](architecture.md#14-pipelines-pipelinecache--stable-uuid-shaders), and [effect-compositor.md § 2.2](effect-compositor.md#22-allocation--pooling-the-frames_since_last_use-pool) — note the per-*group* targets there are pinned `Rgba16Float` linear regardless of the view, **not** `main_texture_format()`). On the default SDR view `main_texture_format()` *is* `Rgba8UnormSrgb`, so Phase 0's format already matches the default target; an opt-in HDR view (the camera entity carrying the `Hdr` marker component — `bevy_render-0.18.1` `view/mod.rs:202`) is the only case where it becomes `Rgba16Float`. The chain, traced through the shipped code (steps 1–3 are already correct at Phase 0 and preserved):

1. **Resolve** — a theme token resolves to a `bevy_color::Color` (the default theme stores `Color::srgb(..)` and `Color::WHITE`; see [theme.rs](../../../crates/buiy_core/src/theme.rs)). `Color` is the gamma-encoded authoring value.
2. **Convert to linear on the CPU** — `render::instance::to_instance` ([instance.rs](../../../crates/buiy_core/src/render/instance.rs)) calls `LinearRgba::from(draw.color)` and packs `[red, green, blue, alpha]` as `f32` into `InstanceData.color`. This is `bevy_color`'s `impl From<Color> for LinearRgba`, i.e. `Color::to_linear()` — sRGB gamma is removed here (per-channel `Srgba::gamma_function_inverse`), so every value crossing the GPU boundary is **linear**.
3. **Composite linear** — the SDF fragment shader ([shader.wgsl](../../../crates/buiy_core/src/render/shader.wgsl)) blends `color.rgb` against the antialiased coverage `alpha` with `BlendState::ALPHA_BLENDING` ([pipeline.rs](../../../crates/buiy_core/src/render/pipeline.rs)). Alpha blending is only physically correct in linear space; doing it on gamma-encoded values darkens edges and tints semi-transparent overlaps. Because the inputs are linear, the blend is correct **for the effect-group `Rgba16Float` path** — group targets are linear, so the SrcOver there resolves in true linear space. On the **default SDR view**, by contrast, the main-pass attachment is `*Srgb`, so a child painting **direct-to-window** has this same SrcOver resolved in the attachment's *encoded* space — the accepted v1 approximation detailed in step 4 / the blend-space seam below (identical to `bevy_ui`). The instance inputs are linear either way; only *where* the blend lands (linear group target vs. encoded `*Srgb` window) differs.
4. **Write linear into the view's color attachment; the OETF runs at that write on the default SDR view** — in the target state Buiy's pipeline writes into the view's color attachment, whose format is `view_target.main_texture_format()` (its API contract — `ViewTarget::main_texture_format(&self) -> TextureFormat`, returning `TextureFormat::bevy_default()` = `Rgba8UnormSrgb` unless the view has the `Hdr` marker, and `Camera2d` does **not** add `Hdr` by default — is owned by [architecture.md § 1.4](architecture.md#14-pipelines-pipelinecache--stable-uuid-shaders); verified in `bevy_render-0.18.1` `view/mod.rs:823`). Buiy's shader emits **linear** and Buiy does **no** manual OETF of its own. On the **default SDR `Rgba8UnormSrgb` view** the attachment is an `*Srgb` surface, so the hardware OETF runs at *Buiy's own write* — which means the per-primitive SrcOver alpha blend happens in **encoded** space (an accepted approximation, exactly what `bevy_ui` does). Only on an **opt-in HDR `Rgba16Float` view** (the camera entity carrying the `Hdr` marker component) does Buiy's linear output stay extended-range, with the sRGB/tonemap encode deferred to the shared post-tonemapping store; there is no shared encode pass on the default `Tonemapping::None` view (§ 1.2). Either way no manual `pow(2.2)` appears in Buiy's WGSL.

The CPU-side `LinearRgba` conversion is retained in the target state. When the hybrid handoff lands ([architecture.md](architecture.md), pillar 3) the *coordinate* packing moves to a view uniform, but the **color** stays pre-linearized on the CPU: it is a single multiply-free table-ish transcendental per channel done once per changed instance, and keeping it CPU-side means the instance buffer is unambiguously linear regardless of which primitive shader consumes it. The instance buffer being linear is exactly what lets the GPU OETF the value correctly at the `*Srgb` attachment write (SDR view) and lets the effect-group `Rgba16Float` targets composite group opacity / isolation in true linear space.

> **One pipeline per target format (the build implication).** A wgpu `RenderPipeline`'s fragment `ColorTargetState` format is *fixed at pipeline creation* and must equal the bound attachment's format — one pipeline cannot target both `Rgba8UnormSrgb` (the default view) and `Rgba16Float` (an effect-group target). So **each typed-primitive pipeline (quad / shadow / glyph / path) is a `SpecializedRenderPipeline` keyed — at least — on the target `ColorTargetState` format**, and Buiy builds each primitive for *both* formats it targets: the **view format** (`view_target.main_texture_format()`, `Rgba8UnormSrgb` by default — § 1.2, [architecture.md § 1.4](architecture.md#14-pipelines-pipelinecache--stable-uuid-shaders)) for the main pass, and **`Rgba16Float`** for effect-group targets ([effect-compositor.md § 2.2](effect-compositor.md#22-allocation--pooling-the-frames_since_last_use-pool)). The instance data is format-independent (always linear); only the pipeline's blend/encode target changes, so the specialization is just a format key, not a second shader.
>
> **The blend-space seam — bounded, accepted v1 approximation.** Because the main-pass attachment is `*Srgb` (SDR view), a child quad painting **direct-to-window** has its SrcOver alpha blend resolved in the attachment's *encoded* (SDR) space, whereas the **same quad inside an effect group** blends in *linear* (the group's `Rgba16Float` target). The consequence is concrete: wrapping otherwise-identical content in an `opacity:~1` (or any other effect-group former, [effect-compositor.md § 1](effect-compositor.md#1-the-identity-effect-group-set--effect-forming-stacking-context-set)) subtly changes how that content's semi-transparent overlaps blend — encoded vs. linear. v1 accepts this seam as an approximation (the encoded main-pass blend is exactly what `bevy_ui` does); the only fully-correct alternative — paint **all** content into linear intermediates and do a single sRGB resolve at the end — is noted as the **revisit path**, not v1, because it would force every direct-to-window primitive through an off-screen linear target even when no effect group is present.

### 1.2 The pre-tonemapping placement is the color-management hook

The Buiy node sits inside `Core2d` pinned by the explicit render-graph edges [architecture.md § 1.3](architecture.md#13-node-placement-viewnode--viewnoderunnerbuiynode-in-core2d-after-post-processing-before-tonemapping) owns — the canonical owner of the graph wiring. Those edges are: an after-anchor edge `add_render_graph_edge(Core2d, Node2d::StartMainPassPostProcessing, BuiyRenderLabel)`; the **load-bearing** edge `add_render_graph_edge(Core2d, BuiyRenderLabel, Node2d::Tonemapping)`; and a **conditional** edge `add_render_graph_edge(Core2d, Node2d::Bloom, BuiyRenderLabel)` that is inert unless a 2D bloom plugin adds the `Bloom` node. The base `Core2d` graph wires only `… EndMainPass → StartMainPassPostProcessing → Tonemapping → EndMainPassPostProcessing → Upscaling` (`bevy_core_pipeline-0.18.1` `core_2d/mod.rs`); `Node2d::Bloom` and `Node2d::PostProcessing` are **reserved labels with no base-graph edges** — they are **optional-plugin nodes that only appear when their plugin adds them**, landing between `StartMainPassPostProcessing` and `Tonemapping` when present. Anchoring after `StartMainPassPostProcessing` places Buiy inside the post-processing window; the conditional `Bloom → BuiyRenderLabel` edge keeps Buiy painting *after* a 2D bloom node when one exists, so Buiy UI does *not* bloom (crisp text and edges). The load-bearing `BuiyRenderLabel → Tonemapping` edge is what guarantees Buiy writes into the **same color attachment as 2D scene content, before tonemapping** — on the default SDR view that attachment is `Rgba8UnormSrgb`.

Because Buiy paints into that shared color attachment, the placement **opens the seam for whatever tonemapping / color-management the view enables** — but on the default `Camera2d` view that seam is **inert**: `Camera2d` sets `Tonemapping::None` by default (`bevy_core_pipeline-0.18.1` `core_2d/mod.rs:88`, `register_required_components_with::<Camera2d, Tonemapping>(|| Tonemapping::None)`), the attachment is the SDR `Rgba8UnormSrgb` surface (not a linear shared working target), and the OETF runs at **Buiy's own `*Srgb` attachment write** (§ 1.1), so the `Tonemapping` node is a pass-through and the UI is **not** tonemapped. The "Buiy participates in tonemapping" framing therefore has **teeth only on the opt-in HDR / non-`None` path** — when an app adds the `Hdr` marker or selects a non-`None` tonemapper, the working target becomes an extended-range float and the encode moves into the `Tonemapping` node downstream of Buiy. The placement's value is therefore the **seam for opt-in HDR / wide-gamut**, not a claim that v1 tonemaps the UI or that the default view shares a linear working target. Because the default 2D view is SDR pass-through with `Tonemapping::None`, there is no curve to shift the authored token colors before they reach pixels — so whether the *authored* contrast survives to the screen is decided at the linear blend / OETF write that gate **#2** (the visual-regression golden) covers, not by gate #9. (Gate #9 is the static token-pair contrast linter of § 3.2 — it checks the authored token *values*, independent of the render path.)

This is pillar 2's "(pre-tonemapping, so output participates in HDR/color management)" clause, and it is the *enabling seam* for the deferred E-tier HDR pass and C-tier wide-gamut output ([foundation/visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering): "HDR rendering pass" **E**, "Color management … sRGB / display-p3 / rec2020 output" **C**). When a window advertises an HDR or wide-gamut surface, the working format upstream of tonemapping becomes an extended-range float target and Buiy's linear output flows through unchanged — Buiy does not have to learn a second color path. **Inverting this placement (painting after tonemapping) is rejected**: it would force Buiy to color-match the post-tonemap frame itself, which is exactly the complexity the pre-tonemap choice avoids (recorded in [node.rs](../../../crates/buiy_core/src/render/node.rs) module docs).

> **Open — tonemapping vs. authored-color / WCAG-contrast fidelity (opt-in-HDR path only).** For the default 2D view, `Tonemapping::None` makes the node a pass-through, so authored theme-token colors reach the screen intact: the static gate-#9 token-pair contrast lint and the rendered gate-#2 golden agree. The open question is **scoped to the opt-in path**: once an app enables a non-identity tonemap curve (for an HDR / wide-gamut view), that curve **shifts the authored theme-token colors** before they reach the screen — which can move a theme's `Background`/`Outline` pair off the exact ratio the author targeted. Gate #9 (static token-pair lint) would still pass on the authored values, but the *rendered* pixels checked by gate #2 could diverge (the focus-ring ≥3:1 / ≥2px strength asserted in § 3.2). Whether such a view should keep `Tonemapping::None` or adopt a UI-safe curve so authored token colors survive intact is **owned by `buiy-verification-design` / color-management**, not resolved here; see [README § 5](README.md#5-open-questions). This file pins only the graph placement; the contrast claims below (§ 3.2) are unconditional for the default view and written, for the opt-in-HDR path, against the assumption that this open question lands on a UI-color-preserving answer.

> **Constraint for every future primitive.** Quad, shadow, glyph-alpha, and path primitives ([architecture.md](architecture.md)) all target the same view color attachment and all receive **linear** color (the GPU OETFs at the `*Srgb` write on the default SDR view). The atlas-sampled primitives (glyph alpha, gradient, mask) sample *coverage/alpha*, not color — their color tint arrives linear in the instance record, so atlas content needs no color-space tag in v1. The off-screen effect-group targets ([effect-compositor.md](effect-compositor.md)) are by contrast pinned `Rgba16Float` linear (not `main_texture_format()`), so a group's contents composite correctly **in linear space** before the group's `opacity` multiply; the final composite of a group back into its parent target SrcOver-blends in the parent target's space.

## 2. Theme-token resolution at extract time

### 2.0 The `ColorToken` type

Every themeable render-component color field holds a `ColorToken`, not a resolved `Color` ([component-model.md § 2](component-model.md#2-color-tokens-vs-resolved-colors) treats it as opaque and points here for the definition and its resolution). It is the typed CSS `<color>` reference set Buiy needs on the paint boundary:

```rust
/// A themeable color reference, resolved against `Res<Theme>` at extract time
/// (§ 2.1). Default is `Transparent`, matching `Visual.background_token == ""`
/// and the CSS-initial "no fill" semantics (component-model.md § 2/§ 3).
#[derive(Reflect, Clone, Default, PartialEq, Debug)]
pub enum ColorToken {
    /// CSS `transparent` (and the empty-token "skip the fill" case). The
    /// default; resolves to `Color::NONE` (alpha 0). Extract skips emitting a
    /// quad for a transparent fill (component-model.md § 3).
    #[default]
    Transparent,
    /// A named theme token, e.g. `Token("surface")`. Resolves via
    /// `Theme::color(name)`; a miss is the magenta sentinel + `warn!` (§ 2.2).
    Token(Cow<'static, str>),
    /// CSS `currentColor`: resolves to the element's inherited *text* color
    /// (the foreground token owned by `buiy-text-rendering-design`), so a
    /// border/outline can track the text color without re-authoring it. That
    /// inherited-text-color carrier does not exist yet — a TRACKED cross-spec
    /// dependency. v1 FALLBACK: until the text spec exposes the inherited-text-
    /// color component, `CurrentColor` resolves to the theme default foreground
    /// token (`CanvasText` / `color.text.primary`); see § 2.0 prose + README § 5.
    CurrentColor,
    /// A CSS system-color keyword (`Canvas`, `CanvasText`, `Highlight`, …).
    /// Resolves against the active theme's system-color map; under
    /// forced-colors this is the *only* set that resolves (§ 3.1).
    SystemColor(SystemColorKeyword),
}
```

Each variant resolves to one `bevy_color::Color` at extract time: `Transparent` → `Color::NONE`; `Token(name)` → `Theme::color(name)` (sentinel on miss, § 2.2); `CurrentColor` → the inherited text color *(see the v1 fallback below)*; `SystemColor(kw)` → the active theme's entry for that keyword (the 16-keyword set is enumerated in § 3). `SystemColorKeyword` is the foundation-**F** system-color enum ([visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering)).

> **`CurrentColor` v1 resolution — a TRACKED cross-spec dependency.** The inherited-text-color carrier that `currentColor` should resolve against is owned by `buiy-text-rendering-design` and **does not exist yet**. Until that spec exposes an inherited-text-color component, the **concrete v1 behavior** is: `CurrentColor` on a v1 `Border`/`Outline` resolves to the **theme default foreground token** — `CanvasText` under forced-colors, otherwise the theme's `color.text.primary` (foreground) token. The **default-path fallback resolves today**: `color.text.primary` is an ordinary theme token that `Theme::color` returns now. The **forced-colors `CanvasText` branch**, by contrast, only resolves once `buiy-theme-tokens-design` delivers the forced-colors **system-color map** (the entry for `CanvasText` et al.) — already a tracked dependency (§ 2.0 prose, [README § 5](README.md#5-open-questions)); until that map lands a `CanvasText` lookup misses → magenta sentinel + `warn!` (§ 2.2), the same self-announcing failure as any other missing token. This is deterministic and self-correcting: when the text spec lands the inherited carrier, this resolution rule switches to read it with no change to the `ColorToken` variant set or the extract path. The token-parser/typed-taxonomy work (how authored strings map onto these variants) is owned by `buiy-theme-tokens-design`; this file fixes the *render-side variant set and how each resolves*.

### 2.1 Resolution happens in `Extract`, against `Res<Theme>`

Render resolves color tokens to concrete `Color` values **during the extract phase**, reading the main world's `Theme` resource through `Extract<Res<Theme>>`. The Phase-0 shape (`extract_buiy_draws` in [mod.rs](../../../crates/buiy_core/src/render/mod.rs)) is the target shape; the target state only generalizes *which* components carry tokens:

```rust
// Target: Background/Border/Outline/BoxShadow carry tokens; extract resolves
// each against Res<Theme> to a packed linear instance. Phase 0's single
// Visual.background_token generalizes to this set (component-model.md).
fn extract_buiy_nodes(
    mut commands: Commands,
    paints: Extract<Query<(&Background, &ResolvedLayout, &GlobalTransform, &ClipRect /* … */), With<Node>>>,
    theme: Extract<Res<Theme>>,
    // Token resolution is window-independent; the window param is here only for
    // the per-window pillar (§4), so extract reads ALL windows, never just the
    // primary — a With<PrimaryWindow> filter would contradict per-window-by-
    // construction (architecture.md §4 / README pillar 2).
    windows: Extract<Query<(Entity, &Window)>>,
) { /* token -> Color via theme.color(token) -> LinearRgba::from(..) -> InstanceData */ }
```

`Theme::color(&str) -> Option<Color>` ([theme.rs](../../../crates/buiy_core/src/theme.rs)) is the resolver. **Why extract-time, not a main-world pre-pass:** resolution is a pure read of a layout-independent resource, it produces a value only render needs, and doing it in extract keeps it off the main-world hot path and naturally re-runs every frame the extract query fires. It does **not** violate pillar 1 (thin render consumer): pillar 1 forbids render *re-deriving geometry / paint order / stacking*; token→color is none of those — it is a leaf-value lookup with no tree traversal. (Clip geometry, by contrast, *does* traverse and so is computed in the `WriteClipRects` render-prep pass, not extract — see [clip-and-transform.md](clip-and-transform.md).)

### 2.2 Missing-token policy

On a miss, `Theme::color` returns `None`. Phase 0 substitutes a **magenta sentinel** `Color::srgb(1.0, 0.0, 1.0)` and emits a `warn!` naming the token ([mod.rs](../../../crates/buiy_core/src/render/mod.rs) `MISSING_TOKEN_FALLBACK`). The target state keeps the visible-magenta-plus-warn behavior — a missing token is an author bug that should be *loud in screenshots and logs*, never silently transparent. The Phase-0 comment's "promote to `error!` once tokens are typed" is a typed-token-taxonomy decision owned by `buiy-theme-tokens-design`, not this spec; render's contract is only "miss → sentinel + diagnostic, never panic, never silent."

The sentinel participates in the same linear pipeline as any other color (it is an ordinary `Color::srgb`), so a missing token is visible *and* correctly composited — you see solid magenta, not a magenta-tinted blend artifact.

### 2.3 A theme switch invalidates and re-extracts

Swapping the active theme (light↔dark, a brand variant, or a hot-reloaded `ThemeAsset` — gate #13) must re-resolve every token-bearing entity's color. The mechanism:

- **`Theme` is a `Resource`** ([theme.rs](../../../crates/buiy_core/src/theme.rs)). Replacing it (`commands.insert_resource(new_theme)`) or mutating it via `ResMut<Theme>` marks the resource **changed**.
- **Extract re-runs and re-reads it.** Because resolution is extract-time and reads `Theme` live, the next frame's extract sees the new resource and produces the new linear colors. There is no cached, theme-stamped instance buffer to invalidate on the render side — the `Changed<T>`-gated instance rebuild ([architecture.md](architecture.md), pillar 3) is keyed on the *paint components and layout*, and those have not changed, so a naïve gate would **miss a theme-only switch**.
- **The fix is an explicit theme-change trigger.** Extract treats `theme.is_changed()` as a global "re-resolve all token-bearing instances this frame" signal: when the `Theme` resource is changed, the per-entity `Changed<T>` short-circuit is bypassed and every token-bearing paint is re-resolved and re-packed. This mirrors the layout side, where a theme switch that alters spacing/radii tokens invalidates `BoxModel` and re-runs `SyncStyles` ([layout architecture.md § 9](../2026-05-08-buiy-layout-design/architecture.md#9-performance-contract), "Mass-mutation frame (e.g. theme switch …)"). Color tokens that feed *only* paint (not layout) are render's responsibility to invalidate, and `Theme::is_changed()` is the single edge that does it.

> **Open — token typing and the change granularity.** Whether a fine-grained "only re-resolve entities whose *referenced* tokens changed" path is worth building (vs. the all-token-bearing re-resolve above) depends on the typed-token taxonomy and is owned by `buiy-theme-tokens-design`. The coarse all-re-resolve is correct and bounded (`O(token-bearing entities)` on the rare theme-switch frame, `O(0)` steady-state); the fine-grained path is an optimization, not a correctness fix. Flagged, not silently resolved.

## 3. The forced-colors contract (F-tier, gate #11)

**Forced-colors** is the OS-driven high-contrast mode (Windows High Contrast, and the `forced-colors: active` media feature). When active, the OS mandates a small palette of **system colors** and the app must paint within it. Buiy surfaces the OS state as `UserPreferences.forced_colors: bool` ([theme.rs](../../../crates/buiy_core/src/theme.rs)); the foundation lists this **F** ([accessibility.md](../2026-05-07-buiy-foundation/accessibility.md), "User preferences: `forced-colors: active | none` + system color keywords. **F**"). The CSS system-color keyword set is foundation-**F** too ([visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering): `Canvas`, `CanvasText`, `LinkText`, `ButtonText`, `ButtonBorder`, `GrayText`, `Highlight`, `HighlightText`, `Field`, `FieldText`, `Mark`, `MarkText`, `SelectedItem`, `SelectedItemText`, `AccentColor`, `AccentColorText`).

Gate #11 ([foundation/verification.md § CI gates](../2026-05-07-buiy-foundation/verification.md#ci-gates)) is two static + visual checks. This section explains how the render component model satisfies each.

### 3.1 Check (a): no color outside the system-color token set when forced-colors is active

**The claim:** when `forced-colors: active`, no widget in the default catalog paints a color that did not resolve from a **system-color token**. (`forced-color-adjust: none` per-element opt-out and `color-scheme` are **C** — [visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering) — and out of v1's default-catalog scope; the v1 gate covers the default theme path where every paint goes through forced-colors remapping **provided the forced-colors system-color map exists**.)

> **v1 prerequisite — the forced-colors system-color map must exist (even as a stub).** The "every paint goes through forced-colors remapping" claim is **conditional on a minimal v1 stub forced-colors system-color map being present** — i.e. the active forced theme's `colors` map must actually hold the 16 system-color keys (`Canvas`, `CanvasText`, `Highlight`, …). This is a **hard v1 prerequisite**, not an optional polish: with no such map, the very tokens forced-colors widgets reference miss resolution. Concretely, `CurrentColor` resolves to `CanvasText` under forced-colors (§ 2.0 v1 fallback), so an absent `CanvasText` entry makes every `currentColor` border/outline **miss → magenta sentinel + `warn!`** (§ 2.2) rather than remap — the gate would observe magenta, not a constrained palette. The stub map (owned by `buiy-theme-tokens-design`, even as placeholder system-color values) is therefore the thing that makes check (a) meaningful at v1; until it lands, #11(a) and the forced-colors goldens are blocked on the same dependency the goldens are (cross-ref [verification § 3 gate #11(b)](verification.md#3-the-render-relevant-ci-gate-map), whose "minimal v1 stub map" note is the shared blocker).

**How the component model supports it.** Every render-side paint color is a **token reference resolved against `Res<Theme>`** (§ 2), never a literal `Color` baked into a widget. So forced-colors is modeled as a **theme variant**: when `forced_colors` is set, the active `Theme` is the forced-colors theme whose `colors` map keys are exactly the 16 system-color tokens, and every `Background`/`Border`/`Outline`/`BoxShadow` token a default widget references resolves into that constrained map. A widget that hard-codes a non-token color, or references a brand token absent from the forced map, fails resolution → magenta sentinel + `warn!` (§ 2.2) — i.e. the violation is *self-announcing at runtime* in addition to being caught statically.

**The concrete selection mechanism.** `Theme` and `UserPreferences` are **separate main-world resources** (`Res<Theme>`, `Res<UserPreferences>` — [theme.rs](../../../crates/buiy_core/src/theme.rs): `Theme { colors: HashMap<String, Color> }`, `UserPreferences { forced_colors: bool, … }`). Forced-colors is selected in the **main world, before extract**, by swapping which `Theme` resource is active when `UserPreferences.forced_colors` flips: a main-world system observes the `forced_colors` edge (a `Changed<UserPreferences>` / OS-event handler owned by `buiy-window-and-surface-design`) and calls `commands.insert_resource(forced_colors_theme)` — replacing `Res<Theme>` with the variant whose `colors` map holds exactly the 16 system-color keys (and restoring the prior theme when `forced_colors` clears). Because the swap mutates `Res<Theme>`, it rides the **existing § 2.3 `Theme::is_changed()` re-resolve edge**: the next frame's extract re-reads `Res<Theme>` live and re-resolves every token-bearing paint into the constrained map — no separate forced-colors code path in extract for *color* selection. (The one place extract reads `UserPreferences.forced_colors` directly is the **shadow-suppression branch** of § 3.3, which is a draw-skip, not a color-resolution decision.) Equivalently the forced/system palette can be carried *inside* the `Theme` as a selectable sub-map chosen at the same `forced_colors` edge; either way the render-side contract is identical — extract resolves against whatever `Res<Theme>` is active, and the forced variant is what the main world makes active when `forced_colors` is set.

**The static check is a token-flow analyzer** (gate #11, "token-flow analyzer"). It is a build-time / test-time pass over the default widget catalog that walks each widget's emitted `Background`/`Border`/`Outline`/`BoxShadow` and asserts the color field is a **token reference** (not a literal `Color`) and, under the forced-colors theme, that the token resolves inside the system-color key set. The analyzer is possible *only because* paint color is uniformly a token edge in the component model — there is no second, literal-color path for it to miss. This is why § 2's "tokens, not literals" rule is load-bearing for accessibility, not just theming.

### 3.2 Check (b): no shadow-only affordance

**The claim:** every focusable / state-bearing widget conveys its affordance and state with a **non-shadow** visual cue — a border, fill, or outline — because Buiy **drops `box-shadow` entirely** in forced-colors mode (a Buiy design decision justified in § 3.3, not an OS/CSS mandate), so a widget that signals "focused" or "pressed" using only a shadow becomes indistinguishable.

**How the component model supports it.** The render component model deliberately separates the **shadow channel from the structural channels**:

| Channel | Component | Survives forced-colors | Role in the check |
|---|---|---|---|
| Shadow | `BoxShadow` | **No** (Buiy suppresses it — § 3.3) | Must never be a widget's *only* state cue. |
| Fill | `Background` | Yes (remapped to a system color) | A non-shadow cue. |
| Border | `Border` | Yes (remapped; `ButtonBorder`/`CanvasText`) | A non-shadow cue. |
| Focus ring | `Outline` | Yes (remapped to `Highlight`) | A non-shadow cue; painted outside the border box, never clipped (component-model.md). |

Because these are **four distinct components**, "does this widget have a non-shadow cue for state X?" is a structural query over which components a widget emits in each state — answerable statically without rendering. The gate's static half walks the catalog's per-state styling and asserts: for every focusable/state-bearing widget and every state it distinguishes (`:focus-visible`, pressed, checked, selected, …), at least one of `Background`/`Border`/`Outline` *differs from the resting state*, independent of any `BoxShadow` delta. A widget whose only inter-state difference is `BoxShadow` fails. The gate's **visual half** is the golden-image diff under the forced-colors theme (gate #11, "golden visual diff under forced-colors") — it confirms the *rendered* result, with `BoxShadow` suppressed, still shows the distinction.

> **Why `Outline` is the structural anchor for focus.** `Outline` is a **dedicated F-tier component** ([README § 3.2](README.md#32-render-owned-this-spec-introduces)) precisely so the focus indicator is never expressed as a shadow. It is painted *outside* the border box and *is not clipped by the element's own clip* (component-model.md), which keeps the focus ring at full ≥2px / ≥3:1 strength (WCAG 2.4.7 / 2.4.11 — [accessibility.md](../2026-05-07-buiy-foundation/accessibility.md)) even on a clipped/overflow-hidden element, and visible in forced-colors where it remaps to `Highlight`. This is the render-side reason the foundation can mark "Focus Visible **F**" with confidence. (The ≥3:1 ratio is checked statically on the *authored* token-pair values by gate #9; whether that authored ratio survives to *pixels* is a render-path question gate #2's golden answers, not gate #9. For the default `Tonemapping::None` 2D view the authored colors reach the stored frame intact, so the two gates agree unconditionally — whether a non-identity tonemap curve on an opt-in HDR/wide-gamut view preserves it is the narrowed open question flagged in § 1.2 / [README § 5](README.md#5-open-questions).)

### 3.3 Forced-colors suppression is a render-side rule, not per-widget code

In forced-colors mode, render **does not draw `BoxShadow` instances** for default-catalog widgets — the shadow primitive batch ([architecture.md](architecture.md)) is skipped when `UserPreferences.forced_colors` is set. This is one branch in extract, not a per-widget opt-out, so widgets cannot accidentally retain a shadow.

> **This is a Buiy *design decision*, not an OS/CSS mandate.** The CSS forced-colors model does *not* require dropping `box-shadow`; it remaps the limited color properties (background/border/text/etc.) to system colors and leaves `box-shadow` largely to the UA. Buiy chooses **unconditional** shadow-suppression because it makes the structural-cue guarantee (§ 3.2) self-enforcing: with shadows always gone under forced-colors, a widget whose only state cue *were* a shadow is guaranteed to fail the static check rather than silently degrade on some platforms. The structural-cue guarantee is exactly what makes this safe — nothing load-bearing is lost, because every state distinction already has a non-shadow cue. **Runner-up (rejected):** keep author shadows under forced-colors and rely solely on the § 3.2 cue check to catch shadow-only affordances. Rejected because it leaves a non-system color (the shadow) painting in a mode that is supposed to constrain the palette, and because "the check will catch it" is a weaker guarantee than "the mode structurally cannot express it" — the suppression turns a lint into an invariant. (`forced-color-adjust: none` to *preserve* an author's shadow/color is **C** and rides the same branch later, as a per-entity override — the seam is the `forced_colors` read in extract; the override component is reserved to `buiy-theme-tokens-design`.)

### 3.4 What this file owns vs. defers for gate #11

- **Owned here:** the rule that paint color is a token edge (enables check (a)); the four-channel component split and unconditional shadow-suppression (enables check (b)); the concrete forced-colors selection mechanism — a main-world `Theme` swap to the system-color variant at the `UserPreferences.forced_colors` edge, re-resolved through the existing § 2.3 `Theme::is_changed()` extract path (§ 3.1).
- **Deferred / cross-file:** the *contents* of the forced-colors theme (which token maps to which system color) belong to `buiy-theme-tokens-design`; the analyzer's harness wiring and the golden-image baseline belong to [verification.md](verification.md) and `buiy-verification-design`; the per-widget "which states must differ" roster belongs to `buiy-widget-catalog-design`. This file pins the *render-side mechanism that makes those checks expressible*.

## 4. Boundary: deferred C-tier color management

Full color management is **C-tier and explicitly deferred** ([foundation/visuals.md § 3.3](../2026-05-07-buiy-foundation/visuals.md#33-visual-styling-and-rendering); [README § 1 non-goals](README.md#non-goals): "gradients … are deferred"). v1 ships exactly the linear-light sRGB pipeline of § 1. The deferred set and **where each slots in** without re-architecting:

| Deferred feature | Tier | Where it slots in (no v1 commitment) |
|---|---|---|
| `lab()` / `lch()` / `oklab()` / `oklch()` color | C | Resolution-time only: the token resolver returns a `bevy_color::Color`, whose enum already carries `Laba`/`Lcha`/`Oklaba`/`Oklcha`/`Xyza` variants in Bevy 0.18. `LinearRgba::from(color)` already converts *any* `Color` variant to linear — each variant has its own **direct** `LinearRgba` conversion (`impl From<Color> for LinearRgba`, `bevy_color-0.18.1` `color.rs:548`), not routed through any single intermediary space. So an `oklch()` authored token flows through the **existing** § 1 pipeline unchanged — no render change, only a token-parser change owned by `buiy-theme-tokens-design`. |
| `color()` profiles (display-p3, rec2020, a98, prophoto, xyz) | C | Output-gamut, not blend-space. The pipeline's working space stays linear; the *target format* and a final gamut-map slot in at the §1.2 pre-tonemapping seam when the window advertises a wide-gamut surface (`buiy-window-and-surface-design` owns surface format). Buiy's linear output is gamut-agnostic until that final encode. |
| `color-mix(in <space>, …)` | C | A resolution-time function over two resolved colors in a named space; produces one `Color`. Slots in at the token resolver, upstream of § 1. No render change. |
| **Gradient / color-stop interpolation in a named space** | C | **This is the one place a *render-side* color-space conversion lands.** A gradient is rasterized into the texture atlas ([atlas-and-text-seam.md](atlas-and-text-seam.md)); interpolating stops "in oklch" vs "in srgb" is a per-texel conversion done **when the gradient texture is generated**, in the atlas-bake step — not in the per-fragment hot path. The atlas seam reserves the gradient slot; the *interpolation-space* parameter rides the gradient's descriptor. v1 bakes no gradients, so the converter is absent, but the bake step is the named insertion point. |
| Per-element `filter` / `backdrop-filter` / `mix-blend-mode` color math | C | Run inside the off-screen effect-group compositor in **linear working space** ([effect-compositor.md](effect-compositor.md)); their components ship v1 (reserved), shaders deferred. Because compositing is already linear (§ 1.1), these effects get a correct color space for free when their shaders land. |

**The non-preclusion guarantee:** every deferred item above attaches at one of three named seams — the **token resolver** (color spaces, `color-mix`), the **atlas bake step** (gradient interpolation space), or the **pre-tonemapping working-space target** (wide-gamut output, HDR). None of them requires changing the §1 linear-blend invariant, the `LinearRgba`-on-the-CPU packing, or the component model. The v1 pipeline is the *floor* of the C-tier pipeline, not a parallel path that C-tier work would have to tear out. Where any of these is genuinely undecided (e.g. whether gradient bake or a per-fragment LUT is the right gradient strategy at scale), it is an open question for `buiy-theme-tokens-design` / a future render follow-up — see [README § 5](README.md#5-open-questions); this file does not invent a resolution.

## 5. Verification

Tied to the gates in [foundation/verification.md](../2026-05-07-buiy-foundation/verification.md) and detailed in [verification.md](verification.md):

- **Linear-light correctness (§ 1)** — gate #2 (visual regression): a golden of two overlapping semi-transparent fills and an antialiased rounded-rect edge; a gamma-space blend in the *group* compositor regresses the overlap tint, so the golden is the linear-blend assertion for the effect-group `Rgba16Float` path. The golden reads back the **stored, post-tonemapping sRGB output** of the frame; on the default SDR `Rgba8UnormSrgb` view a match confirms the GPU OETF at Buiy's `*Srgb` attachment write and the linear-correct group compositing, while on an opt-in HDR `Rgba16Float` view it additionally confirms the OETF at the shared post-tonemapping store. The per-primitive main-pass SrcOver is in encoded space on the default SDR view (an accepted approximation matching `bevy_ui`), so the golden's main-pass overlap is asserted against that accepted behavior, not against a linear main-pass blend.
- **Token resolution + theme switch (§ 2)** — unit/headless (no GPU): assert `extract` produces the magenta sentinel + one `warn!` on a missing token; assert that replacing `Res<Theme>` re-resolves a fixture's instance color on the next frame (the `is_changed()` invalidation edge). Hot-reload of `ThemeAsset` is gate #13.
- **Forced-colors (§ 3, gate #11)** — check (a): the token-flow analyzer over the default catalog (build/test-time, no GPU) asserts every paint color is a system-color token reference under the forced theme. Check (b): the structural query asserts every focusable/state-bearing widget has a non-`BoxShadow` inter-state cue, plus the forced-colors golden-image diff (gate #2 harness, shadows suppressed) confirms the distinction renders.
- **C-tier boundary (§ 4)** — no gate in v1 (the features are deferred); the test that *protects the seam* is the linear-blend golden above, which fails if a future change accidentally moves blending out of linear space.
